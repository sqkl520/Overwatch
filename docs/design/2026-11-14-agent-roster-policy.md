# 岗位策略：可配置的是什么，边界在哪

> 用户 2026-11-14 的裁定。**本文件推翻 2026-11-11 那份「必须问问题不可关闭」的表述。**

## 用户原话

> **选启用哪些岗位，遇到阻塞（验收不过、产出不全）时，默认停还是自动重试可自定义**

> **全部都可配，包括不问，但不问属于小众玩法，比如测试 AI 模型质量**

## 两条可配置维度

### 1. 岗位组合（roster）

用户为一次工作选择启用哪些岗位。

| 场景 | 岗位组合 | 理由 |
|---|---|---|
| 改一个拼写 | `executor` | 不需要计划、不需要验收 |
| 常规开发 | `planner` + `executor` + `acceptor` | 有验收但不要红队 |
| 高风险变更 | 全套（+ `redteam` + `critic`） | 需要对抗性检查 |
| 测模型质量 | `executor` 单跑，**不问问题** | 就是要看模型的原始反应 |

**未启用的岗位，它负责的环节不执行。** 这是用户明确要的。

### 2. 阻塞处置（on-block）

岗位跑出阻塞结论时，默认行为可配：

```
stop      默认停，等人（保守）
retry:N   自动重试 N 次，仍失败才停
escalate  升级到上一级决策
```

**对应之前定的风险分级**：可逆操作可 retry，不可逆操作必须 stop。

## 一个必须保住的区分

「不问」和「问了但没问出来」是两件事：

```
不问（policy = skip）    用户显式选择跳过 —— 记录一条「本次未提问，原因：用户策略」
该问没问（ZERO_ASK）     策略要求问，但实际没问 —— 这是缺陷
```

**策略跳过不算缺陷，静默跳过算。**

判据仍然是 `question-protocol.md` §5.2 的 `no_open_questions_why`：**允许不问，但必须逐条说明为什么。**

## 为什么「全部可配」是对的

之前把「必须问」定成不可关闭，理由是「关掉就退化成又一个猜意图的 agent」。

**但那个理由不成立**：用户要的是**能力**，不是**强制**。

```
好的工具：默认安全，但允许关掉
坏的工具：不允许关
```

而且用户给出了一个真实用途：**测模型质量时必须不问**——否则测的是"AI 会不会问"，不是"AI 自己做得怎么样"。

## 代价（必须承认）

关掉环节后，出问题不能怪工具：

- 关掉 `acceptor` → 没人判交付物对不对
- 关掉提问 → AI 按自己的理解做，可能偏

**所以策略选择必须记录**，事后能回答"当时为什么没做这一步"。

对应已实现的 `no_open_questions_why` 和 `claim-ledger` 的 `declare` 记录。
