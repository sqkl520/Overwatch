# 方向约定：`intent.md` 的格式、取值与判定

> **⚠ 裁决（2026-10-30）**：本方案**不作为核心机制**。主线程会同设计与红队复核后判定：
> 边际贡献仅 **2.7pp**，且字符重合度这个度量与「方向是否改变」原理上正交。
> 本文件保留为**设计存档**，可采纳的部分见 [`verdict-intent-contract.md`](verdict-intent-contract.md) §5.2。
> **不要按本文直接实施。**

> 状态：**Proposed**（未实现，未提交用户批准）
> 依据标注：`[S§x]` = [`docs/research/2026-10-30-stop-signals.md`](../research/2026-10-30-stop-signals.md)；
> `[M]` = 本文作者 2026-10-30 在本机语料上的独立复算（判据与抽样口径完整写在本文件 §9，可据此重实现）；
> `[设计选择]` = 无数据支撑的取舍。
>
> **术语**：本文的「代决策」沿用 `hosted-mode.md` 的定义——不是 OmniSight 自己执行命令，
> 而是**允许目标会话执行的下一步**。所以约定的粒度必须是**命令能力类**，不是「这件事我觉得没问题」。

## 0. 结论先行（先说坏消息）

1. **「与用户确认方向」不能把 84% 的不可推样本变成多数。** 我在 84% 的不可推样本里抽了 120 条人工标注：
   **48.3% 是程序性放行、10.8% 是流程指令**（这两类是约定能碰的），
   **14.2% 是外部事实**（报错、日志、真机反馈、凭据），**5.0% 是新范围**，**5.0% 是用户反问**，
   **16.7% 是新的偏好/选型**（约定写得够细才可能覆盖，写不细就是白写）。
   但「能碰」不等于「能代」——见第 3 条。`[M]`
2. **真正被约好就能消掉的那部分，大部分已经被「会话内已有的规则」覆盖了。**
   把 33 条可被闸门放行的样本按授权来源三分类：**25 条（76%）依据在本会话前文**、
   **4 条（12%）依据在同项目的更早会话**（扫 transcript 就能拿到，不必写文件）、
   **4 条（12%）全项目从未说过**——这才是 `intent.md` 独有的份额。`[M]`
3. **所以本机制的正确位置是「减少重复确认」，不是「让 AI 更敢替你决策」。**
   - **分类器读前文 + 能力闸门**（不含 `intent.md`）：可安全代答从 8.8% 抬到约 **25–38%**（点估计 31%）。
   - **再加上 `intent.md`**：只多 **≈2.7pp**（4/120 的"全项目从未说过"份额）。
   - **叠加「上一轮只读」的保守配置**：从 2.8% 到 **9–10%**。
   区间宽是因为 120 例里落到闸门内的只有 47 条（Wilson 20.3–36.1%），不是拍的。`[M]`
4. **但它有一个 baseline 具备不了的收益：把「隐性规则」变成可审计对象。**
   实测同一批项目里，同类规则被用户反复陈述：40 组「项目×规则」共 677 次陈述，
   其中首次只有 40 次，**其余 637 次是复述（冗余系数 16.9）**。`[M]`
   跨会话复述（换一个会话就要再说一遍）101 次，占全部真人消息的 **7.2%**；
   同会话内复述 141 次，占 **10.1%**。前者是本机制能直接省掉的，后者省不掉（那是上下文丢失）。`[M]`

## 1. 先修正分母：哪些「推不出」是「没明说」

### 1.1 方法

按 `[S§9.1]` 的口径重建样本：对每个 `end_turn` 停止点找下一句真人回复（排除 §9.3 列出的六类系统注入），
算回复与 (A) 紧邻上一条真人消息、(B) 更早全部真人消息的字符二元组 Jaccard 重合度。
阈值取 0.30（与 `[S§9.2]` 的严格口径同量级）。`[M]`

| 口径 | 样本 | 可推（max(A,B) ≥ 0.30） |
|---|---|---|
| 全部停止→真人 | 965 | **170（17.6%）** |
| 去掉「会话续写摘要 / 工具回显 / `<system_warning>` 复读」 | 965 | **85（8.8%）** |
| 上述再叠加「上一轮只读」 | 965 | **27（2.8%）** |

> **为什么必须去掉续写摘要**：可推样本里 **50%（85/170）** 是
> `This session is being continued from a previous conversation…`、`<system_warning>` 回显、
> 或整段贴回工具输出。它们与上文的 Jaccard 高，是因为**就是上文**。
> `[S§9.2]` 的 15.9% 包含了这批噪声；含噪声时本文复算为 **17.6%**，去掉后是 **8.8%**
> （`[S§9.2]` 用 945 对样本得 15.9%/9.0%，本文用 965 对得 17.6%/8.8%，差异来自样本边界，结论一致）。
> 两者都保留，下文用「artifact-free」作为保守值。

### 1.2 对 120 条不可推样本的人工标注

从 776 条 `max(A,B) < 0.30` 的样本里，按固定种子抽 120 条，逐条读「AI 的末段提问（ASK）+ 用户回复（REPLY）」，
按**「若有一份理想的方向约定，这条能否被推出」**分 6 类：`[M]`

| 类 | 定义 | n | 占比 | 95% CI | 约定能消掉吗 |
|---|---|---|---|---|---|
| **P** | 程序性放行：继续既有计划、重跑测试、改文档、查状态 | 58 | 48.3% | 39.6–57.2% | **能**（约 29 条落在闸门内，见 §5） |
| **S** | 需要偏好/选型：版本号策略、要不要删老包、目录怎么排 | 20 | 16.7% | 11.1–24.3% | **部分**（约定必须写到具体，否则是自欺） |
| **N** | 新外部事实：报错、真机反馈、截图、凭据、线上现象 | 17 | 14.2% | 9.0–21.5% | **不能**（原理不可推） |
| **M** | 流程指令：多 agent、锐评、验收、重开一轮 | 13 | 10.8% | 6.4–17.7% | **能**（但多数已被会话前文授权） |
| **ID** | 新范围/新任务：再做个 GUI、重新设计前端 | 6 | 5.0% | 2.3–10.5% | **不能** |
| **Q** | 用户反问：这是什么、在哪、为什么 | 6 | 5.0% | 2.3–10.5% | **不能** |

**「约定能消掉」的上界 = P + M = 71/120 = 59%**，但这是上界，原因见 §1.3 与 §5：
其中相当一部分提问里已经带着**具体的、会改变持久状态的动作**（"提交并发布 1.2.1"、"删除老版本"），
即使程序性放行，也要按 `hosted-mode.md` 的 L0–L5 分级逐个判。

### 1.3 关键修正：「能被解释」≠「能被安全代答」

对 P 组 58 条的 ASK 做动词分析：**42 条（72%）** 的提问里含有会改变持久状态的动作
（push / 发布 / 删除 / 提交 / 安装 / 部署）；M 组 13 条中 **13 条（100%）** 含有（它们本身就是派发动作）。`[M]`

所以必须再叠一个**能力闸门**：提问涉及的每个动作，都必须在约定里被显式放行。
这个闸门的实测覆盖率（同一批 120 条，按「提问提到的高风险动词集合 ⊆ 允许集合」计）：`[M]`

| 允许集合 | 覆盖 |
|---|---|
| 什么都不放行（只放行"无动词"的提问） | 41/120 = 34.2% |
| + `commit` | 60/120 = 50.0% |
| + `release` | 77/120 = 64.2% |
| + `push` | 82/120 = 68.3% |
| + `delete`（项目内清理） | 91/120 = 75.8% |
| + `install` / `deploy` | 102/120 = 85.0% |

**这是整份设计里最容易被忽略的一点**：约定写得越宽，"能代答"的比例越高，但放行的动作也越危险。
所以约定必须有**下限不可让**的禁区（§2.4），且禁区不能被 `intent.md` 覆盖。

### 1.4 三条必须承认的边界

- **外部反馈（N）不可推。** 17 条里 13 条是「我测了一下 / 还是没修好 / 日志在这里 / 这是 token」。
  这类回复携带的是**世界的新状态**，任何记忆都无法生成。`[S§9.4]` 的结论在人工标注下复现。
- **改主意（REVERSAL）占比不高，但检测不到。** 带明确撤销语义的回复 6/120 = **5.0%**（95% CI 2.3–10.5%）。
  其中 2 条是「删掉 / 以后也不要再加」这类**对约定的修订**，4 条是对新事实的反应。
  全语料层面：显式「撤回前一条规则」的措辞（"之前说的不算 / 以这次为准 / 改主意"）**0 例**；
  但规则的反向措辞（"推吧 / 可以删了"）出现 11 次，而**没有一次**发生在同会话内一条显式禁止之后。
  结论：**用户不会撤销，他会直接下相反的指令。** 所以 §3.4(d) 的"反向证据"检测是必需的，
  按关键词找"撤销"是没用的。`[M]`
- **「按你的判断」几乎不出现。** 短句里"按你的判断/你看着办/都行/随你"只有 **11/1398 = 0.8%**。`[M]`
  这条重要：**用户不是"懒得决定"，而是"没被问到"**。所以本设计的重心是「问对问题」，不是「猜对答案」。

## 2. `intent.md` 的格式

### 2.1 三个硬要求与它们的冲突

| 要求 | 冲突 | 取舍 |
|---|---|---|
| 人 5 分钟能填 | 机器要精确 | **正文是 markdown 表格 + 固定章节**，不做 YAML（YAML 的缩进错误会让整份文件不可解析，而"文件坏了"必须 fail-closed，代价是全部动作关闭） |
| 机器能精确引用 | 自然语言歧义 | **每个可放行的动作必须落到一张受控词表**（§2.3 的 `capability` id），自由文本只允许出现在 `note` 列，**解析器不读 note** |
| 可增量更新 | 历史不可丢 | **版本化追加**：只加行、不删行；撤销用 `superseded_by` 指向新行。谁、何时、依据哪句话 → 记在 `evidence` 列 |

### 2.2 文件位置与加载顺序

```
<repo>/intent.md                                  # 项目级，可发布；模板 templates/intent.example.md
%LOCALAPPDATA%/Overwatch/intent-<projectHash>.md  # 机器级覆盖，不发布
```

后者**逐行覆盖**前者（同 `id` 的行以后者为准）。加载规则与 `hosted-mode.md` §1.1 一致：
**解析失败 = 全部 `autonomy` 行失效 = 退化为 `observe`**，不"用默认值继续跑"。
`[设计选择]` 理由同该文：最危险的失败模式是"以为关着其实开着"，反过来同样成立。

### 2.3 受控词表：`capability`

词表只描述**动作类别**，不描述业务。每一个 id 都能被一条命令级规则判定（§3.2），
**不接受"按你的判断"作为 capability**。

| id | 涵盖的命令/工具 | 默认 |
|---|---|---|
| `read_only` | `git status/diff/log/show`、`ls`、`cat`、`grep`、`rg`、`Read`、`Grep`、`Glob` | **allow** |
| `doc_edit` | 项目内 `.md` 的 `Write`/`Edit` | ask |
| `code_edit` | 项目内非 `.md` 的 `Write`/`Edit` | ask |
| `test_run` | 白名单内的只读测试/构建命令（整条匹配） | ask |
| `agent_spawn` | `Agent`（派子 Agent） | ask |
| `tidy` | 项目内文件移动/归档/创建目录 | ask |
| `local_commit` | 非默认分支上的 `git add` / `git commit` | ask |
| `release` | `git tag`、`gh release create`、改版本号 | **deny** |
| `push` | `git push`（非 force） | **deny** |
| `delete_local` | 项目内 `rm`、清理附件目录 | **deny** |
| `install_deps` | `npm install` / `pip install` 等 | **deny** |
| `deploy` | 部署脚本、发布到服务器 | **deny** |
| `rewrite_history` | `--force`、`filter-branch`、强推 | **deny（不可配置）** |
| `credential` | 读 `.env`/`~/.ssh`、导出 token、改 IAM | **deny（不可配置）** |
| `outbound` | 邮件、PR 评论、`npm publish`、对外消息 | **deny（不可配置）** |
| `money` | 任何支付/订阅/额度购买 | **deny（不可配置）** |

**默认值即"什么都不开"**：文件不存在时，只有 `read_only` 放行，其余全 ask/deny。
这与 `hosted-mode.md` 的 fail-closed 一致，也保证「没填 = 没授权」。

### 2.4 禁区（`denywins`，不可被项目配置覆盖）

四条，理由与 `hosted-mode.md` §1.4 的 B1–B9 相同（不重复推导），这里只声明它们在 `intent.md` 里的表现：

1. `rewrite_history` / `credential` / `outbound` / `money` **永远不可设为 allow**，写在 `deny` 里也不行（解析器拒绝）。
2. **`intent.md` 里任何一行的 `evidence` 为空** → 该行非法。不允许无出处的授权。
3. **`expires` 缺失的行** → 视为 `expires: +90d`，到期自动降为 `ask`（§3.4）。
4. **「未分类」不是 allow**：匹配不到任何 capability 的命令一律 `ask`，不落 `read_only` 兜底。

## 3. 分类器怎么用

### 3.1 在判定流程的哪一步

插在 `hosted-mode.md` §2.2 的**第 4 步之后、第 5 步之前**，作为**第 4.5 步**：

```
 4.5 若 stop 的「建议动作集合」非空:
         caps = extractCapabilities(stop.proposedActions)      // §3.2，规则层
         若 caps 为空                              → 不干预（沿用 5–9 步）
         若 caps 里有任一 ∈ HARD_DENY             → CHOICE_HARD_DENY（不可代）
         若 caps ⊆ intent.allow(now, scope)        → CHOICE_PREAUTHORIZED（可代，高优先级）
         若 caps ∩ intent.deny(now) ≠ ∅           → CHOICE_FORBIDDEN（不可代，且提示"这违反你自己的约定"）
         否则                                      → 沿用 5–9 步（未分类，保守）
```

**为什么在这**：它是第一个**不需要猜语义、只需要查表**的步骤，但它的输入依赖第 0–4 步已经
确定了「这是一个人会回话的停止点」——在 `CHILD_PENDING` / `ACTIVE` 上查约定没有意义（那里根本不该动）。

### 3.2 规则层实现（零依赖，纯规则）

`extractCapabilities()` 只看**停止点那一轮 AI 自己提出的动作**，不看 AI 的自然语言总结：

| 输入 | 来源 | 用途 |
|---|---|---|
| 上一轮 `tool_use` 的 `name` + `input.command` | transcript | 已经做了什么（用于判定是否只读） |
| 最后一条 `assistant` 文本里**引号或代码块内的命令** | transcript | AI 建议的下一步（`\`git push\`` 这种） |
| `jobs/*/state.json` 的 `suggestedReply` | 宿主 | 宿主已给的半成品回复 |

匹配方式：**命令整条匹配白名单**，与 `hosted-mode.md` §1.2 的 `actions` 表同一套正则，不做前缀匹配。
文本里没有可识别的命令时，`caps = []` → 不干预。**这是有意的保守**：宁可少代，不可错代。

**必须写进代码注释的一条**：`extractCapabilities` 是**规则层**，它不知道「这个删除是不是安全」。
它只知道「这是 `delete_local`」。语义判断留给 `intent.md` 的 `scope` 列——那是人写的。

### 3.3 AI 层在哪（明确标出）

以下三件事**放弃用规则做**，标为 AI 层，且只在 `hybrid` 产出形态下允许：

| 事项 | 层 | 失败时的行为 |
|---|---|---|
| 从首次对话里**起草** `intent.md` 的候选行 | AI 层（生成本身不参与判定） | 生成失败 → 留给用户手填，不影响判定 |
| 判断「用户的这句话是不是在撤销某行」 | AI 层（**只产建议**，不自动改文件） | 不生效；变更必须由用户确认后写盘 |
| 解释 `note` 列的自然语言 | **不做**。解析器不读 note | — |

判定本身**永远是规则层**：`allow` / `deny` 是查表，不是让模型理解。

### 3.4 四个边界情形

**（a）查不到（没约定过）怎么办**
`intent.md` 不存在 → `allow` 集合只有 `read_only`。这不是"降级"，是**定义**：
没约定过 = 只有只读是默认安全的。与 `hosted-mode.md` 的 L0 默认一致。

**（b）粒度太粗（「按你的判断」）怎么办**
`capability` 是受控词表，**"按你的判断"不是合法值**，解析器直接拒绝该行（记 `invalid_intent_line`，T3 告警）。
这挡住了最常见的一种自欺：把「我不知道该放什么」写成「都行」。
实测支撑：用户真正说「按你的判断/都行/随你」的只有 **0.8%** 的短消息 `[M]`，
所以"粒度粗"主要不是用户的问题，是**模板给了坏榜样**。模板里每一行都有 `scope`（要么是路径 glob，
要么是 `branch:!main` 这类可判定的表达式，要么是 `*`），**但不允许写"按你的判断"**。

**（c）约定过期**
每行有 `expires`（缺省 +90d）。到期行为：
- `allow` 行 → 降为 `ask`（不是 deny：到期意味着"需要重新确认"，不是"现在禁止"）
- `deny` 行 → **保持 deny**（拒绝是安全方向，过期不会变危险）
- 到期前 7 天在 T0 摘要里提一次，不单独发 T2/T3
实测依据：同一项目内，规则陈述到该项目最后一次活动的中位间隔 **18.1 天**，p90 22 天，最长 48 天 `[M]`。
所以 **90 天足够宽**，宽到"三个月前的约定还适用吗"这个问题在实际语料里不会发生；
真正发生的是「项目 20 天就结束，约定还没到期，但项目换了方向」——这个 `expires` 挡不住，
只能靠 §4 的「阶段」节 + §3.4(d)。

**（d）方向变了但约定没变**
三条检测，全部是规则层：
1. **阶段跃迁**：`intent.md` 的 `current` 字段与最近 3 条 AI 消息里出现的 `Phase N` / `Wave N` 不一致 → T1 提示"约定可能过期"。
2. **否决累积**：同一 capability 在 7 天内被用户拒绝 ≥2 次 → 该 capability 自动降为 `ask`，并在下次交互时要求确认。
3. **反向证据**：用户说出与 `已定选型` 的结论矛盾的动词（如 T3 写"不用 SQLite"而用户说"上 SQLite"）→ **只提示，不改文件**。

### 3.5 与 `hosted-mode.md` 分级的关系（不重复定义）

`intent.md` **不放宽 L0–L5 的语义边界**，只做两件事：
- **把 L2–L4 的 `enabled` 从"全局开关"细化到"每个 capability 每行"**；
- **给 L5 的 `allowHighRisk` 提供逐项授权**（`push` / `release` 各自一行，而不是一个布尔）。

硬边界 B1–B9 一律优先于本文件。写法上：`denywins` 与 `boundaries.denyClasses` 是同一份清单的两个视图，
**`check-structure.mjs` 应校验两者一致**（§8 的待办）。

## 4. 首次对话流程

### 4.1 现状与问题

`oversight/SKILL.md` §1 的 Q1–Q5 只问**监控参数**（范围、触发、口吻、禁止操作、输出风格），
产出的是一份会话内偏好，**不落盘、不跨会话、不含项目走向**。

### 4.2 按「信息价值」排序的提问（不是按好问排序）

价值 = （能消掉的不可推样本数）×（该问题的答案能稳定多久）。第二项用实测的规则存活期中位数估。`[M]`

| # | 问题 | 为什么排这个位置 | 默认值 | 跳过时 |
|---|---|---|---|---|
| **Q0** | 「这个项目**做完**长什么样？给我一句话」 | 唯一能生成 `阶段` 节 `完成定义` 的输入。没了它，后续所有"该不该继续"都无法判 | 从 `README.md` / `CLAUDE.md` 首段自动起草，让用户改 | 标 `phase.definition: unknown`，**所有阶段相关判定退化为 ask** |
| **Q1** | 「哪些事**以后别问我**？」（给 6 个候选，勾选） | 直接产出 `放行` 行。实测**闸门命中的 47 条全部**落在 `doc_edit`/`test_run`/`agent_spawn`/`tidy`/`status_check`/`continue_plan`/`local_commit` 这 7 类里，没有第 8 类 `[M]` | 只勾 `doc_edit`+`test_run`+`agent_spawn`，`tidy` 不勾 | 全不勾 = 只有 `read_only` |
| **Q2** | 「哪些事**必须问我**？」（给 8 个候选，**全选**） | 产出 `必须问` 行。默认全选是刻意的：**拒绝比放行便宜** | 8 项全选 | 保持全选 |
| **Q3** | 「已经定了哪些技术选型？为什么？」 | 产出 `已定选型` 行；也是**唯一能挡住"AI 重新论证已否掉的方案"**的字段 | 空 | 空表 = 该字段不参与判定 |
| **Q4** | 「现在到哪一步了？下一步算什么完成？」 | 产出 `阶段` 行；用于 §3.4(d) 的过期检测 | 从最近会话的 `Phase/Wave` 标记起草 | `current: unknown` |
| **Q5** | 「有没有**一句话能概括你口味**的规则？」（例：别一次改太多文件） | 只进 `人工约定`，**不参与判定**。放在最后，因为它最容易写成不可判定的东西 | 空 | 跳过 |

**Q3 与 Q5 的顺序是有意的**：Q3 要求"为什么"，能挡住事后编造理由；Q5 允许模糊，因为**它本来就不进判定**。
把模糊的东西隔离在一个不参与判定的区块里，比强迫用户把模糊写成精确更现实。

### 4.3 产出物与可见性

| 产出 | 位置 | 可发布 | 谁读 |
|---|---|---|---|
| `intent.md` | `<repo>/intent.md` | **是**（模板 `templates/intent.example.md`） | 用户、目标会话的 AI（作为项目上下文）、分类器 |
| 起草记录（哪句话生成了哪行） | `tasks/runs/<run-id>/intent-draft.md` | 否 | 主线程、审计 |
| 解析结果（allow/deny 快照 + 时间戳） | `%LOCALAPPDATA%/Overwatch/state.json` 的 `intentSnapshot` | 否 | 分类器 |

**必须是可发布文件**：它写的是项目方向，不含会话 ID 和本机路径。
`check-structure.mjs` 的盘符检查会自动覆盖它（`intent.md` 在仓库根，属 `PUBLISHED_FILES` 之外——
**需要新增一条规则**，见 §8）。

### 4.4 5 分钟怎么保证

实测：真人首条消息长度中位 **111 字符**，p90 378 字符 `[M]`——用户**本来就会**写这么长。
所以 5 分钟不是靠简化问题，而是靠：
1. **每题给一个"照抄也行"的默认**（上表的默认列）；
2. **Q1/Q2 用勾选不用填空**（6 + 8 个候选，来自实测的高频 capability `[M]`）；
3. **允许"以后再答"**：跳过的题在 `intent.md` 里写成 `unknown`，而不是不写——
   `unknown` 与"没这行"在判定上等价，但在**提示用户补全**上不等价。

## 5. 能带来多少提升（诚实评估）

### 5.1 口径

全部在「120 条不可推样本」上算，再按 776/945 = 82.1% 的占比折算到全部「停止→真人」对。`[M]`
（抽样时阈值取 `max(A,B) < 0.30`，与 `[S§9.2]` 同口径；抽样后复核：**120 条里有 99 条**的
`max(A,B) < 0.15`，21 条落在 0.15–0.30 的灰区。只用 99 条重算，分母 120 换成 98 个去重样本，
结论从 27.5% 变 29.6%、8.3% 变 9.2%——**不改变结论**，下文一律用全量 120。）`[M]`

「闸门」定义（E2，最宽的一档）：提问提到的动作 ⊆ `{doc_edit, test_run, agent_spawn, tidy, status_check, continue_plan, local_commit}`，
且不含 `push/release/delete/deploy/install/rewrite/credential`。

| 指标 | 值 | 95% CI |
|---|---|---|
| 闸门触发（"这事约好了"） | 47/120 = **39.2%** | — |
| 触发且用户确实放行 | 33/120 = **27.5%** | 20.3–36.1% |
| 闸门精度（触发时用户放行的比例） | **70.2%** | 56.0–81.3% |
| 触发且用户放行且上一轮只读 | 10/120 = **8.3%** | — |
| 后者精度 | **83.3%** | 55.2–95.3% |

### 5.2 折算

| 口径 | 现在 | 分类器读前文+闸门 | 再叠加 `intent.md` | 增量（含文件） |
|---|---|---|---|---|
| 宽松（含重述/续写噪声） | 17.6% | 17.6% + 22.6pp ≈ **40%** | ≈ 42% | +2pp |
| **artifact-free（保守）** | **8.8%** | 8.8% + 22.6pp ≈ **31%** | ≈ 34% | +3pp |
| artifact-free + 只读上一轮 | 2.8% | 2.8% + 6.8pp ≈ **9.6%** | ≈ 11.6% | +2pp |

**两种读法，都要写清楚：**

- **只上 `intent.md`，不改分类器**：提升 **≈ 0**。文件没人查，等于没写。
- **上「读前文 + 能力闸门」**（不含文件）：从 8.8% 到 **25–38%**（Wilson 折算）。
- **文件本身的边际**：**+2.7pp**（C 组 4/120），叠加后约 **11–12%（保守口径）**。

**区间估计：8.8% → 11–12%（点估计）是"文件"的贡献；8.8% → 25–38% 是"整个机制"的贡献。**
把两者混在一起报，就是夸大。

### 5.3 但这个增量里有多少是"约定"独有的

这是本文最重要的一张表。对 33 条「闸门+放行」逐条查：**授权依据是否在本会话（同一 transcript）里已经出现过**。

| 需要什么 | n | 占 33 | read-only 子集 |
|---|---|---|---|
| A：本会话前文已说过（不需要 contract，只需分类器读前文） | 25 | **76%** | 6 |
| B：只能由同项目更早的会话授权（扫 transcript 即可，不必写文件） | 4 | **12%** | 1 |
| C：全项目从未说过（**只有 `intent.md` 能提供**） | 4 | **12%** | 3 |

C 组的全部 4 条原文（去重后 2 条）：
`「不需要考虑网络问题，替补的那些都重新全量跑一遍…然后就开始修 P0」`、`「提交并发布 x.y.z」`。

**契约的边际贡献 = C 组 = 4/120 = 3.3%，折算到全部对约 2.7pp，且落在只读上一轮的只有 3 条 ≈ 2.0pp。**
换言之：`intent.md` 把可安全代答从 8.8% 抬到 **11–12%**（含 A+B 的"读前文"能力则是 31%）。
其余 20pp 的增量来自**「分类器开始读 AI 自己提出的动作」这个改动本身**，与文件格式无关。

> 这就是 §0 结论 3 的来源：**这个机制卖的是"少问一遍"，不是"更敢替你决定"。**
> 如果只做 `intent.md` 而不改分类器的步骤 4.5，收益接近零。

### 5.4 不为迎合而夸大的三条

1. **不要把它包装成"记住偏好就能替你决策"。** 84% 的不可推样本里，闸门放行的只有 27.5%，
   其中**只有 4/120 = 3.3% 是"全项目从未说过"、必须靠约定才有**。把它当卖点会立刻被数据打穿。
2. **N 类（14.2%）与 ID 类（5.0%）原理不可消。** 任何"提升可代答比例"的方案都必须先减掉这 19%。
3. **70% 的精度对"代发命令"是不够的。** 30% 的触发会是误判，而误判的代价不是"多问一次"，
   是"代发了一条用户不想执行的命令"。所以实际可用配置应叠加「上一轮只读」，把精度抬到 83%，
   代价是增量从 +23pp 降到 +7pp。**这是真实的取舍，不是保守。**

## 9. 复算方法（可重实现）

分析脚本是一次性脚本，**没有进仓库**（含本机路径，按 `CLAUDE.md` 分区规则不进可发布区）。
下面给出全部判据，读者可自行重实现；数字会随语料增长小幅漂移，比例稳定。

**S1 建样本（965 对）**
1. 遍历 `~/.claude/projects/*/*.jsonl`（排除 `subagents/`）。
2. 「真人消息」= `type === "user"` **且** `typeof message.content === "string"` **且** `!isMeta`
   **且** `origin.kind` 为空或 `"human"` **且** 正文不以
   `<task-notification|local-command-caveat|system-reminder|ide_opened_file|cross-session|command-name|command-message|local-command-stdout` 开头。
3. 「停止点」= `type === "assistant"` 且 `message.stop_reason === "end_turn"`。
4. 取停止点之后**第一条真人消息**，且两者之间没有别的 `assistant` 记录。
5. 相似度 = 去空白后的**字符二元组多重集 Jaccard**。A = 紧邻的上一条真人消息；B = 之前全部真人消息（逐条取最大）。
   可推 := `max(A,B) ≥ 0.30`。

**S2 去噪声**：命中 `This session is being continued|以下为手机上的上下文|<system_warning>|DSML`
或长度 > 5000 字符的回复，判为 artifact 并从可推集合剔除（170 → 85）。

**S3 人工标注**：对 `max(A,B) < 0.30` 的样本按固定种子抽样 120 条，逐条读「AI 末段提问 + 用户回复」，按 §1.2 的六类定义打标。
标注规则（写下来是为了可复核）：
- 回复里给出**可执行的动作/放行既有计划**且不引入新事实 → `P`
- 回复在多个已提出的选项里**挑一个**，或给出偏好/选型 → `S`
- 回复**引入 AI 不可能知道的外部状态**（报错、日志、真机现象、凭据、线上事件）→ `N`
- 回复是**对协作方式的指令**（派几个 agent、锐评、验收、重跑一轮）→ `M`
- 回复**开启一件新事**（新功能、新仓库、新目录结构）→ `ID`
- 回复是**提问**（是什么/在哪/为什么）→ `Q`

**S4 能力闸门**：对每条样本的 ASK 做 capability 抽取（用 §2.3 的受控词表 + §3.2 的命令正则），
`caps` 中不含 `push/release/delete/deploy/install/rewrite_history/credential` 且至少命中一个
`doc_edit/test_run/agent_spawn/tidy/status_check/continue_plan/local_commit` → 判「落在闸门内」。

**S5 授权来源三分**：对闸门内且用户放行的样本，按该 capability 的前提规则（如 `agent_spawn` 需
「多 agent / 锐评 / 红队」语句）分别在本会话前文、同项目更早会话中查找；两处都没有 → C 组。
