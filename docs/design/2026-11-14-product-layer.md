## 一、陌生人从看到 repo 到获得价值：路径与断点

### 1.1 今天的路径（逐跳，每跳都是实测或可读到的原文）

```
① 看到 README
     ↓  写的是「30 秒上手」，第一条命令是 git clone + cd + node scripts/scan-sessions.mjs --days 3
② clone 到自己机器上的任意目录
     ↓  能跑，但产出是关于「这台机器上所有会话」的一张表
③ 第一屏
     ↓  40+ 秒无输出（E1），然后一张带 novelty / hb / depth 的表
④ 想把它用在自己的项目上
     ↓  ✗ 断点：没有任何一条命令、任何一段文档说明「怎么让它作用于我的项目」
⑤ 想要「一次给完需求就做完，问题问准，每轮先列 plan」
     ↓  ✗ 断点：那两层文档在 docs/spec 与 docs/design 里，代码零行，且没有载体
```

### 1.2 断点清单，以及每个断点是工程量还是产品定义

| # | 断点 | 证据 | 类型 | 为什么是这一类 |
|---|---|---|---|---|
| B1 | **README 的「30 秒」实际是 40 秒空白** | E1 | **工程量** | 缺的是 `--fast`（只读 env + sessions，135 ms，见 E1 的分解）与一个进度块。判据明确，不需要新决定 |
| B2 | **所有命令绑死 cwd = 仓库根** | E2；`check-structure.mjs:16` 用 `process.cwd()` 当 ROOT；`SKILL.md` 里 11 处裸 `node scripts/…` | **工程量** | 改成按脚本自身位置解析即可。没有取舍 |
| B3 | **`--help` 不存在、未知参数静默吞** | E3 / E4 | **工程量** | 加一个 usage 分支 + 未知参数报错 |
| B4 | **新机器第一屏是 exit 2 的错误** | E5 | **工程量**（判定）+ **产品定义**（文案） | 「没有语料」该说什么，是决定；检测本身不是 |
| B5 | **TUI 首屏要求先装守护进程** | E8，配合 E9 | **产品定义** | 「首次使用该不该先起常驻进程」是取向问题，不是能力问题 |
| B6 | **退出码语义不统一**（scan 0/1/2、health 1、inbox 恒 0、claims 默认 1） | E7 / E10 / E11 | **产品定义** | 「UNKNOWN 算不算通过」这个三值问题在 `verify-claims` 里已回答（不算），但入口层没有继承 |
| B7 | **`CLAUDE_CONFIG_DIR` 一半认一半不认** | E12 | **工程量** | 一致性 bug |
| B8 | **`.claude/agents` + `skills/oversight` 到不了用户的项目** | 全仓检索：没有任何脚本、任何文档描述「安装到别的项目」；`SKILL.md` 的 11 条命令还要求 cwd 是本仓 | **产品定义** | 见 §1.3 |
| B9 | **问问题 / 列 plan 那一层零行实现** | `docs/spec/2026-11-11-question-protocol.md` 标题写着「零行实现」 | 工程量（巨大） | 但它是 B8 的下游：载体不成立，做出来也送不到 |

### 1.3 结论：缺的是产品定义，而且那个决定**已经被做出过一次**，只是没人拿它对照新目标

断点里 5 条是工程量、3 条是产品定义，另有 1 条（B4）两者兼有——
「新机器第一屏是错误」的检测是代码问题，但它该说什么话是决定问题。
**B8 是闸门**：B9 的所有工程量都堆在它后面。

缺的那个决定，一句话：

> **这个产品是「你打开这个仓库来用它」，还是「它装进你自己的项目」？**

这个决定不是空的——2026-10-29 的 ADR 已经选了前者。分叉点就在这一句（`docs/adr/0001-config-only.md`
「未采纳的替代方案」表最后一行，逐字）：

> **plugin 形态**（`.claude-plugin/plugin.json`）| 可安装、可真源即发布物，但插件布局要求 agents
> 在仓库根目录，打开这个仓库时**不会**自动加载 `.claude/agents/`。取舍：`clone 即用` 优先于 `可安装`。

那个取舍在 2026-10-29 是对的：当时产品是「监控本机所有会话」，使用者就是作者，`clone 即用` 确实更省事。

**但 2026-11-14 的产品定义换了。** 用户原话是「给别人的、独立的仓库、长期项目、目标是一个完整框架」，
主题是「需求的传递」「问问题是这个项目的主题」「每轮开头列 plan」。
这三件事的载体恰好是 `.claude/agents/*` 与 `.claude/skills/oversight/SKILL.md`——
**而它们只在它们所在的那个项目里加载。**

于是今天的状态是：

```
产品说：这是给别人的框架，主题是问问题和列 plan
仓库说：你得先站在这个仓库里，才能用这套框架
物理事实：站在这个仓库里，它只能监控这台机器；走出这个仓库，agents 和 skill 都不加载
```

**这不是「还差一个 feature」，是「产品定义里有两句话互斥，而没人把它们放在同一段里读过」。**

ADR-0001 的「反悔信号」列了四条（宿主注入接口 / 10 个以上会话 / 四态误判 / 第二个宿主），
**没有一条是「产品要给别人用」**。所以这个决定从来没被复核。

### 1.4 如果 Y 不成立怎么改

我推荐的是「改成可安装」（§二、§三）。它成立的前提只有一个，而且可证伪：

> **用户的 Claude Code 会加载从外部装进去的 agents 与 skill。**

E14/E15 只证明清单合法、目录能注册，**没有证明加载**（§0.2 第 1 条）。
所以 M2 是一次**一小时内能做完的探针**，不是论证。若它证否：

- 退到「copy 安装」：一条 `init` 把 `.claude/agents/*` 与 `skills/oversight/` 复制进目标项目。
  代价是升级要重新复制、会与用户自己的 agents 混在一个目录——ADR-0001 那句「clone 即用 优先于 可安装」
  就仍然成立，本文的 §三 阶段顺序不变，只是 M3 的实现方式换掉。
- **不再退到「要求用户 clone 本仓」。** 那条路已被 2026-11-14 的产品目标否掉；
  如果两条都不成立，正确的动作是重新谈产品形态，不是加代码。

## 二、那一层长什么样（假定按推荐路线走）

### 2.1 入口叫什么

**一个脚本，一个名字，子命令对应已有脚本：**

```
node scripts/overwatch.mjs [doctor | scan | claims | asked | inbox | tui | hooks | init]
```

- 不叫 `npx overwatch`：那要求发布 npm 包 + 用户联网 + 维护版本（§四 会讲为什么这是陷阱）。
- 不叫 `claude`：那是宿主。
- **只有一个入口文件，它不是重写，是路由。** 每个子命令 `import()` 现有的脚本函数（本仓脚本
  已经按「可直接执行 / 可被 import」写好了：`scan-sessions.mjs` 有 `isDirect` 守卫，
  `watch.mjs`、`verify-claims.mjs` 导出面完整），传绝对路径，不改它们的逻辑。
- 无参数 = `doctor` + `claims --days 1` + 下一步提示（见 §2.4）。**默认不跑全量 scan**，
  因为它是 40 秒（E1），而首屏不能等 40 秒。

这个入口解决 B1–B4、B7：解析自身目录（不依赖 cwd）、认 `--help`、未知参数报错并打印 usage、
统一 `CLAUDE_CONFIG_DIR`、统一退出码。

### 2.2 它怎么知道该做什么

| 判断 | 读什么（只读） | 默认 | 判不出来时 |
|---|---|---|---|
| 有没有宿主 | `$CLAUDE_CONFIG_DIR` 或 `<home>/.claude` 是否存在 | — | 说「这台机器上还没有 Claude Code 的痕迹」，给一句「先在一个项目里跑一次会话再来」 |
| 有没有语料 | `<claude>/projects` 下 `*.jsonl` 的计数与总字节 | — | 「0 份 transcript」不是「一切正常」 |
| 有多少会话 | `<claude>/sessions/*.json` ≤14 条、`<claude>/jobs/*/state.json` | — | 分别报，不合并（三个源本来就不一致，见 `scan-sessions.mjs` 的头注释） |
| 通知能不能发 | `notify.mjs` 的 `isNotificationAvailable()` | — | 报「不可用」并说明退回 `--inbox` |
| 项目怎么跑测试 | `project-commands.mjs` 的 `detectProjectCommands(目标仓库根)` | `unknown` | 明说认不出，并列出它找过的标志文件（E13 就是本仓库的实测：认不出） |
| 窗口 | 默认 1 天（首屏要快）；`--days N` 覆盖 | 1 | — |
| 是否装守护 | `install-watcher.mjs` 的 `status` 只读部分 | 不装 | 「可选，不影响任何结论」——这是刻意的措辞，见 §四.2 |

**成本约束（这是设计，不是口号）**：`doctor` 只允许 stat/readdir，禁止读任何 `.jsonl` 内容。
本机实测这条路径 **135 ms**（86 个目录 / 436 份文件 / 2.22 GB 只数 size）；sessions + jobs **0.8 ms**。
**所以 `doctor` 一秒内出；带 `claims --days 1` 的完整首屏是 2.6 s**（实测：`verify-claims --days 1`
自身 2.45 s）。两者是两档，不许混为一谈——§2.4 那张样例的第二行时间就是这两个数相加。

### 2.3 怎么不破坏零依赖

1. **不加 `package.json` 也能有个「入口」**——一个 `.mjs` 就是入口。`node scripts/overwatch.mjs`
   与今天的命令同形，不引入包管理器。
2. **不用构建**：直接跑源码。宽度表那种生成物已经入库（`scripts/data/` + `width-table.mjs`），
   不新增生成步骤。
3. **不进 npm**：见 §四.3。
4. **如果走插件路线（推荐）**，插件清单 `plugin.json` 是一个 JSON 文件，不是依赖声明；
   `claude plugin validate` 对它做静态检查（E14 实测通过），不需要 `node_modules`。

> **同一个窗口（1 天）、同一台机器、同一次实测**，所以段与段之间对得上；数值会漂，形态不会。
> 复跑：`node scripts/verify-claims.mjs --days 1`、`node scripts/scan-sessions.mjs --days 1`。

> 「值得看一眼」按 `(project, status)` 去重后再列，上限 3 行。本案的原始数据里 `NO_EVIDENCE 1`、
> `STALE_ONLY 1`，正好各一行；如果不去重，同一个项目里的多条断言会把这块撑成噪声——
> 这正是「一张表」退化成「没人看的表」的典型方式，所以去重规则写进契约而不是留给实现者决定。

三个刻意的写法：

- **PLAN 在最前，且带每步耗时。** 用户要求「每轮对话最开始列一个 plan，让用户安心」。
  CLI 首屏是这个要求最便宜的验证场：形状对了，再搬进会话里。反过来如果 CLI 都排不出
  「已知 → 未知 → 下一步」，搬进会话也只会是一段漂亮话。
- **不打印「✓ 一切正常」。** 每一行都是「读到了什么」，不是「好不好」。这是本仓
  `docs/GUIDE.md` 一贯的写法（`[EXPLORING]` 不是「活着」），入口层不能退化成红绿灯。
- **`UNKNOWN` 不进「值得看一眼」，也不被算作通过。** 它单独计数并打印。三值语义从
  `verify-claims.mjs` 的 `EVIDENCE_STATUS` 原样继承，不新发明。

### 2.5 怎么与现有 39 个脚本共存

**并存，不重构。** 三条硬规矩：

1. `overwatch.mjs` **只做路由 + 首屏**，不含任何判定逻辑。它判定的每一件事都必须能从
   现有脚本的**导出函数**或 `--json` 输出里拿到；拿不到就不写进首屏（宁可少一行）。
2. **现有脚本的命令行契约一个字不改。** 别人的脚本、文档、CI 已经引用了它们；
   入口是加法。`check-structure.mjs` 的 `checkDocCommands()` 会继续守着文档里的既有命令。
3. **一份数据两个消费者**（本仓已有先例，`watch.mjs` 的 `--inbox` 与 `SKILL.md` 就是这么接的）：
   首屏与 `doctor` 共用同一个 `envReport()` 纯函数，`doctor --json` 直接输出它。
   `check-structure.mjs` 的 `checkInboxWiring()` 是同形的门，可以照抄思路加一条
   「首屏引用的每个字段在 JSON 里存在」的检查。

**唯一必须动现有脚本的地方**，是 B7（`CLAUDE_CONFIG_DIR`）：`scan-sessions.mjs` 的
`findTranscriptRoot()` / `readLiveSessions()` / `readJobs()` 都硬编码 `homedir()`，
而 `watch.mjs` 的 `claudeRoot()` 认这个变量（E12 实测差异）。修法是把三处改成
`watch.mjs` 已有的那个解析函数（复制 6 行，不跨模块 import——`scan-sessions.mjs` 现在只依赖
`job-event-time.mjs`，保持这个轻依赖是有价值的）。

## 三、分阶段：从今天到「别人能用」

四个阶段，有依赖关系，每个都能在一轮里做完。**每个阶段的验收都是机械可判定的。**

### M1 · `overwatch doctor`：让第一屏在一秒内说人话

- **交付**：`scripts/overwatch.mjs`（**只实现 `doctor` 与无参首屏，其余子命令直接打印
  「未实现」并给出等价的原生命令**）；一个测试文件；`docs/CAPABILITIES.md` 加一行；
  `docs/CHANGELOG.md` 加一条。**不改任何现有脚本**（B7 留到 M3）。
- **陌生人到这一步能做什么**：clone 之后第一条命令，1 秒内知道这台机器能不能用、
  缺什么、以及「下一条该跑什么」。
- **怎么验收**（全部可机械判定）：
  1. 三种环境下 exit 0 且无栈回溯：正常 home / 空 home / cwd 在仓库外。
  2. 空 home 时输出里**不出现任何 `✓`**，且至少给出一条可执行的修复命令。
  3. `--json` 与人类输出来自同一个 `envReport()`；有测试断言 `Object.keys()` 一致。
  4. 单测覆盖：未知子命令 → 非零退出 + usage；未知参数 → 非零退出；
     `doctor` 的 wall time < 1000 ms（用 `performance.now()` 断言，本机基线 135 ms）。
  5. `node scripts/check-structure.mjs` 与 `node --test scripts/*.test.mjs` 全绿。
- **什么时候停下重新评估**：如果 `doctor` 的任意一检查项在两台机器上给出**不同的 ✓/✗ 而无法解释**，
  说明判据不可移植——停下修判据，**不要加第五个检查项**。

### M2 · 载体探针：一小时内证否或证实「装得进去」

- **交付**：一份 `docs/research/` 报告（研究类，因为它是一次性实测），记录 plugin 与 copy
  两种方式在一个**临时 git 仓库**里的三项实测：skill 是否出现在会话里 / agent 是否能被主线程调用 /
  hook 是否触发。附一个临时探针（不入库）。
- **陌生人到这一步能做什么**：还不能做什么。**但这一步决定 M3 是「装插件」还是「复制文件」，
  错了会让 M3 整个白做。**
- **怎么验收**：
  1. 三项各有 T1（磁盘原文）或 T3（目标系统自己留了痕迹）级证据，不许 T0。
  2. 结论与 ADR-0001 的取舍节对照：若「可安装」成立，写一条 ADR 增补，**明确宣布
     「`clone 即用 优先于 可安装`」这条取舍作废**，并写清代价（自用形态怎么变）。
  3. 报告在 `docs/research/README.md` 登记（`checkResearchIndex()` 会拦）。
- **什么时候停下重新评估**：**三项里任一项为否，立即停。** 不要「再试一个办法」——
  那时要做的是回去改 §一.4 的路线，不是继续试。

### M3 · `overwatch init`：把那一层装进别人的项目

- **交付**：`init` 子命令。行为固定为：先打印 **PLAN**（要写哪些文件、写到哪、会不会冲突）→
  等确认（`--yes` 跳过）→ 写入 → 逐条回报。幂等；不覆盖已有同名文件；
  冲突时列出并发文件路径后退出非零；`--undo` 按安装清单反向删除。
- **陌生人到这一步能做什么**：在自己的项目里跑一条命令，开一个新会话，
  `/oversight` 可用、`oversight-*` 角色可被派发。**这是「问问题 / 列 plan」第一次真的到达他手里。**
- **怎么验收**：
  1. 空仓库连跑两次，第二次输出「无需改动」且文件树哈希不变（幂等）。
  2. 目标已有 `.claude/agents/oversight-executor.md` 时，拒绝写入并列出冲突路径，exit 非零。
  3. 安装后按 M2 选定的信号可机械判定（插件：组件清单可见；copy：文件逐个比对哈希）。
  4. `--undo` 后目录树与安装前逐文件一致（测试里用临时目录做快照比对）。
  5. **不改 `SKILL.md` 的既有 11 条命令**；若为迁就 cwd 必须改，则同时改
     `checkInboxWiring()` 对应的门——不许只改文档。
- **什么时候停下重新评估**：若装完后在真实会话里看不到 skill / 派不发 agent，
  说明 M2 的结论不成立，回 M2。**不要在 M3 里打补丁绕过。**

### M4 · 首屏价值：从「一张表」到「一个判断」

- **交付**：无参 `overwatch` 变成 §2.4 的输出形态；加 `--json`；退出码三值化
  （0 = 没有可疑断言 / 1 = 找到 / 2 = 读不全，且 2 **不算通过**）；`claims` 子命令
  继承 `verify-claims.mjs` 的四档但把 `UNCHECKABLE` 与 `UNKNOWN` 分开计数
  （现在合成一行打印，见 E10 的 `34 UNCHECKABLE`）。
- **陌生人到这一步能做什么**：第一次拿到关于**自己**会话的一个判断，并知道下一步跑什么。
- **怎么验收**：
  1. 首行在 3 秒内出现（`date +%s%N` 包一层断言，或测试里注入 `nowMs`）。
  2. 三类输入下 exit 0 / 1 / 2 各一例，有测试。
  3. 空语料时打印「没有语料，无法判定」，**不是**「一切正常」。
  4. 全量 scan 不再在默认路径上被调用（用 spy 断言）。
- **什么时候停下重新评估**：**如果 M1–M4 做完，连续一周没有任何非作者的人在新机器上跑过
  `overwatch doctor`**，停止加功能。那时缺的不是第五个阶段，是 §四.1 说的那类东西。

## 四、反面设计：五条候选，逐个评，三个是陷阱

### 4.1 陷阱一：现在做 TUI / GUI

**看起来该做**：仓库里有 6 个 TUI 文件、878 行设计稿、四个 TUI 测试文件；用户还要「每轮列 plan」，
界面听起来就是答案。

**为什么是陷阱**：

1. **它已经把顺序搞反了，而且留下了证据。** E8 实测：空状态下 TUI 的第一句话是
   `✗ 监视未在跑 · 先修这个`。一个陌生人打开面板，第一屏是让他去装一个守护进程。
   把它做成 GUI，只是把这个顺序错误放大 10 倍，成本也是 10 倍。
2. **TUI 是 40 秒扫描的渲染器。** E1：首字节 41.5 s。把表画得再漂亮，不改首屏要等 41 秒。
   先修「快」，再修「好看」——顺序不能换。
3. **它的输入已经有更好的宿主。** README 自己写着 `claude agents` 已把「看清有哪些会话」
   原生做完。本仓唯一站得住的差异是「断言 vs 证据」，而那件事在 `verify-claims` 里，
   不在面板里。

**该做什么**：先做 §二 的纯文本首屏。它同时是「列 plan」这个要求的形状验证，
又是 GUI 将来要渲染的那份数据（`--json` 同源）。**GUI 留到首屏有外部用户之后。**

### 4.2 陷阱二：把守护进程（daemon）当成入口

**看起来该做**：`watch.mjs` 已经在做，`install-watcher.mjs` 已经在装，通知需要一个常驻进程。

**为什么是陷阱**：

1. **作者本机上，「装好了」与「在工作」是两件事，而且同时成立。** E9 实测：
   启动器 `✓ 最新`、快捷方式 `✓ 存在`，同一时刻 `✗ jobs 已 23 分钟未运行`、`✗ probe 已 24 分钟`。
   让陌生人的第一步就是「装一个会静默停下的东西」，等于让他的第一次体验是
   **「我装了，但它没在工作，而我不知道为什么」**——这正是本仓花了两份研究去诊断的
   DF-023 那类故障。
2. **它和 ADR-0001 的定位正面冲突。** ADR 的决策段原文：「不包含常驻进程、不包含数据库、
   不包含守护循环。」
3. **它是 Windows-only。** `install-watcher.mjs` 的 `autostartAdvice()` 对 macOS/Linux
   只给配置说明而没有通知通道（README 已承认）。把 daemon 当入口，等于对一半用户
   第一句就说「你不被支持」。

**该做什么**：守护进程是**可选的第二步**，措辞固定为「可选，不影响下面任何结论」（§2.4 就是这么写的）。
真正的入口是一次性命令：跑完就退出，不留下任何在后台跑的东西。

### 4.3 陷阱三：做成 npm 包

**看起来该做**：`npx overwatch` 是最短的分发路径；有 `bin` 就有「入口」；
生态里所有工具都这么发。

**为什么是陷阱**：

1. **它买的是「发现」，卖的是「约束」。** 用户的技术约束是零 npm 依赖。发 npm 包本身不违反
   （不产生 runtime 依赖），但它带来发布流水线、版本号、`npx` 的联网拉取——
   而本工具的全部价值是**读本机已有文件**，为它加一次网络请求是纯负债。
2. **它解决不了 B8。** 一个 `bin` 装进 `node_modules/.bin` 之后，agents 与 skill
   仍然到不了用户的项目。**npm 包是「代码分发」的答案，而这里缺的是「配置分发」的答案。**
   选错渠道，做完了还是零。
3. **有更便宜的同类。** E14/E15 实测：一个 `.claude-plugin/plugin.json` + 一个本地目录的
   marketplace，`claude plugin validate` 通过、`marketplace add` 成功，
   **不需要 `package.json`、不需要联网、不需要发布**。它恰好是本仓唯一需要的那个渠道。

**结论**：不发 npm 包；**但要用插件/本地 marketplace 这个渠道**——它不是 npm 包的替代品，
它是「配置分发」这个问题的唯一现成答案。

### 4.4 评估过但不入选：支持多 provider

**看起来该做**：本仓全是 Claude Code 专属（`~/.claude/projects`、`DEFAULT_WEIGHTS`、
`state.json` 的字段），换宿主就归零，所以「抽象一层」很诱人。

**为什么现在不做**：本仓自己的研究已经量过——hook 协议层 Claude Code 与 Codex 可以共用脚本，
**但 transcript 格式无法统一**（JSONL+`type` / JSONL+`{type,payload}` / JSON+结构化记录）。
`scan-sessions.mjs` 的每一行判据都建立在 Claude Code 的 transcript 形状上。
做第二家 = 第二个解析器 + 一套新权重 + 新的、没有实测校准过的判据。
**而目前没有任何证据表明有第二家的需求**——这是一个零用户的工具，先解决第一个用户。
（ADR-0001 的反悔信号 #4 已经写了这条，不改。）

### 4.5 评估过但不入选：做 agent framework

**看起来该做**：用户原话里有「完整框架」。

**为什么这是最贵的那个陷阱**：`docs/design/2026-11-11-agent-framework-v2.md` 已经用实测把这条路
走过一遍并给出了结论——Mastra 覆盖「派活」，我们只剩「判活」，因此
**「框架」这个名字应当放弃，它是验收层**；不引 Mastra 的理由是 149 MB / 10 085 文件 / 6 分钟安装 /
要求 Node ≥ 22.13（本仓 README 写 ≥18）/ 默认权限自动放行（P15）。
**再开一次「做框架」，等于推翻一个已经用 22 条本机实测做出的决定，而手上没有任何新证据。**

**该做的**：把「完整框架」翻译成用户真正在描述的东西——一张能装进项目的
`.claude/agents` + `skills` + 一条 init（M3），加一个能判定交付物的入口（M4）。
**框架是结果，不是交付物。**

## 五、硬问题：如果只能做一件事

> **让 `.claude/` 那一层能被装进别人的项目，并为此写一条安装命令。**

理由：

今天这个仓库对陌生人的三个卖点里，有两个——「用户一次给完需求就做完」和「问问题」与「每轮先列 plan」——
**物理上只在这个仓库内部存在**。它们住在 `.claude/agents/` 与 `.claude/skills/oversight/SKILL.md` 里，
而这两处只在它们所在的那个项目被打开时加载；`SKILL.md` 里那 11 条裸 `node scripts/…`
还要求 cwd 就是这个仓库（E2 实测）。也就是说，一个陌生人 clone 下来、装好、配置好，
最好的结果是「他能在 Overwatch 仓库里用 Overwatch 的提问层」——
**他得到的不是能用在自己项目上的工具，是一个必须住进去的样板间。**
其余所有改进都排在这个事实后面：`doctor` 再快再准，它诊断的仍然是「这台机器能不能用这个样板间」；
首屏再漂亮，首屏之后依然没有第二条路。

而这一件事是**唯一一件「不做则其余全部作废」**的：

- 不做它 → 做 `doctor`、修退出码、加进度条，产品仍然是「一个只能自我观测的仓库」，
  陌生人拿到的价值等于零。
- 做了它 → 即使 `doctor` 很糙、首屏很丑，陌生人第一次拥有「我的项目里多了问问题和列 plan 这一层」，
  那是产品定义里唯一不可替代的部分。
- 它还有一个可证伪的、一小时内能完成的探针（M2），所以这不是一个赌注，是一个决策点。

**为什么不是「先做入口命令」。** 入口命令让使用体验变好，但它改善的是「这个工具好不好用」，
而当前的问题是「这个工具根本到不了要它的人手里」。前者是第二位的事。
**只有当 M2 证否（装不进去）**，答案才变成「入口 + doctor」——那个分叉已经写在 §一.4 和 M2 的停点上。

## 六、本文没有解决的

1. **问问题与列 plan 的协议本身（`question-protocol.md`、`plan-first`）本文不设计。**
   本文只建载体，假定那两层会由别的文档实现。载体成立而协议不成立，结果是
   「装得进去但没用」——这个风险不在本文范围内，但它是本文路线成立后的第一个风险。
2. **`init` 与用户已有 `.claude/` 的冲突策略只给了原则（不覆盖、列冲突）。**
   具体到「用户已经有一个叫 `oversight-planner` 的 agent」怎么办，需要真跑一次才知道。
3. **升级路径没设计。** 插件方式由宿主管版本；copy 方式要靠 `init --undo && init`。
   两者的代价没有实测对比。
4. **没有第二台机器、第二个宿主版本的数据。** 本文所有环境结论同源（一台 Windows / v26.12.1 / 2.1.289）。
