## 四类文档，四种可信度

**不要把它们的可信度混为一谈。**

| 目录 | 是什么 | 可信度 | 引用前要做什么 |
|---|---|---|---|
| 根目录 / `docs/*.md` | 入口与手册 | **当前事实**，硬门守着一部分 | 直接引用；数字跑命令复核 |
| [FACTS.md](FACTS.md) | 实测事实清单 | **快照**（每条注明时间） | 引用前重跑命令；先读「如何读这份文档」 |
| `docs/spec/` | 现行规格 | **当前事实**（唯一真源） | 直接引用；与代码冲突时以代码为准并修文档 |
| `docs/adr/` | 决策记录 | **当前事实**（为什么这么定） | 引用结论，注意「反悔信号」节 |
| `docs/design/` | 设计推演 | **全部未实现** | 不要当能力说明；先看 `design/README.md` 的状态列 |
| `docs/research/` | 实测报告 | **过程记录**，会过期 | **必须先查 `research/README.md` 的状态标记** |

`docs/research/` 是最容易误用的一类：里面既有最好的样板，也有已被自己后续报告推翻的结论。
索引页的「已被推翻的结论」表就是为此存在——**任何一条结论在引用前，先去那里查一眼**。

## 硬门守着哪些「文档一致性」

数字靠人记着同步是不现实的。`scripts/check-structure.mjs` 把这些变成提交前必过的检查：

| 检查 | 守什么 | 红了怎么办 |
|---|---|---|
| `checkTestCount()` | 四份文件里的回归测试数必须等于实跑值 | 跑 `node --test scripts/*.test.mjs` 看真实条数，改文档 |
| `checkDocReferences()` | 活文档里引用的 `scripts/` `templates/` 路径必须存在 | 补文件，或在该行标「待建」 |
| `checkDocCommands()` | 文档里的 `node scripts/<名字>.mjs --flag`，脚本要存在、参数要真被支持 | 改命令或改脚本 |
| `checkDocConstants()` | 文档写 `` `CONST = 42` `` 时，源码里那个常量必须真是 42 | 改数字或改常量 |
| `checkResearchIndex()` | 每份研究报告都要在索引里登记状态 | 在 `research/README.md` 加一行 |
| `checkCapabilities()` | 能力清单里的每条命令必须可执行；README 必须指向它 | 改命令或补入口 |
| `checkLinks()` | 文档相对链接不能悬空 | 修链接 |
| `checkDesignIndex()` | 设计文档必须在索引里、且索引写明「未实现」 | 登记状态 |
| `checkChangelog()` | 改了源码/规格却没有 CHANGELOG 条目 | 补条目 |

这些检查的共同思路：**把「记得同步」换成「不同步就红」**。它们在每次提交前跑，
成本是一秒内；收益是文档不会再悄悄落后于代码。

## 归档与合并建议

见 `docs/research/README.md` 里的「文档同步审计」条目。要点：

- `docs/research/` 只进不出（历史记录有证据价值），但**索引是唯一入口**。
- `docs/design/` 里已裁决否决或已无实施可能的，索引里标清楚，不删（同样的理由）。
- 任何「当前事实」级文档都必须有入口指向它，否则等于不存在（硬门会查其中一部分）。
