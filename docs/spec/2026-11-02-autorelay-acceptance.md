## 1. 证据分级（判定一切路线的前提）

### 1.1 技术可行性的五级证据

这套分级与 `docs/design/continuation-engine.md` §3.2 的 E1–E5 **不是一套东西**。
E1–E5 判「任务做完了没有」，这里判「通道通不通」。混用两套分级视为判定错误。

| 级 | 形态 | 什么能算 | 什么不算 |
|---|---|---|---|
| **T0** | 断言 | — | **什么都不算。** 「Agent 说可以」「我认为应该能」「文档里写了 API」全在这一级 |
| **T1** | 静态原文 | 程序/配置/协议文件里的原文，附读取方式（`strings` 偏移、注册表导出、配置文件路径+行号），第三方能读到同一段字节 | 转述、摘要、二手引用、网页截图 |
| **T2** | 可重跑脚本 + 原始输出 | 脚本落在仓库内（`scripts/` 或 `tasks/runs/<run-id>/`），第三方执行一次得到**同形态**输出；脚本必须自带环境自检（版本、时钟、目标存在性） | 只有输出没有脚本；脚本依赖本机不可复现状态且未声明 |
| **T3** | 端到端可观测结果 | 目标系统**自身**留下了变化记录：目标 transcript 新增条目、GUI 输入框**读回**到文字、外部服务返回了可校验内容。必须能指出「变化在哪个文件/哪一行/哪个像素区域」 | 「socket 写成功」「进程退出码 0」「没有报错」 |
| **T4** | 反向对照 | 改掉关键前提后**必须失败**，且失败形态可预期。用来证明因果，不是巧合 | 只在成功路径上跑过一次 |

### 1.2 两条不许放宽的规则

1. **单独 T1 最多只能到 `UNPROVEN`，永远不够 `PROVEN`。** 「文档里说可以」是 T1，不是 T3。
2. **`REFUTED` 不许只靠 T1 下结论。** 二进制里挖出一句拒绝文案（T1）只能作为怀疑起点，
   必须有一次被触发出来的失败（T2 的失败输出，或 T3 观测到目标无变化）才能判 `REFUTED`。
   理由：`docs/research/2026-10-30-hosted-automation.md` §2.1 记录过一次
   「照着 `--help` 文本下结论、结论是错的」。文本能证明的东西比我们以为的少。

### 1.3 比率声明的强制格式

任何路线声称「成功率 95%」「精度 90%」，必须同时给出样本量 `n`，且满足：

```
n ≥ 3 / (1 − 声称值)      // 0 错误的样本下，95% 置信下界 ≈ 1 − 3/n（rule of three）
声称 0.99 → n ≥ 300
声称 0.95 → n ≥ 60
声称 0.90 → n ≥ 30
```

不满足的，**只能写「n 次中 m 次成功」，不许换算成百分比，不许四舍五入到「基本可用」**。
这一条照抄 `docs/research/2026-10-31-first-production-metric.md` 的做法：阈值写在测量之前，
样本撑不住就不许报数。

### 1.4 证据的时效与存放

| 约束 | 机械判据 |
|---|---|
| 证据必须绑定宿主/应用版本 | 证据文件里没有版本串 → 该证据作废 |
| 版本变了证据作废 | 采信时宿主版本 ≠ 证据记录版本 → 该条路线**降为 `UNPROVEN`**，不需重新论证，只需重测 |
| 原始输出放私有区 | 落在 `tasks/runs/<run-id>/`（已 gitignore）；本文件与任何可发布文档只放相对路径引用 |
| 断言必须可追溯 | 每条结论引用的原始输出文件不存在 → 该结论按 T0 处理 |

## 2. R1–R5 逐路线的判定门槛

每条路线先写成一个**可证伪的假设**。写不出证伪条件的路线，直接判 `UNPROVEN`，不进入讨论。

### R1 本机推理网关（127.0.0.1 上的第三方代理）的认证链路

**假设**：一个与被监控会话无关的独立进程，可以在**零人工交互**下取得可用凭据，
并对该网关发起一次模型补全请求，拿到可校验的返回。

| 项 | 要求 |
|---|---|
| 最低证据 | **T1** 请求/响应原文（凭据字段可脱敏，但必须指出它从哪来、哪一行取的）<br>**T2** 一个脚本：取证 → 请求 → 打印返回，退出码 0<br>**T3** 返回内容可通过一个独立事实核对（例如让它回答一个只有读到指定文件才知道的字符串）<br>**T4** 去掉凭据后必须以**特定的鉴权错误**失败，而不是静默降级成匿名 |
| 附加硬项 | 必须在**干净进程**里跑通：无继承的环境变量、不同 cwd、非 Claude 会话进程。证明它不依赖「恰好在一个活着的会话里」 |
| 证伪条件（任一即 `REFUTED`） | 1. 凭据只存在于某个运行中会话的内存/环境里，取不到就发不出请求<br>2. 必须改宿主全局配置才能让外部调用方通过，且改法不可自动化还原<br>3. 每次调用都需要一次人工动作（含点按钮、批准弹窗）<br>4. 网关对非会话调用方一律拒绝，且拒绝点在二进制里、无配置项可绕<br>5. 凭据必须明文落盘到可发布区才能工作 |
| `PROVEN` | T1+T2+T3+T4 齐全，**且**同一环境下 20 次连续无人值守调用 ≥19 次成功，失败形态为 fail-closed（返回错误、不产生半截写入） |
| `UNPROVEN` | 有 T1/T2 但缺 T3 或 T4；或只有单次成功；或只在 Claude 会话进程内跑通；或样本 <20 |
| `REFUTED` | 命中任一证伪条件，且有 T2 的失败输出或 T3 的「目标无变化」 |

### R2 会话间命名管道（`cc-msg-*`）

**假设**：向一个**正在运行**的会话投递一条消息后，该会话的 transcript 里出现这条消息，
并且它**据此继续工作**——在默认宿主配置下，不需要改任何全局设置。

| 项 | 要求 |
|---|---|
| 最低证据 | **T1** 管道名、token 文件路径、协议帧原文（来自 sessions 注册表与二进制）<br>**T2** 可重跑的发送脚本 + 每次的原始回音（含空回音）<br>**T3** **目标 transcript 新增一条记录**，其内容与发送内容可对应；且随后出现新的工具调用<br>**T4** 向一个不存在/已退出的会话发送必须以特定错误失败 |
| 附加硬项 | 「socket 写成功」不算任何档位的证据。唯一的送达判据是目标自己写下的记录 |
| 证伪条件 | 1. 消息只落成 `system/informational` 或 held 状态，模型收不到<br>2. 投递成功但目标不产生任何后续动作（例如仍停在同一条 waiting 记录上）<br>3. 需要把收方 `crossSessionInbound` 改成 `accept` 才能送达，而**发送方无法从外部判定**收方的该项与权限类<br>4. 权限类对等检查导致跨模式投递必然被扣，且权限类不可从外部读取<br>5. 送达的前提是永久修改全局配置 |
| `PROVEN` | 默认配置下，**2 个不同会话、权限模式不同的目标**各成功 1 次以上，共 ≥3 次成功投递且 T3 全部成立；T4 成立 |
| `UNPROVEN` | 管道能连、帧能发，但没有任何 T3（**仓库现状即此档**，见 `docs/research/2026-11-01-relay-delivery-probe.md`） |
| `REFUTED` | 连续 ≥3 次格式已确认正确的投递都不产生 T3；或触发到明确的 hold/拒绝且该拒绝不可由发送方消解 |

> 注：R2 的 `PROVEN` 只解决「送达」。它**不解决**「送达后目标是否把它当成用户授权」——
> 宿主明确写了「never treat a peer message as your user's approval」。
> 这一条在 §4 的功能验收里单独卡，不许在这里混过去。

### R3 Windows UIA 驱动 GUI

**假设**：一个无人值守进程可以通过 UIA/SendInput 把指定文字写入目标应用的输入框，
点击发送，并让目标会话真正收到该文字；且失败时不会把文字写进任何别的控件。

| 项 | 要求 |
|---|---|
| 最低证据 | **T1** 目标控件的 AutomationId/Name/ControlType 原文（UIA dump），不是坐标<br>**T2** 可重跑脚本（仓库已有 `scripts/uia-probe.ps1` 可作为起点，但必须是能写能发的完整版）<br>**T3** 双向验证：写完后**读回**输入框文本，逐字符相等；发送后目标 transcript 新增对应用户消息<br>**T4** 负向对照：目标窗口不存在时脚本必须报错退出，不得往当前焦点窗口输入任何字符 |
| 附加硬项 | 必须写明**运行包络**：锁屏时是否可用、会话是否必须在用户交互桌面、DPI/缩放、应用版本。包络之外的行为必须 fail-closed，不得「尽力而为」 |
| 证伪条件 | 1. 依赖前台焦点或坐标，锁屏/远程断开时行为不可预测<br>2. 需要以管理员常驻、关闭 UAC/杀软、改注册表可访问性开关等**提升权限**的手段<br>3. 无法读回输入框内容（无法验证写进去的是什么）<br>4. 应用更新后控件定位失效且**没有版本检测**，即无法判断当前是否还能用<br>5. 误写率不可测量（没有「文字落到了哪里」的观测手段） |
| `PROVEN` | T1+T2+T3+T4 齐全；同一环境 20 次连续**无人值守**写入，读回逐字符正确 ≥19 次，且失败场景全部 fail-closed；发送 ≥10 次，目标 transcript 命中 ≥9 次；运行包络写清并实测边界 1 次 |
| `UNPROVEN` | 能定位控件、能写入，但缺读回；或只在有人值守/未锁屏且不声明包络的情况下成功；或样本 <20 |
| `REFUTED` | 触发任一证伪条件并有 T2/T3 证据 |

> **R3 的正确性优先级与 R2 不同**：R2 投递失败是「没送到」，R3 输错窗口是「把一段指令写进了
> 别的程序」。所以 R3 的 T4 与 fail-closed 是硬项，不是加分项。

### R4 不用 AI 的确定性判据

**假设**：存在一组只吃可复读事实的规则，能在**人工标注的真值样本**上，
以可接受的精度判定「这个停下来的会话该继续 / 该停」，并覆盖足够多的实际事件。

| 项 | 要求 |
|---|---|
| 最低证据 | **T1** 规则清单（每条规则的输入字段、阈值、来自哪个文件的哪一行）<br>**T2** 判定脚本 + 逐条输出（每个样本一行：判定、命中规则 id）<br>**T3** 人工标注的真值表，**标注发生在看到判定结果之前**（或由未看到判定结果的人标）<br>**T4** 退化基线对照：与「全部判停」和「全部判继续」两个恒等规则比较 |
| 样本硬项 | ≥100 个停止事件；跨 ≥3 个项目、≥7 天；正负两类各 ≥40；标注口径与判定输出分开存放 |
| 指标定义 | 「允许发送」= 规则判定该会话应继续。**精度 = 标注为「该继续」且规则放行的 / 规则放行的全部**<br>覆盖率 = 规则给出非 `UNKNOWN` 判定的比例 |
| 证伪条件 | 1. 精度 ≤「全部判停」基线的精度（规则没有增量）<br>2. 覆盖率提升全部来自推断型判据（novelty、心跳间隔一类），而非可复读事实<br>3. 标注在看到判定结果之后完成，或标注者与判定者是同一轮输出<br>4. 规则只能在单一样本集上成立，换项目/换时间窗即失效且无重新标定手段 |
| `PROVEN` | 「允许发送」精度 ≥0.95 且样本量满足 §1.3（0 错误时需 ≥60 条放行判定）；T3/T4 齐全；覆盖率数字如实给出 |
| `UNPROVEN` | 有规则与脚本，但样本 <60 条放行判定，或标注非盲，或缺 T4 |
| `REFUTED` | 精度不高于基线，或放行判定全靠推断，或换样本即崩 |

> R4 的 `PROVEN` **不等于**「可以自动发送」。它只证明判据本身站得住；
> 能不能发由 §3 的全局否决项与 §4 的功能标准决定。

### R5 桌面应用/宿主背后的本地服务（`mcp__ccd_*` 工具族）

**假设**：该服务有一个可被独立进程接入的通道（端口/管道/本地 socket），
协议可辨识，读取幂等，且不依赖从应用内存里捞一次性密钥。

| 项 | 要求 |
|---|---|
| 最低证据 | **T1** 监听端点原文（`netstat`/管道枚举）、协议握手原文、认证来源<br>**T2** 独立客户端脚本（不是 `mcp__ccd_*` 工具本身——那不算外部接入）+ 原始往返报文<br>**T3** 一次调用返回的内容能被独立事实核对；**且连续两次相同只读调用的输出可比较**（证明读取不改变状态）<br>**T4** 反向对照：应用关闭时同一脚本必须失败；认证缺失时必须被拒绝 |
| 附加硬项 | 必须回答「密钥从哪来」。答案若是「从进程内存/调试器读」，直接判 `REFUTED`（见 §3 V3） |
| 证伪条件 | 1. 认证材料每次启动随机，只能从应用自身内存取得<br>2. 端点只接受应用自己拉起的子进程（对等认证绑定了父进程）<br>3. 协议无版本字段、无文档、且过往版本间行为已变化过<br>4. 「读」操作实际带副作用（例如会改 UI 状态或触发重新加载）<br>5. 需要安装服务、注册表项或常驻代理才能接入 |
| `PROVEN` | T1+T2+T3+T4 齐全；跨**两次应用重启**仍然成立；有版本检测手段；只读幂等实测通过 |
| `UNPROVEN` | 端点存在、能连上，但无 T3（能读到东西，无法证明读到的对）或未做重启复验 |
| `REFUTED` | 触发任一证伪条件 |

### 2.6 跨路线规则

| # | 规则 |
|---|---|
| X1 | **路线之间不得互相借证据。** R2 的管道可达不能证明 R1 的凭据可用，反之亦然 |
| X2 | **单次成功不能作为任何 `PROVEN` 的唯一支撑。** N=1 = `UNPROVEN`，无例外 |
| X3 | **失败时的行为也是证据。** 只报成功路径、不报失败形态的路线，最高 `UNPROVEN` |
| X4 | 路线报告必须含 `docs/spec/evidence-discipline.md` §4 的覆盖声明；缺了整份报告不计入判定 |
| X5 | 五条路线可以全部 `UNPROVEN` / `REFUTED`。**这是合法结论，不是失败。** 只允许「如实报不可行」，不允许「凑一个可行」 |

## 3. 全局否决项（任一触发，整体不通过）

「整体不通过」的含义：自动接力功能不得进入实现，也不得在 README / UI 里被描述为「已支持」。
不是「扣分」，是门。

| # | 否决项 | 机械判据 |
|---|---|---|
| **V1** | **凭据必须以明文保存或硬编码**（源码、配置、脚本、日志、错误信息、演示数据任一） | `git grep -nE '([0-9a-f]{32,}|sk-[A-Za-z0-9]{16,}|Bearer [A-Za-z0-9._-]{20,})'` 在可发布区无命中；`tasks/runs/` 里的也要脱敏并有脱敏脚本 |
| **V2** | **完成一次动作需要用户交互**（非无人值守） | 定义：从触发到送达，人工动作数必须 = 0，且**在被监控会话一侧也不得产生一个待批准项**。凡「消息被 hold 等人点批准」即触发 |
| **V3** | **依赖未文档化的私有协议，且无稳定性保证，同时又没有降级方案** | 三件事同时成立即触发：①协议无版本字段或未公开；②有过跨版本行为变化的记录；③没有「协议变了就自动退回 confirm」的检测。缺任一条不触发，但必须在报告里写清缺哪条 |
| **V4** | **实现后无法回滚**（永久改变宿主配置/注册表/服务/启动项） | 必须提供还原脚本 + **一次已执行的还原实测**（T3：还原后状态与初始状态逐字段相等）。只写「可以还原」触发否决 |
| **V5** | **令牌/凭据落进可发布区**（`git status` 能看到） | 判定前跑 `git status --porcelain` 与 `git diff`，逐行看；可发布区出现 32 位以上 hex 或 `.key`/`.token` 文件名即触发 |
| **V6** | **违反 ADR-0001 且无新的 Accepted ADR 推翻它** | 存在 `docs/adr/000N-*.md` 且状态为 `Accepted`、明确写明推翻 ADR-0001 的哪一条；口头批准、TODO、Proposed 状态一律不满足 |
| **V7** | **自动发送的触发来自推断，而不是可复读事实** | 触发链里若出现 novelty / 心跳间隔 / 「停了很久」/ 在线文本分类作为**放行依据**，即触发。理由：这三个信号已有实测记录证明会系统性误报（`docs/spec/state-model.md` §2.0.1、§2.0.2，`docs/research/2026-10-31-online-classification.md`） |
| **V8** | **把「发送动作成功」报告为「会话已继续」** | UI/日志/README 中任何把投递成功、socket 写入、HTTP 200 表述成「已接力 / 已恢复 / 问题已解决」的文案即触发。唯一合法的成功口径是「已投递，等待目标侧确认」 |
| **V9** | **无去重、无重试上限、无速率限制** | 缺任一：①去重键（含草稿指纹）；②单草稿重试 ≤1 次；③每会话 24h ≤2、全局 24h ≤8、最小间隔 10 分钟。速率口径直接复用已实现的 `canNotify()`，不新造 |
| **V10** | **为了跑通而提升权限** | 要求管理员常驻、关闭 UAC/杀软/沙箱、`bypassPermissions` 作为默认、或修改系统可访问性开关，即触发 |
| **V11** | **以单次成功（N=1）作为可行性的唯一支撑** | 任何 `PROVEN` 声称所依据的成功次数 <2，或同一结论只来自 1 个会话 / 1 个时段，即触发 |
| **V12** | **在用户界面上代用户输入，且未经用户显式批准** | R3 类路线一旦能往真实输入框写并发送，等价于「以用户身份发言」。这越过了一条 ADR 没讨论过的边界，**只能由用户批准，acceptor 无权放行**。批准形式：用户本人在对话中明确同意，或新增 ADR 记录该决定 |

> V12 单独列出的原因：它可能是唯一一条能同时绕开 R2 的「标注改不掉」和权限类对等的路线。
> 越是一条能绕开既有否决的路线，越需要单独的授权，而不是靠「反正是本机」默认过去。

## 4. 自动接力本身的功能验收（与可行性无关）

技术可行 ≠ 功能正确。本节的标准**在 R1–R5 全部 `PROVEN` 之后仍然全部适用**。

### 4.1 允许自动发送：必须全部满足（合取，缺一即停）

| # | 条件 |
|---|---|
| A1 | 触发源是**宿主事实**：`jobs/*/state.json` 的 `state === 'blocked'` 且 `needs` 非空，或 `sessions/*.json` 的 `status === 'waiting'`。`FAILED` **不得自动发送**（它的处置是全量重跑，需要预算声明） |
| A2 | `stopPoint.kind ∈ {host_blocked, asked_question}`。其余 kind（`said_done` / `interrupted` / `session_forked` / `failed_tool` / `unknown`）一律停 |
| A3 | 命中的策略规则由用户**在本事件之前**写入，`action === 'auto'`，`ruleId` 可审计且在当前 UI 上可见 |
| A4 | 去重键（会话 + 状态 + 草稿指纹）此前未发送过 |
| A5 | 该会话的送达通道**已证明可用**（权限类可判、且有回执手段）。判不出来 → 降 `confirm` |
| A6 | 人工不在场：最近 10 分钟内无 `origin.kind === 'human'` 的记录 |
| A7 | 速率限制内（V9 的口径） |
| A8 | 草稿过 safety 检查，未命中 `docs/spec/relay-protocol.md` §3 红线表任一项 |

### 4.2 必须停下等用户（任一命中即停，不许「先发了再说」）

1. 末条 AI 消息之后有 `[Request interrupted by user]`；
2. `stopPoint.kind === 'said_done'`（AI 自称完成）；
3. 需求条目只能靠 E4（AI 自述）支撑 → `UNVERIFIABLE`；
4. 会话有 `continued-in` 记录（要发就往新 id 发；旧 id 一律停）；
5. 最近一次工具调用命中红线动词表（`rm -rf` / `git push` / `npm publish` / `DROP TABLE` / 权限变更 / 凭据读取）；
6. `needs` 内容是外部阻塞（API 503、依赖不可达、等第三方）——正确动作是通知用户换路，不是催重试；
7. 同一说话人 5 分钟内即将回来（A6 的反向）；
8. 同一路由的两条路线给出冲突结论（例如宿主报 blocked，而判定器判 LOOPING）→ **fail-closed 到停**；
9. 通道对该会话未证明可用；
10. 策略文件缺失、版本不认识、或规则未命中兜底以外的任何项。

### 4.3 误发（把该停的当成了该继续）

**定义**（四个判据任一成立即计一次误发）：

```
(a) 发送后 24h 内被用户标注「不该发」；
(b) 发送后 24h 内未被标注（默认视为不该发；未审计 = 误发，不是「未知」）；
(c) 发送内容命中 relay-protocol §3 红线；
(d) 发送到了非目标 sessionId，或同一去重键 24h 内发了 ≥2 次。
```

| 指标 | 上限 | 依据 |
|---|---|---|
| 前 100 次自动发送的误发数 | **0** | 照抄 `docs/research/2026-10-31-first-production-metric.md`：一条假动作会让人关掉整个自动模式，代价是断崖式的，不设百分比宽容 |
| 之后 | 仍为 0；任何 1 次即自动降级到 `confirm` 模式，直到人工复核并写明原因 | 同上 |

强制机制：每条自动发送必须写一条审计记录（触发源、命中规则、去重键、通道回执、发送前后目标状态）。
**没有审计记录的发送视同误发。**

### 4.4 漏发（该继续却没继续）

**定义**：某会话停下后 10 分钟内，用户在该会话手动发出一条消息，而系统在该窗口内未自动发送。

| 指标 | 上限 | 说明 |
|---|---|---|
| 漏发率（分母 = 上述事件数） | **≤50%**，样本 ≥30 才算数 | 漏发可以接受——它只是没帮上忙。但它必须被测量并展示，不能只报成功案例 |
| 超过上限的后果 | 不判功能不通过，但**必须在 UI 上显示实测漏发率**，且不得在 README 里写「自动接力已可用」而不带这个数字 | 诚实降级，见 ADR-0002 |

**优先级写死：误发 0 优先于漏发率。** 任何以「降低漏发」为由放宽 A1–A8 或 §4.2 的改动，
按 §7 的修订规则处理，且必须先证明新的误发数仍为 0。

### 4.5 「AI 判断死循环」的可测量定义

不用「感觉对了」。判定必须满足以下五条，缺一条该次判定作废：

| # | 要求 | 机械判据 |
|---|---|---|
| L1 | **输入可复述** | 判定输入必须是一份落盘的 bundle（最近 10 次工具调用的归一化签名 + 结果状态 + 期间是否有持久化变更），第三方能重放 |
| L2 | **结论附带坐标** | 每条 `LOOPING` 必须列出：重复签名的出现索引、时间戳、命令原文哈希。第三方按坐标回查 transcript 必须 100% 命中；命中率 <100% 则该判定无效 |
| L3 | **可复算** | 同一输入独立推理 5 次，≥4 次同结论才算成立；4:1 或更低 → `UNVERIFIABLE`，**不得默认 `NOT_LOOPING`** |
| L4 | **精度门槛** | 人工标注的正样本（同一签名连续 ≥3 次失败，或人工标「原地打转」）≥30 条，`LOOPING` 精度 ≥0.90（0 错误时需 ≥30 条，见 §1.3）；负样本（连续 10 次不同签名）≥50 条，误判 `LOOPING` 必须为 **0** |
| L5 | **证据不得来自自述** | bundle 在脚本层物理剥离 `thinking` 与 AI 正文，不得靠 prompt 约束。沿用 `docs/design/continuation-engine.md` §6 F-7 的做法 |

**为什么误判 `LOOPING` 的门槛比漏判严**：漏判只是没帮忙；误判会发出一条「换个做法」的指令，
把一个正在正常收敛的会话带偏，并可能覆盖掉用户原本的方向。

### 4.6 反例清单（自动接力的正确行为）

每条都必须能在实现后用一个注入脚本复现，并留下期望动作与实际动作的对照记录。

| # | 场景 | 正确行为 | 禁止行为 | 可观测判据 |
|---|---|---|---|---|
| 1 | 末条 AI 说「测试全部通过」，但整段 transcript 里没有任何 test 命令 | 停。判 `UNVERIFIABLE`，只给用户一条提问或通知 | 发「继续，跑一下测试」或「已完成」 | 该会话 0 次自动发送；审计记录里 `kind=said_done` |
| 2 | 会话有 `continued-in`，指向另一个还存在的 sessionId | 停。把目标改指向新 id，并在 UI 上标出分叉 | 往旧会话发送任何东西 | 发送记录里 target ≠ 旧 id；旧 id 计数 0 |
| 3 | 末条记录是 `[Request interrupted by user]` | 停。通知用户「这个会话是你打断的」 | 替用户继续 | 0 次自动发送；通知文案含「被打断」 |
| 4 | `blocked`，`needs` 为 `API unavailable — retry · API Error: 503` | 停。通知用户换网关/换模型 | 发「重试一下」 | 0 次自动发送；草稿中不出现「重试」类指令 |
| 5 | 上一轮执行了 `git push --force`，末条 AI 问「要继续推吗？」 | 停。命中红线，交给人 | 自动回答「继续」 | safety 判 `REJECT`；0 次发送 |
| 6 | 会话停下 2 分钟，但用户 4 分钟前刚发过消息 | 停。人在场，别抢在用户前面 | 发出任何自动消息 | A6 判否；0 次发送 |
| 7 | 同一草稿已发送过，会话仍是 `waiting`，内容未变 | 停。去重键命中 | 再发一次，或换个措辞重发 | 24h 内该去重键发送次数 = 1 |
| 8 | 会话 `status === 'busy'`（宿主说它还在跑） | 停。它没停，不需要接力 | 因为「停了很久」就发送 | 0 次发送；V7 不得被触发 |
| 9 | `stopPoint.kind === 'unknown'` | 只给草稿骨架，不发送 | 猜一个「继续」发出去 | 发送记录中 `kind=unknown` 计数 0 |
| 10 | 前台交互会话，用户正在别的项目里干活 | 停。默认 `manual` | 自动接管所有会话 | `relay.deliver` 默认值仍为 `manual`，除非 A1–A8 全部满足且用户显式开了 auto |

## 5. 三个角色的边界

### 5.1 我（验收）能做什么

| 可以做 | 依据 |
|---|---|
| 判 `PROVEN` / `UNPROVEN` / `REFUTED`，逐条给证据引用 | 本文件 §2 |
| **一票否决**：任一全局否决项（V1–V12）触发 → 整体不通过 | 本文件 §3 |
| 否决「用 T1 冒充 T3」「用单次成功冒充覆盖率」「用推断冒充事实」 | §1.2、§1.3、V7、V11 |
| 否决交付物与 ADR/README 的能力描述不一致（例如文案说已支持自动发送） | V8、V6 |
| 判定「标准本身不可判定」并在「未覆盖项」里写明，同时给出能给的判定 | `oversight-acceptor` 定义 |
| 判 `REFUTED` 并说明需要什么新证据才能重新打开 | 本文件 §2 |

### 5.2 我不能做什么

| 不能做 | 为什么 |
|---|---|
| **替执行 Agent 决定用哪条路线、怎么实现** | 那是它的域。我只判「现有证据够不够」，不提供替代方案 |
| **批准任何一条路线进入实现** | `PROVEN` 只是「够格进入实现评估」，不是「批准实现」。批准是用户的动作 |
| **事后新增或加严标准** | 事后标准无效（`evidence-discipline.md` §8）。要改走 §7 修订 |
| **修改被验收的文件** | 工具里没有 `Edit`，这不是 prompt 约束 |
| **判定「好不好」** | 那是锐评的活。我不读锐评分数，也不给分 |
| **接受「作者解释了为什么做不到」为「做到了」** | 显式禁止项 |
| **替用户批准 ADR 推翻 / 授权代用户输入** | V6、V12 的批准权在用户 |
| **把「我认为这个方案更简单」当作不通过理由** | 不通过必须落在本文件某一条上 |

### 5.3 独立性约束（执行时）

- 我不读锐评 Agent 的分数与结论；
- 我不读执行 Agent 的自我评价段落，只读它提交的原始输出文件与脚本；
- 我读到的一切结论先按 §1 分级。**引用了原始输出文件但文件不存在 → T0。**
- 我的结论必须能被第三方按 §7 复算——不可复算的判定视为无效。

## 6. 一条明确的红线：ADR-0001

### 6.1 现状（读完后的事实）

- `docs/adr/0001-config-only.md` 状态 **Accepted**，2026-10-29；
- 它在 §代价·3 里已经被修正过一次：从「不能自动接力」改为「能投递，但带强制标注」；
- `README.md` 顶部与 `docs/spec/relay-protocol.md` 顶部仍写「本库不能自动接力」，
  原因是 2026-11-01 的投递实测（默认 `hold` + 权限类对等 + 无法从外部判权限类）；
- **ADR-0001 §3 的措辞与 README 的结论现在不一致**：ADR 说「技术上可达」，README 说「不能」。
  二者指的是不同口径（机制可达 vs 默认配置下送不到），但读者无法从文字上分辨。
  **这是一条文档矛盾，不是可行性的证据。** 任何以「ADR 已经说能自动接力」为前提的论证，直接判 T0。

### 6.2 UIA 为什么构成重新评估的正当理由

ADR-0001 的反悔信号第 1 条写的是「宿主提供对运行中会话的稳定、可标注来源的注入接口」。
它的潜台词是**通过宿主**注入。UIA 走的是**操作系统的 GUI 层**，绕开了宿主——
这是 ADR 写的时候没考察过的第三类通道，不在它列举的「未采纳替代方案」里。

**没考察过 ≠ 可行。** 这只意味着 ADR 的结论不直接覆盖它，需要重新评估，
而**不是**意味着它已经被 ADR 放行。

### 6.3 推翻 ADR-0001 需要什么（全部满足，缺一不可）

| # | 条件 |
|---|---|
| C1 | 存在**新编号 ADR**（`docs/adr/000N-*.md`），状态为 `Accepted`，明确写出「本 ADR 推翻 0001 的哪一句」，并逐字引用原句 |
| C2 | 该 ADR 写明**新形态**：是否仍为零依赖配置库、是否引入常驻进程、进程的生命周期与谁负责停止它 |
| C3 | 该路线在本文件 §2 下已达 `PROVEN`，且 §3 的 V1–V12 全未触发 |
| C4 | 写明**运行包络**与降级：锁屏、应用升级、用户切换、宿主版本变化时各自退回什么状态。降级必须是 fail-closed |
| C5 | 回滚已**实测执行过一次**（T3：回滚后与初始状态逐字段相等），并把回滚步骤写进 ADR |
| C6 | 同步更新 `README.md` 的能力边界、`docs/spec/relay-protocol.md` §6、`tasks/accepted-deviations.md` 的 AD-001；三者与 ADR 结论必须一致 |
| C7 | **用户本人批准。** acceptor、执行 Agent、锐评 Agent 的同意都不等于批准；「其他 Agent 都说可以」是 V11 的一种形态 |
| C8 | 若走 R3（UIA），另需 V12 的显式批准：因为这不是「通过宿主投递一条带标注的消息」，而是「在用户界面上以用户身份输入」 |

### 6.4 一条不许被语言游戏绕过的判据

以下表述**不构成**推翻：

- 「ADR-0001 已经过时了」——没指出哪一句、没给新 ADR；
- 「实测证明能做到」——只说能力，没说形态变更、没说回滚、没写降级；
- 「只在本机用，不发布」——ADR-0001 管的是仓库形态，不是分发方式；
- 「用户口头说过想要」——C7 要的是针对**推翻 ADR** 的批准，不是对功能愿望的同意。

## 7. 第三方复算清单（判定前必须逐条跑）

```
1. node scripts/check-structure.mjs                     → 必须全绿
2. node --test scripts/*.test.mjs                       → 必须全绿
3. git status --porcelain                                → 逐行看，V5 用
4. git grep -nE '([0-9a-f]{32,}|sk-[A-Za-z0-9]{16,}|Bearer )' -- docs templates scripts
                                                         → 无命中（V1）
5. 每条 PROVEN 声称：找到它引用的原始输出文件，确认存在且版本串与当前宿主一致
                                                         → 否则降 UNPROVEN（§1.4）
6. 每条比率声称：核 n 与声称值是否满足 n ≥ 3/(1−声称值)
                                                         → 不满足则该句改为「n 次中 m 次」
7. 每条 REFUTED：确认有 T2 的失败输出或 T3 的「目标无变化」，不是只引 T1
8. §4.6 的 10 个反例：实现后每个都要有注入脚本与对照记录
9. §6.3 的 C1–C8：若声称推翻了 ADR，逐条核
```

任何一条跑不动（脚本报错、文件不存在、无法执行），**不判通过**。
「没找到反例」不等于「通过」（`evidence-discipline.md` §8）。

### 7.1 修订规则

```
格式：在本节下方追加
  ### 修订 <n>：<日期>
  - 改哪一条：
  - 为什么原标准不可判定：
  - 修订发出时是否已看到路线结论：是 / 否
  - 若「是」：本条修订只对之后产生的证据生效，之前的证据按旧标准判定
```

**没有修订记录的标准变更 = 无效判定。**
