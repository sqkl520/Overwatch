# 接力协议

> **能力边界（先读这一段）**：本库**不能自动接力**。
> 原因是宿主的注入语义与规格假设不符，不是因为实现没做完。详见 [ADR-0001](../adr/0001-config-only.md) §代价·3。
> 所有接力投递默认为 `manual`：Relay Agent 产出草稿，由用户复制发送。

## 1. 触发条件（Q2）

| 代号 | 条件 | 默认启用 |
|---|---|---|
| (a) | 显式完成信号（目标会话产出终止标记，或用户标记完成） | 否 |
| (b) | 超过 N 分钟无新用户消息，**且**最后一条 AI 消息是「请你确认 / 请你提供」类问句 | **是** |
| (c) | 检测到 AI 反复重复同一失败动作（同一命令签名连续失败 ≥3 次） | **是** |
| (d) | 用户手动标记 | **是** |

默认组合：**(b) + (c) + (d)**。

### 1.1 (b) 的判定细节

「停滞」不等于「空闲」。以下情况**不算**停滞：

- 会话状态为 `busy`（宿主 `~/.claude/sessions/*.json` 的 `status`）；
- 最近一次 `tool_use` 在 N 分钟内；
- 派生树任一节点仍有增益（见 `state-model.md` §5）；
- 状态判定为 `PRODUCING` 或 `EXPLORING`。

只有同时满足「`idle` 超过 N 分钟」+「最后一条 AI 消息是问句」+「状态为 `STALLED` 或冷启动 `EXPLORING`」才触发。

> ⚠ `STALLED` 实测命中率 0.018%，且从未出现在会话末态——**按本条件触发的接力，实际上不会发生**。
> 当前真正可用的是 [`needs` / `suggestedReply` 透传](../spec/state-model.md)（宿主自己写的等待内容）。
> 本节保留作为设计意图，不代表已实现的能力。

### 1.2 (c) 的判定细节

比较的是**归一化后的 Bash 签名**（`state-model.md` §3.3），不是原始命令字符串。因为重试通常会带不同参数：

```
npm test -- --grep "a"     ← 第一次
npm test -- --grep "b"     ← 第二次（参数不同，但签名相同）
npm test -- --grep "c"     ← 第三次 → 触发 (c)
```

## 2. 身份口径（Q3）

| 代号 | 口径 | 可行性 |
|---|---|---|
| (a) | 完全模仿用户历史语气，不暴露 AI 介入 | **不可达**。宿主跨会话投递一律标注来源（`From {发送方标题}`） |
| (b) | 中性口吻：「继续，请按原需求推进」 | 可达，**默认** |
| (c) | 明确标注「这是 OmniSight 代用户发送」 | 可达 |

选 (a) 时，Relay Agent 必须**拒绝**并说明原因，不得假装能做到。

## 3. 红线清单（Q4）

接力消息**不得**包含以下指令。Safety Agent 逐项检查：

| 红线 | 示例 |
|---|---|
| 不可逆删除 | `rm -rf`、`git reset --hard`、`DROP TABLE`、删除分支 |
| 向外发送 | 发邮件、发消息、发 PR 评论、`git push --force` 到共享分支 |
| 金钱交易 | 下单、支付、订阅 |
| 权限变更 | 改 IAM、改仓库权限、`chmod 777`、`sudo` |
| 凭据操作 | 读取 `.env`、`~/.ssh`、导出 token |

命中任一 → Safety Agent 判 `REJECT`，草稿不得提交给用户。

## 4. 草稿质量标准

### 4.1 必须带具体下一步

**反例**（不合格）：

```
你好，请继续。
```

```
上一步好像失败了，要不要再试试？
```

**正例**：

```
继续。上一条你停在 API 超时没有重试。
现在重跑 `npm run build`，如果仍然超时，改用 `npm run build -- --no-cache` 作为 fallback。
不要再来问我确认。
```

### 4.2 必须包含的三要素

| 要素 | 说明 |
|---|---|
| 停滞点定位 | 「你停在 X」，用事实而非猜测 |
| 具体下一步 | 可执行的命令或明确动作，不是「继续推进」 |
| 决策授权 | 「如果 A 不行就做 B，不用问我」——减少下一轮再停滞 |

### 4.3 长度约束

- 不超过 **5 行**；
- 不超过 **1 个**命令块；
- 不重复目标会话已有的上下文（它自己记得）。

## 5. 流程

```
1. scan-sessions.mjs 判定触发条件
2. 分两条路，取决于宿主是否已给出原料（见 §5.1）
3. 草稿 → 写入 tasks/runs/<id>/relay-draft-<n>.md
4. 派 safety Agent，输入：草稿全文 + 红线清单
5. safety 判 ACCEPT / REJECT
   - REJECT → 退回重写（最多 2 轮）
6. 通过 → 向用户展示草稿，由用户复制发送
7. 用户发送后，该会话在下一轮扫描中重新进入监控
```

**主线程不得自己写草稿**（规格 §2.1）。也不得自己判红线。

### 5.1 宿主已给的原料是一等输入

后台作业的 `~/.claude/jobs/<job-id>/state.json` 里，`blocked` 会话会带两个字段：

| 字段 | 内容 | 实测样例 |
|---|---|---|
| `needs` | 它在等什么 | 「要我现在就把用户回执交给你，还是你先看这四份报告？」 |
| `suggestedReply` | 宿主建议怎么回 | 「把回执发给我」 |

`scan-sessions.mjs` 已把两者透传到 JSON 与终端输出。**这改变了 relay 的工作性质**：

不是「从零生成一条消息」，而是**补全 + 结构化宿主已有的半成品**。

| 情况 | 草稿来源 | 谁来做 |
|---|---|---|
| `blocked` 且 `suggestedReply` 非空 | 直接用，必要时补「决策授权」 | TUI 按 `c` 即可，无需派 Agent |
| `blocked` 只有 `needs` | 据 `needs` 写回复 | Relay Agent |
| `STALLED` / `FAILED`（无 job 记录） | 从 transcript 重建停滞点 | Relay Agent |

**但 `suggestedReply` 不一定对。** 它只解决「当前这个问句」，不解决「为什么会停在这里」。两种典型误用：

1. **等 API 恢复的 `blocked` 没有 `suggestedReply`** —— 实测有一条 `needs` 是 `API unavailable — retry · API Error: 503 …`。这时正确动作是检查推理网关或换模型，不是催它重试。按 `c` 只能复制到「（目标会话正在等待：API unavailable…）」，需要人补一句真正的指令。
2. **`suggestedReply` 可能把会话引向错误方向** —— 它是宿主基于当前上下文猜的，不掌握用户的整体意图。要改方向就自己改，别盲信。

### 5.2 Relay Agent 的输入（派发时给这些）

```
- 目标会话的最后 N 条消息（不含 AI 推理文本）
- 原始需求摘要
- 停滞点（scan 输出的 reason 字段）
- needs 与 suggestedReply（若有，逐字给出，不要摘要）
- Q3 身份口径
```

## 6. `host` 模式（未来）

若宿主提供对**运行中**会话的、可控制来源标注的注入接口，可将 `relay.deliver` 从 `manual` 切到 `host`。

切换条件（三者同时满足）：

1. 接口可对运行中会话生效，不产生副本分叉；
2. 调用方可控制是否显示来源标注（否则 Q3(a) 永远不可达）；
3. 接口稳定（非 research preview）。

在此之前，`host` 模式的所有代码路径应当**不存在**，而不是存在但被禁用——避免「看起来支持其实不支持」。

## 7. 状态记录

`state.json` 的 relay 段：

```json
{
  "relay": {
    "deliver": "manual",
    "drafts": [
      { "n": 1, "target": "<session-id>", "created": "...", "safety": "ACCEPT", "sent": false }
    ]
  }
}
```

- `deliver` 只有 `manual` 一个合法值（当前）；
- `sent` 由用户确认后置 `true`，系统**不猜测**用户是否已发送；
- 若用户未确认，草稿保留，不重复生成第二份。
