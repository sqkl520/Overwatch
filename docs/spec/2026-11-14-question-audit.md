# 提问形态：哪几条能机械判定，哪几条不能

> **状态：已实现。** 判据在 `scripts/question-audit.mjs`，配置在 `overwatch.config.json`，
> 回归测试在 `scripts/question-audit.test.mjs`（69 条）。
> 本文与 [`2026-11-11-question-protocol.md`](2026-11-11-question-protocol.md) 的关系：
> 那份是**目标形态**（pack / answer / 风险四档，零行实现），本文是**当前能跑的那一小块**。
> 两者不冲突，本文不取代它；本文只回答一个问题——「问得准不准」判不了，那**判得了的是什么**。

---

## 0. 判据来源（用户原话，逐字）

> 问要问的准，要问的泛，这是一切未来持续性工作的基础

> 在问问题之前 AI 需要了解项目文件夹状态，环境状态，然后再去问，而不是写完文件再去问

> 有很多时候用户是不知道要实现这个功能还要考虑到什么什么的，也有很多时候 AI 不知道用户真正的意图

第 1 条里的「准」和「泛」是**判断**，不是**观测**。抓着它们去写判据，产出的一定是一个
看起来像指标、实际由语言模型编出来的数字——`state-model.md` §8 已经立过同一条规矩：
「外观像遥测、实际由语言模型编出的数字，比没有更糟」。

所以本文的写法是：**先把命题拆成可观测的形态，再逐个交代哪个能判、哪个不能。**

---

## 1. 四条判据的结论表

| # | 判据 | 结论 | 依据 |
|---|---|---|---|
| C1 | 问之前读过项目吗 | **可判定** | 两次 `tool_use` 在 transcript 里的先后顺序。纯结构事实，离线可复算 |
| C2 | 问了几次、每次几问 | **可判定**（附两个陷阱） | `AskUserQuestion` 调用计数；陷阱见 §2 |
| C3a | 会话内重复问同一件事 | **可判定** | 两次提问文本的字符二元组重合 ≥0.8 |
| C3b | 重复问「用户已经写过的信息」 | **不可判定** | 判据要拿问题去比开放集合（用户说过的全部内容）。关键词重叠只是启发式，见 §4 |
| C4a | 写了文件却整场零提问 | **可判定**（代理指标，但**不算缺陷**——见 §7.1） | 有 `Write`/`Edit` 调用且 `AskUserQuestion` 计数为 0 |
| C4b | 需求有歧义词却没问 | **不可判定** | 缺「本轮识别出的待决点清单」这个输入。没有它，「没问」与「没必要问」在数据上完全同形 |

**C4b 是「必须问」这条命题的核心，而它恰恰判不了。** 这不是实现遗漏，是输入缺失：
要判「该问而没问」，先得有一份「本轮识别出了哪些待决点」的声明，再对比「问了哪些」。
那份声明在 `2026-11-11-question-protocol.md` §5.2 里叫 `coverage.decisions_seen`，
**从未被实现，也不在 transcript 里**。本脚本不假装能从一个没有它的语料里算出来。

## 2. 两个不处理就会算错的实测陷阱

### 2.1 `tool_use` 重复行

宿主会把同一个 `tool_use` 写两行（一行带 `timestamp`、一行不带，重写留下）。
**本机语料实测 29,338 行是重复的。** 按行计数会把「问了几次」系统性算高：
同一批语料里原始 `AskUserQuestion` 块 273 次，按 `tool_use.id` 去重后是 **197** 次——虚高 39%。

规则：**所有调用计数一律按 `id` 去重**，`AskUserQuestion` 尤其不能例外。

### 2.2 `input.questions` 不总是数组

实测三种形态：数组（绝大多数）、JSON 字符串（能解析，等价于数组）、
**JSON 字符串但解析失败**（197 次去重调用里 6 次，来自「选项里带多行 `preview` 文本」的调用，
模型把引号写坏了）。

解析失败的那 6 次，问题数是**不知道**，不是 0。
规则：记 `questionsUnknownCalls`，且**不参与** `maxQuestions` 判定——不知道就不许判。

## 3. C1 的判据细节：为什么有「宽」「窄」两个口径

「读过项目」有四个层次，实测它们的结论不同：

| 口径 | 什么算 | 典型工具 |
|---|---|---|
| `any` | 读过任意一个文件**内容** | `Read` / `NotebookRead` / `cat` / `head` |
| `doc` | 读过项目文档 | `CLAUDE.md` / `README.md` / `GUIDE.md` |
| `code` | 读过源码或配置 | `*.mjs` / `*.java` / `*.yml` … |
| `structural` | 做过**结构性探索** | `Glob` / `Grep` / `LS` / `ls` / `find` / `git log` |
| `covered` | 按写前闸的判据读过 ≥ `minReads` 个**不同**文件 | 与 `pre-write-gate.mjs` 共用实现 |

`any` 与 `structural` 取最早的那个，得到**宽口径**；只用 `any` 得到**窄口径**。

**为什么必须有 `structural` 这一档（实测教训）。** 会话 `3f0f6fac`（PerfScope）的序列是：

```
Glob → Agent×6 → TaskOutput×2 → WebSearch×2 → Agent… → [第 20 次] AskUserQuestion
                                                       [第 32 次] 第一个 Read
```

按 `any` 判，它是「先问后读」。但它开场就 `Glob` 了整个项目目录——用户原话是
「了解项目**文件夹状态**、环境状态」，那正是 `Glob` 在做的事。
**漏了这一档，就会把「正确地先看目录再问」误判成缺陷。**

反过来，宽口径比窄口径松，所以脚本**两个都输出**（`verdict.narrow` / `verdict.broad`），
不替读者选。`verdict.effective` 取对会话有利的那个——判据的目的是抓「完全没看就开始问」，
不是抓「只看目录没读文件」。

### 3.1 `unattributable`：证据不在这一份文件里

同一个 `3f0f6fac` 还有一个更麻烦的性质：它提问前派了 6 个子 agent。
**子 agent 读了什么，主 transcript 里没有记录**（只有一个 `Agent` 调用）。

规则：提问前有过 `Agent` 派发、且本地找不到任何读取证据 → 判 `unattributable`，
**不计入违规**。「没读到」不等于「没有」——这是 `verify-claims.mjs` 的 UNKNOWN 纪律，
不许在这里退回去。实测 41 个提问会话里有 2 个落进这一档。

### 3.2 为什么不用时间戳

用去重后的**调用序号**，不用 `timestamp`。理由：重复行会让时间戳并列，
而序号是单调的。实测「同一批消息里既读又问」的并列情形 **0 个**——
真有并列时如实返回 `tie`，不猜。

## 4. C3b 的启发式：为什么它被明确标成「不是判据」

脚本算了一个 `docTokenOverlap`：把问题里的 ASCII 标识符（`DF-018` / `CLAUDE.md` / `--trace`）
与项目入口文档里的标识符求重叠。**它只进 `--json`，不进人类可读报告，也没有判定词。**

理由是本机实测：377 条可算的问题里，重叠 ≥0.5 的占 **13.0%**，但逐条看，
命中的绝大多数只是「问题里提到了项目里的名字」：

```
1.00 | agent,versions,jar,docs | 灾备 Agent 报了两条高优先级建议：① versions/ 的 7 个 JAR…
0.91 | claude,agents,ralph…    | `.claude/agents/*.md`、`ralph/prompt.md` …
0.50 | hilltop,manage          | 要不要支持 /hilltop manage <竞技场ID> 直接跳到…
```

这些**不是在问已知信息**，是在用项目的词汇问项目的事——那恰好是「问得准」的样子。
把这种当缺陷，会逼人删掉好问题。

中文刻意**不做分词**（不用字符二元组）：那会把「怎么处理」和「怎么弄」判成高度重合，
假阳性率高到指标失去意义。`classify-stop.mjs` 的研究已经记录过这一点。

C3a（会话内近似重复）是同一类噪声的**可判定**那一半：两次提问的文本都是问题，
比的是它们彼此，不是开放集合。实测全语料只有 **5 对** —— 说明「重复问」不是当前的主要毛病，
**如实给出，不夸大**。

## 5. 「先读再问」能不能变成事前拦截？

**不能拦「提问」这个动作本身。** 理由是硬约束，不是工程量：
`PreToolUse` 的 hook 只能返回 allow / deny / ask / defer 四种决策，
其中 `ask` 让**宿主权限系统**去问，问的是「允许这次工具调用吗」，而不是
「你想让项目做什么」——问题的内容由宿主决定，hook 无法注入。
（实测见 [`../research/2026-11-14-pretooluse-desktop-verification.md`](../research/2026-11-14-pretooluse-desktop-verification.md) §5.5。）

**能拦的是「把这次写入放行」。** 已实测可行的形态是：

| 动作 | 能不能拦 | 怎么拦 |
|---|---|---|
| 拦住首次 `Write` / `Edit` | ✅ | `permissionDecision: "deny"`，reason 里写清下一步 |
| 要求写之前读过项目 | ✅ | 同上：`readTranscriptReads()` 数不同文件数 |
| 要求写之前**问过** | ❌ 直接 | 见 §5.2 的间接形态 |
| 弹出真问题等人答 | ❌ | `ask` 只能问「允许这次调用吗」 |

### 5.2 唯一可行的间接形态：把「问过」变成可观测的标记

既然拦不住提问，就只能把「提问」这件事**降级成一个可被写前闸检查的前置动作**：
写前闸的 reason 已经在下这条指令（`pre-write-gate.mjs` 的 `reasonFor()` 第 2 步），
但那是**提示**，不是强制。

要做到强制，需要一个**提问凭据**：`AskUserQuestion` 的 `tool_result` 落进 transcript 之后，
把它（含 `tool_use.id`）记进写前闸的状态文件；写前闸在放行首次写入时检查该凭据。
这条路**没有实现**，因为它的先决条件是「提问必须在写之前发生」——
而本机实测 41 个提问会话里有 41 个满足这条（宽口径 39 + 判不了 2），
即它抓不到任何现存样本。**先有不违规的语料，再加这道闸，否则它只是在给未来的自己上锁。**
这条判断可以被推翻：若后续语料里出现「写完才问」，凭据闸就是该做的东西。

### 5.3 所以本文走的是事后审计

`question-audit.mjs` 把「没读就问」从「没人会发现」变成「一次可复现的报告」。
**这是提高可见度，不是消除。** 与 `state-model.md` §2.2 同一立场，
也是 ADR-0001 的直接后果。

## 6. 配置（S5「全部可配，包括不问」）

文件：**仓库根的 `overwatch.config.json`**（不是 `.claude/`）。三条理由：

1. **本项目是应用，不是插件。** 应用的配置在项目根，用户打开仓库第一屏就该看见按什么策略问。
2. `.claude/` 在本仓库已有 `settings.local.json`（gitignored）与 `.ow-*`（gitignored，含签名密钥）。
   再放一份**可发布**的默认策略进去，读者无法从路径判断它该不该提交。
3. 它必须可提交——默认策略本身是被审计对象。根目录没有歧义。

```json
{
  "version": 1,
  "ask": {
    "mode": "always",
    "maxQuestions": 5,
    "requireReadFirst": true,
    "minReads": 3
  },
  "agent": {
    "agentPrefix": "oversight-",
    "roster": ["oversight-planner", "oversight-executor", "oversight-acceptor"]
  }
}
```

| 键 | 合法值 | 默认 | 含义 |
|---|---|---|---|
| `ask.mode` | `always` / `never` / `auto` | `always` | `always`=每次都按判据审；`auto`=只审复杂会话（见 §6.1）；`never`=不问是策略（测模型质量），零提问不算缺陷 |
| `ask.maxQuestions` | 1..20 整数 | `5` | **单次调用**的上限，不是整场总额 |
| `ask.requireReadFirst` | 布尔 | `true` | 「问之前必须读过项目」可关，但默认开 |
| `ask.minReads` | 0..50 整数 | `3` | 「读过项目」要几个**不同**文件（与写前闸同口径） |
| `ask.minQuestionsBeforeWrite` | 0..20 整数 | `0` | 第一次写文件之前必须已经问过几个**去重后的**问题。`0` = 这条判据不启用。**执行侧是 `pre-write-gate.mjs`，不是本脚本**（本脚本只负责让它通过校验，见 §6.3） |
| `agent.roster` | 已知角色名数组 | planner+executor+acceptor | 启用哪些岗位，对应 [`../design/2026-11-14-agent-roster-policy.md`](../design/2026-11-14-agent-roster-policy.md) 的意图。**合法值来自 `.claude/agents/` 目录**，不是脚本里的字面量清单（`scripts/roles.mjs`） |
| `agent.agentPrefix` | 非空字符串，不含路径分隔符 | `oversight-` | `.claude/agents/*.md` 的 `name` 去掉这个前缀就是它的 **id**（＝任务图里的 `capability`）。frontmatter 写了 `id:` 时以 `id:` 为准。把本库当模板复用时改这一行即可，不必改代码（`DF-044`） |

### 6.1 校验：非法即报错，绝不静默回落

这条是本仓库付过学费的：`scan-sessions.mjs` 的 `--days abc` 曾静默回落成 7 天，
于是「只看 1 天」的调用实际扫了一周，输出里没有任何提示。配置比命令行参数更危险
（它不出现在命令行历史里，没人会重新看一遍），所以：

| 情形 | 错误码 | 为什么必须报错 |
|---|---|---|
| 未知键 | `unknown-key` | 拼错 `requirReadFirst` 会被当成默认值忽略——用户以为自己关了闸门，实际开着 |
| 类型不对 | `bad-type` / `bad-range` | `"maxQuestions": "5"` 拒绝。不做 `Number('')===0` 那类隐式转换 |
| `mode=never` 且 `requireReadFirst=true` | `contradiction` | 不问就不存在「问之前」。要关提问，请同时写 `false` |
| 未知角色名 / 空 roster / 重复角色 | `unknown-role` / `bad-roster` / `duplicate-role` | 打错一个名字等于静默少一个岗位 |
| 缺 `ask` 或 `agent` 段 | `missing-section` | 不写就等于不声明策略——请显式写出来 |
| 文件不存在 | （不报错） | 用内置默认。**这是唯一允许的回落** |

`agent.roster` 的角色名清单写死在脚本里，由测试断言「与 `.claude/agents/` 目录一致」——
两处不会漂。

### 6.2 `auto` 的两个阈值是实测的

`auto` 用「写过 ≥3 个不同文件」或「工具调用 ≥15 次」判复杂，来自本机 257 个会话的分布
（写过 ≥3 个文件的 147 个、调用 ≥15 次的 168 个、并集 168 个）——即 `auto` 会把约 65%
的会话判为「该问」。**这个比例是实测的，不是设计意图。**

不用「模型自评复杂度」：那是编出来的数字。

### 6.3 `ask.minQuestionsBeforeWrite`：校验在这里，执行在写前闸（2026-11-19）

§5.2 曾把「提问凭据闸」列为**未实现**，理由是「抓不到任何现存样本，先加闸只是给未来上锁」。
用户后来给了另一条理由，改变的是**这条闸要防什么**：

> 提前问主要服务的是长时间工作这个目的。一旦开头提示词给的模糊，
> 做出来的东西不是用户想要的就是白费力气了。

即它防的**不是**「写完才问」（那是 §5.2 说的那种，现存样本里已经有 41/41 合规），
而是「一句话都没问就开始写」。所以判据从「凭据 + 顺序」简化成**「数得清的问题个数」**，
落点是写前闸已有的 PreToolUse 拦截（那条路已经实测能拦）。

| 项 | 值 |
|---|---|
| 键 | `ask.minQuestionsBeforeWrite` |
| 缺省 | `0` = 这条判据**完全不存在**（现有用户行为逐字节不变，测试钉住的是「0 时连 transcript 都不读」） |
| 范围 | `0..20`，与执行侧的 `MAX_MIN_QUESTIONS` 逐字相同 |
| 环境变量 | `OW_ASK_MIN_QUESTIONS`，**优先于**配置文件（临时试跑） |
| 执行侧 | `scripts/pre-write-gate.mjs` 的 `decide()`「判据零」 |
| 口径 | `AskUserQuestion` + `ExitPlanMode`，按 `tool_use.id` 去重、按 `normalizeText()` 去重（**与写前闸 `readTranscriptActivity()` 同一份实现**：工具名判据是 `pre-write-gate.mjs` 的 `isAskToolName()`，去重键是 `question-form.mjs` 的 `normalizeText()`） |
| 去重 vs 总数 | 审计报**两个数**：`questionsKnown` = 总问题数（同一问题问两遍算两个，用于 `too-many-questions`）；`distinctQuestions` = 去重后个数（**与写前闸的放行判据同一口径**）。两处曾经都自称「同一口径」而数字不同 —— 因为它们本来在数不同的东西，现在各有名字 |
| 只判 | **第一次写**。transcript 里已有**真写成过**的写（有 `tool_result` 且非 error）→ 不再判（写到一半才拦会打断正在进行的活）。被闸门拒掉的写不算「写过」 |
| 叫停 | 与 Stop 闸共用同一族 PAUSE 文件：`stop-verify-hook.mjs` 的 `pausePathsFor()` / `pausedPathOf()`（`isPaused()` 是它的布尔投影）。**任一候选存在即暂停**；旧的 `%LOCALAPPDATA%/Overwatch/` 仍生效（`DF-041`，2026-11-21 修） |
| fail-open | transcript 读不到 / 配置是垃圾 / 越界 → 回落到 `0`（不拦） |
| 长会话 | 尾窗口（默认 1 MB）内没有提问时**向前回扫**，上限 `OW_PRE_WRITE_GATE_TRANSCRIPT_SCAN_BYTES`（默认 8 MB，实测 75 ms）；到上限仍不够 → 放行 + `scanTruncated:true`。**不许拿「没读到」当「没问过」** |
| 子 agent | 宿主给了 `agent_id` 的调用**不参与**这条判据（直接放行，日志 `questions:"subagent-exempt"`）。理由：多数 agent 的工具白名单里没有 `AskUserQuestion`，且它们的 `transcript_path` 指向主 transcript —— 拿主 transcript 的计数判子 agent 的第一次写，判的是别人的账 |

**校验与执行分两处，是刻意的**：校验器（`validateConfig()`）的职责是「用户有没有写对」，
执行侧（`minQuestionsBeforeWriteOf()`）的职责是「这条判据能不能工作」。
执行侧**不调** `validateConfig()` —— 否则「闸门能不能工作」取决于配置校验器的版本，
而校验器只要漏认一个键就会让整个配置变 `null`（连带 `launch` 的 roster 一起塌）。
两边都写死 `20` 由 `question-audit.test.mjs` 的四条用例对账。

**诚实边界**：判的是**次数**，不是「问得准不准」。问三个敷衍的问题照样能过闸 ——
这一条本文 §8 已经声明判不了。这条判据的价值在于它的失效方向：
读不到、解析不了、配置写错，一律**不拦**。

## 7. 本机实测（2026-11-14 19:10 快照）

复跑命令：

```bash
node scripts/question-audit.mjs --json
```

| 量 | 值 |
|---|---|
| 主 transcript | 561 份 |
| 有工具调用的会话 | 230 个（fork 副本合并掉 82 份） |

**读这张表要注意两件事**：

1. **fork 副本必须合并。** 本机 538 份主 transcript 里有 82 份是同一次对话的拷贝

### 7.1 为什么 `zero-ask` 报告但不阻塞

这是被实测逼出来的：230 个会话里 **153 个（67%）**「写了文件却整场零提问」。
若它算违规，本脚本**永远 exit 1**——一个永远红的门等于没有门，而且会让人开始忽略全部输出。

更根本的理由仓库里已经写过（`CLAUDE.md`）：
**「其余状态是描述，不是判据——不要用 `EXPLORING` / `PRODUCING` / `STALLED` 去驱动重跑或重拆解。」**
`zero-ask` 是同一个位置：它是**当前现实的描述**（这个仓库里 AI 大多数时候不问），
不是一件能「修好」的事。

所以退出码只由两条**二值、可复现**的判据决定：

| 违规码 | 阻塞 | 为什么 |
|---|---|---|
| `read-first-violation` | **是** | 读了没读是二值的，顺序可复算 |
| `too-many-questions` | **是** | 用户原话「一次问清，最多 5 个」 |
| `zero-ask` | 否（`--strict` 时升级） | 描述现状，不是缺陷 |

**看见 ≠ 判红。** `zero-ask` 仍然逐会话列出。

## 8. 已知局限（读之前先看这一节）

| 局限 | 后果 | 为什么本轮不修 |
|---|---|---|
| C4b（该问而没问）判不了 | 「必须问」的核心命题**没有判据** | 缺 `coverage.decisions_seen` 这个输入；补它要先实现 pack 的产出侧 |
| 子 agent 内的提问不计入 | 若提问发生在子 agent 里，主脚本看不到 | 主 transcript 不含子 agent 正文；读了也会撞 4 秒/会话的预算 |
| 同一批消息里既读又问判 `tie` | 不猜 | 序号相同，顺序不可知；本轮实测 0 例 |
| `unattributable` 不等于「读过」 | 它只是「判不了」，可能真的没读 | 子 agent transcript 缺失时无从核实 |
| C3b 只给线索不给判定 | 报告里没有「重复问」的数字 | 想避免 13% 的假阳性 |
| 提问凭据闸未实现 | 只能事后审计，不能事前强制 | 见 §5.2：抓不到任何现存样本，先加闸只是给未来上锁 |

## 9. 一页速查

```
能判的：问之前读没读（C1）· 问了几次几问（C2）· 会话内重复问（C3a）· 写文件却零提问（C4a）
判不了的：问得准不准 · 重复问已知信息（C3b）· 该问而没问（C4b）

不能拦的：提问这个动作本身（ask 只能问「允许这次调用吗」）
配置：overwatch.config.json，非法即报错，唯一回落是「文件不存在」
退出码：只有 read-first-violation / too-many-questions 阻塞；zero-ask 是描述，报告但不判红
```
