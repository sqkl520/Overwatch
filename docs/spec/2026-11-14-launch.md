# `overwatch launch` 的契约（现行规格）

> 本文件是 `node scripts/overwatch.mjs launch` **现行行为**的规格，不是设计推演。
> 与代码冲突时以代码为准，并就地修本文（见 `../README.md` 的「四类文档」表）。
>
> 实现：`scripts/launch.mjs`（唯一一份判据）· 入口：`scripts/overwatch.mjs`（只转发）
> 测试：`scripts/launch.test.mjs`（28 条）
>
> 依据（全部为本机实测，2026-11-14，不是估算）：
> - 交互式会话挂得上载荷：`--debug` 日志里 `Loaded 12 agents from plugin overwatch default directory`，
>   cwd 在仓库**之外**（排除项目布局自动加载的干扰）
> - 只挂载荷、不起推理：`claude --plugin-dir <dir> plugin details <name>` 报 `Agents (12)`，**不需要认证**
> - 认证是硬边界：未登录跑 `-p` 返回 `{"subtype":"success","is_error":true,"result":"Not logged in · Please run /login"}`，
>   退出码 1；另有一次网关配方下 **exit 0 且输出完全为空**
> - `auth status --json` 是一个**可用的判据**：未登录 `loggedIn:false` + 退出码 1；给 `ANTHROPIC_API_KEY` 后 `loggedIn:true` + 退出码 0

---

## 0. 一句话

`launch` 起一个**挂了 `.claude/` 载荷与两条 hook 的宿主会话**，
并且**自己判定成败** —— 因为宿主的失败语义不自洽（§2），直接转发它的退出码会说谎。

它是 `overwatch.mjs` 里**唯一真正执行**的子命令。其余子命令只路由，理由见
`2026-11-14-entry-point.md` §6（参数口径互相冲突，wrapper 必须替用户选一个口径，
而那个选择没有第二份判据测它）。`launch` 不属于那一类：**没有**任何原生命令能替你拼
`--plugin-dir` + `--settings`，而拼错了宿主**不会报错**。

## 1. 启动形态：哪几种存在，哪个能用（逐条实测）

| 形态 | 载荷挂得上？ | 要认证？ | 读得到输出？ | 本命令用它？ |
|---|---|---|---|---|
| **交互式**（无 `-p`） | **是**。`--debug` 日志 `Loaded 12 agents from plugin overwatch default directory`，且 cwd 在仓库外 | 是（起会话时） | **否**（直接写终端） | **是，默认** |
| **`-p` / `--print`** | 是（`--output-format stream-json` 的 init 事件里 `plugins:["overwatch"]`，`agents` 里有 12 个 `overwatch:oversight-*`） | 是 | 是 | 是（`--print`） |
| **`--bg` / `--background`** | 是 | 是 | 否（要 `claude logs <id>` 再捞） | **不**：它 exit 0 的意思是「已放到后台」，不是「跑成功了」，与本命令的判定纪律冲突 |
| **`claude --plugin-dir <dir> plugin details <name>`** | 是（`Agents (12)`） | **否** | 是 | **是**（`--verify`） |
| `claude --plugin-dir <dir> plugin list --json` | 是（`scope:"session"`, `enabled:true`） | 否 | 是 | 不：`details` 给的是**组件清单**，`list` 只给安装状态 |
| `claude --plugin-dir <dir> --help` | 不加载 | 否 | 是 | 不：它不证明载荷挂对了 |

**三个问题的直接回答：**

1. **`--plugin-dir` 在交互式会话里生效吗？** **生效。** 这是本节最重要的一条，
   因为它决定「应用」这个概念能不能成立。判据不是猜的：把 cwd 放到仓库**外面**
   （`%TEMP%` 下一个空目录）再起交互式会话，`--debug` 日志里仍然出现
   `--plugin-dir <repo>/.claude is one plugin: .claude-plugin at its top marks it`
   → `Loaded inline plugin from path: overwatch` → `Loaded 12 agents from plugin overwatch default directory`
   → `Loaded 1 skills from plugin overwatch default directory`。
   cwd 在仓库外这一点是关键：在仓库内的话，项目布局（`.claude/agents/`）也会被自动加载，
   同一个数字有两种来源，那样的证据不算证据。
2. **`--plugin-dir` + `--settings` + 位置参数能组合吗？** **能。**
   实测 `claude --plugin-dir <dir> --settings <file> -p "hi" --output-format stream-json`：
   init 事件里 `plugins:["overwatch"]`，之后才报认证失败。也就是说**载荷与 hooks 都在推理开始前
   就已挂好** —— 失败发生在挂载之后。`--settings` 也接受**内联 JSON 字符串**（实测一条
   `SessionStart` hook 在认证失败的情况下照样触发了）。
3. **有「只挂载荷、不起推理」的形态吗？** **有，而且它不需要认证。**
   `claude --plugin-dir <dir> plugin details <name>` 走的是 plugin 子命令，不建会话、
   不推理、不需要登录。本命令的 `--verify` 就是它。**这一条很重要**：它意味着
   「验证载荷挂对了」这件事在任何机器上都能做，包括本机（未登录）与 CI。

## 2. 为什么包装层必须自己判定：宿主的失败语义不自洽

本机实测的三种形态，**没有一种能靠退出码认出来**：

| 形态 | 宿主 stdout | `is_error` | `subtype` | 宿主退出码 | 朴素调用方的结论 |
|---|---|---|---|---|---|
| 未登录 | `Not logged in · Please run /login` | `true` | `success` | 1 | 看 subtype → **成功**（错） |
| 未登录（JSON） | `{"subtype":"success","is_error":true,…}` | `true` | `success` | 1 | 看 subtype → **成功**（错） |
| 网关配方 | **（空）** | 无 | 无 | **0** | 看退出码 → **成功**（错） |

第二、三行是本仓库已经吃过两次亏的形态。所以 `judgeHostRun()` 的判据**顺序是刻意的**：

| 顺序 | 判据 | `judge.kind` | 退出码 |
|---|---|---|---|
| 1 | 输出里有认证字样（`Not logged in` / `Please run /login` / `authentication_failed` / `Invalid API key` / `OAuth token expired`） | `auth` | **6** |
| 2 | stdout 是 JSON 且 `is_error === true` | `is-error-true` | **7** |
| 3 | 退出码 ≠ 0 | `host-exit` | **7** |
| 4 | 退出码 0 且 stdout 与 stderr **都空** | `silent-empty` | **7** |
| 5 | 以上都不满足 | `ok` | **0** |

**为什么认证放在最前**：三种毛病可能同时出现（第二行即是），而用户的下一步动作只有一个
（去登录）。拆成三个码只会让人以为要修三件事。

**为什么 `is_error` 排在退出码前**：`is_error:true` + `exit 0` 是可能的（假宿主 `liar-zero`
就是这一形态，测试钉住了它）。只看退出码会漏。

**为什么「空输出」必须单独判**：那不是「宿主什么都没说所以没问题」，是
「宿主什么都没做」。`exit 0` 在这台机器上被实测过出现在**什么都没跑**的时候。

## 3. 认证：为什么预检是交互式唯一的判据

交互式会话的 stdout/stderr 直接进终端（`stdio: 'inherit'`），**本命令读不到一个字节**。
所以事后无从判定「到底是什么失败了」。于是：

- **交互式**：起会话**之前**跑一次 `claude auth status --json`（本机实测约 1.9 秒）。
- `--print`：不预检。它有输出，`judgeHostRun()` 能直接判 —— 预检只会多花 2 秒。
- `--verify`：不预检。它不需要认证（§1 第 3 条）。

`authPreflight()` 是**三态**，不许合并：

| 态 | 判据 | 动作 |
|---|---|---|
| `ok` | `loggedIn === true` 且退出码 0 | 继续 |
| `blocked` | JSON 可读且 `loggedIn === false` | **不跑**，exit 6，打印可操作提示 |
| `inconclusive` | 跑不起来 / 输出不是可读 JSON / 没有 `loggedIn` 字段 | **继续**，但在 stderr 上说「预检没有结论」 |

**`inconclusive` 不许被当成 `blocked`。** 一个被 `--host-bin` 指过来的包装器或旧版本可能
根本没有 `auth` 子命令，那时退出码 1 说的是「不认识的命令」，不是「没登录」。
把它断成「没登录」就是编了一个它没说过的结论 —— 这正是本仓库最恨的那种缺陷。

**认证失败的提示必须是可操作的**，判据是「有能直接敲的命令」，三条 + 一条自检：
`claude auth login` / `ANTHROPIC_API_KEY=` / `ANTHROPIC_AUTH_TOKEN=` / `<宿主> auth status --json`。
其中最后一条的宿主前缀取自**实际要执行的那个**（`--host-bin` 指到 `.mjs` 时是 `node <路径>`），
不写死 `claude` —— 否则「可操作提示」会指向另一个程序的登录状态。

## 4. 挂上什么

### 4.1 载荷：`--plugin-dir <repo>/.claude`

同一个目录既是**项目布局**（cwd=repo 时宿主自动加载）也是**plugin 根**
（`.claude-plugin/plugin.json` 在那儿）。所以**不需要生成任何东西**，也就不存在
「生成物与源漂移」。布局校验走 `build-payload.mjs` 的 `verifyPluginRoot()` ——
本文件**不另写一份**「布局对不对」的判据。

### 4.2 hooks：`--settings <内容寻址的文件>`

| hook | 事件 | matcher | 默认行为 |
|---|---|---|---|
| `pre-write-gate.mjs` | `PreToolUse` | `Write\|Edit\|NotebookEdit\|Bash\|PowerShell` | **observe**：只记账、只放行 |
| `stop-verify-hook.mjs` | `Stop` | — | **observe**：只记账 |

两条默认都是观测模式，所以**默认挂上是安全的**。关掉的办法：`--no-hooks`，
或环境变量 `OVERWATCH_LAUNCH_HOOKS=off`。

**为什么开关不是 `overwatch.config.json` 的一个键**：那份配置的顶层键白名单由
`question-audit.mjs` 的 `validateConfig()` 硬校验（未知键直接报错），改它要动那个脚本
与它的 69 条测试。本文件不越界，如实写在 `--help` 里。

**为什么写文件而不是传内联 JSON**：内联 JSON 在 shell 里要转义（Windows 上尤其恶心），
而 `--dry-run` 的输出要能**直接复制粘贴**。落盘路径是**内容寻址**的
（`tasks/runs/launch/settings-<sha256 前 8 位>.json`）：同一份内容永远同一个文件，
不同内容（换平台 / 换仓库根 / `--no-hooks`）落在不同文件，互相不覆盖，
也不会出现「后一次启动把前一次正在跑的 settings 改了」的竞态。

**`--settings` 是合并，但只写 `hooks` 一个键**（两条实测）：

| 键类别 | `--settings` 与项目设置的关系 | 实测 |
|---|---|---|
| `hooks` | **叠加**。同一次会话里项目自己的 `SessionStart` 与 `--settings` 的都触发了（`fan.txt` 里 `project` 与 `app` 各一行） | 本项目 fixture 的 `.claude/settings.json` + `--settings` |
| 标量键（`model` / `permissions.defaultMode`） | **覆盖**。项目写 `defaultMode:"plan"`，挂上 `--settings` 后 `permissionMode` 变成别的值 | 另一 Agent 的红队报告 `2026-11-14-launch-redteam.md` |

所以本命令的 settings **只写 `hooks`** —— 不去碰用户的权限模式与模型。
「额外挂上两条 hook」是用户能预期的；「顺手改了你的权限模式」不是。

**命令里用绝对路径，不用 `${CLAUDE_PROJECT_DIR}`**：hook 进程里的那个变量指的是
**用户当前项目**，不是本仓库根（`templates/*.settings.json` 里那段注释是实测结论）。
`${CLAUDE_PLUGIN_ROOT}` 在 plugin 上下文有值、在 `--settings` 上下文是 `null`，
所以这条路也不通。

**为什么 hooks 不在 plugin 载荷里**（与 `build-payload.mjs` 的 `verifyPluginRoot()` 同一条）：
plugin 里的 hook 要写 `${CLAUDE_PLUGIN_ROOT}/scripts/x.mjs`，那要求载荷把脚本的
**整个 import 闭包**一起带走。实测踩过：只拷 `pre-write-gate.mjs`，它在
`claim-ledger.mjs` → `verify-claims.mjs` 那一跳断掉，hook 报 `ERR_MODULE_NOT_FOUND`，
而 `claude` 退出码**仍是 0** —— 静默失去介入能力。

## 5. roster：为什么只挂一部分做不到（如实说，不假装做了）

`overwatch.config.json` 的 `agent.roster` 只影响**调度**（谁该被派发），
不影响**挂载**（谁可见）。本命令**整目录挂载**，12 个角色全部可见。

**为什么不做筛选**（四条都实测过）：

1. `--plugin-dir` 的单位是**目录**。宿主的 CLI 里没有「只挂这个目录里的前三个 agent」的开关。
2. **`--agents <json>` 是加法不是减法。** 实测把 `{"oversight-planner":{"description":…,"prompt":…}}`
   传进去，init 事件的 `agents` 里 `oversight-planner`（裸名）与 `overwatch:oversight-*`
   12 个**同时存在** —— 它「再加一个」，不是「只要这些」。所以它顶不掉 roster 之外那些。
3. **筛一份目录出来挂技术上可行**：把 roster 里的 `.md` 复制到一个临时目录、配上
   `.claude-plugin/plugin.json`，实测 `plugin details` 会报 `Agents (3)`。**但那是第二份载荷** ——
   它与 `.claude/` 必然漂移，而漂移的那份没人测。本仓库的头号事故就是这个。
4. `.claude/skills/oversight/SKILL.md` 里引用了**全部 12 个**角色。筛掉一个，
   skill 就会派发到一个不存在的角色 —— 那比「全都可见」坏得多（后者只是多花 token）。

**还要说清一件事**：`agent.roster` 目前**没有一行代码在执行**。全仓读它的只有
`question-audit.mjs` 的 `validateConfig()`（校验形状）、`launch.mjs`（告知「它不影响挂载」）。
也就是说它是**声明**，不是**生效的策略**。§5 上表里那三种「常规开发 / 高风险 / 测模型质量」
的组合，今天没有任何东西按它派发 —— 派发发生在 SKILL.md 的流程里，而那份流程读的是角色清单
而不是 roster。这一条必须写在这里，否则读者会以为配置改了行为就变了。

所以本命令在**三处**都写明这件事，不只是某处注释里：

| 位置 | 形式 |
|---|---|
| `--dry-run` 人类输出 | 列出「没被 roster 启用的 N 个是：…」+ 为什么不做筛选 |
| `--dry-run --json` | `roster.applied = false` + `roster.note`（是**数据**，不是散文） |
| 台账 | `roster.applied = false` + `roster.note` —— 否则事后看台账会以为 roster 生效了 |

测试钉住这个现状：`launch.test.mjs` 的「roster 只影响调度、不影响挂载」一条断言
命令行里**只有一个** `--plugin-dir` 且指向整目录。哪天有人真做了筛选，这条会红，
届时必须同时改本节的那四条理由。

## 6. `--dry-run`：可测的锚点

`--dry-run` 的承诺是**三条**，每条都有测试：

| 承诺 | 判据 |
|---|---|
| 不起**任何**子进程 | 假宿主的 spawn 日志文件不存在（假宿主有写日志的代码，只是没被跑到） |
| 不写**任何**文件 | 注入的 `OVERWATCH_RUNS_DIR` 目录不存在或为空 |
| 打印的命令行**逐字可执行** | 命令行那一段里有 `--plugin-dir <repo>/.claude`，路径归一化后逐个字符相等 |

第三条的「逐字」还包含一个实现细节：`--host-bin` 指向 `.mjs`/`.js` 时，
真正 spawn 的是 `node <脚本>`（Windows 上直接 spawn `.mjs` 会 `spawn EFTYPE`）。
**打印的就是这一对**，不打印一个我们其实没执行的命令行 —— 否则 `--dry-run` 变成装饰品。

输出形态（本机真跑，路径已遮）：

```
overwatch launch · 这个会话会被挂上什么

  形态       interactive（无 -p：直接进 TUI，输出写终端）
  宿主       claude（PATH 上找到：<home>/.local/bin/claude.exe）
  工作目录   <cwd>
  载荷       <repo>/.claude · 12 个 agent · 1 个 skill · 名字 overwatch
             oversight-acceptor, oversight-critic, …, oversight-safety
  roster     oversight-planner, oversight-executor, oversight-acceptor —— 来自 overwatch.config.json
             ⚠ **只影响调度，不影响挂载**：--plugin-dir 的单位是目录，没有「只挂一部分」的开关。
               本次整目录挂载，12 个角色全部可见；没被 roster 启用的 9 个是：
               oversight-critic, oversight-probe, …（全列）
               （筛一份目录出来挂是可行的，但那会变成第二份载荷、与 .claude/ 漂移，
                 且 skill 里引用了全部角色，筛掉一个就会派发到不存在的角色。所以本命令不做。）
  hooks      2 条，默认都是 observe（只记账、不拦任何东西）：
               · pre-write-gate（PreToolUse：Write|Edit|NotebookEdit|Bash|PowerShell）→ scripts/pre-write-gate.mjs
               · stop-verify-hook（Stop）→ scripts/stop-verify-hook.mjs
  settings   <runs>/launch/settings-336225b3.json
             （内容寻址：同一份内容永远同一个文件名；真跑时才写，--dry-run 不写）
             这两条是**额外**挂上的：项目自己的 hooks 照旧生效（实测两边都会触发）。
             settings 里只写了 hooks 这一个键 —— 别的键（权限、模型）会覆盖你的项目设置。
  台账       <runs>/<日期>.jsonl（gitignored：只记摘要、退出码、判定，不记会话 ID）
  认证预检   起会话前跑 claude auth status --json（--dry-run 不跑）

要执行的命令行（逐字，可直接复制粘贴；本次没有执行任何东西）：
  claude --plugin-dir '<repo>/.claude' --settings '<runs>/launch/settings-336225b3.json'

交互式会话结束后，本命令只能报宿主的退出码 —— 它读不到终端上的输出，
所以台账里那一行会写 judge.kind="handover"（交出去了），而不是「成功」。

--settings 会写进 settings-336225b3.json 的内容（真跑时写入，这里只用来看）：
  { "hooks": { "PreToolUse": [...], "Stop": [...] } }
```

最后一段（settings 的全文）是刻意印的：用户要能看出「我的会话会被挂上**什么**」，
而不只是「挂了**两条** hooks」。

## 7. 非 TTY：不许自己改主意

宿主在非交互环境下**不报错**，它会静默切成 `--print` 然后等 stdin
（实测原话：`Input must be provided either through stdin or as a prompt argument when using --print`）。
一次「我以为在起交互式会话」变成「它在等 stdin」，是本命令必须**提前**说清的事。

所以：`stdin` 或 `stdout` 不是 TTY、又没给 `--dry-run` / `--print` / `--verify` / `--interactive`
时，**exit 5**，并列出四条可选路。**不**自动降级 —— 降级后的东西不是用户要的那个东西。

| 选项 | 用途 | 非 TTY 下可用？ |
|---|---|---|
| `--dry-run` | 只打印命令行 | 可用（测试与 CI 的主路） |
| `--print` | 非交互，能判定成败 | 可用 |
| `--verify` | 只验载荷 | 可用（不需要认证） |
| `--interactive` | 确实要在终端里跑 | 给出但会失败 —— 显式要求就照做，不辩解 |

## 8. 台账：`tasks/runs/launch/<日期>.jsonl`

gitignored（`tasks/runs/` 整棵树）。**每次真跑一行**（`--dry-run` 不写）。

| 字段 | 内容 |
|---|---|
| `at` / `ms` | ISO 时刻 / 本次耗时 |
| `mode` | `interactive` / `print` / `verify` |
| `hostBin` / `hostResolved` / `hostArgv` | 宿主与**完整 argv**（已遮路径） |
| `cwd` | 会话工作目录（已遮） |
| `payload` | `mounted` / `dir` / `name` / `agents` 数 / `skills` 数 / `layoutOk` |
| `roster` | `configured` / **`applied: false`** / `note`（为什么是 false） |
| `hooks` | `mounted` / `ids` / `settings` 路径 |
| `exitCode` | **本命令纠正过的**退出码，不是宿主的 |
| `judge` | `{ failed, kind, detail }` —— **「是否被判为失败」就是这一个字段** |
| `note` | 预检拦住时写「会话没有起来」 |

**不记完整会话 ID**（本命令拿不到，也不去要；测试断言台账里没有 UUID 形态的串）。
**不记本机绝对路径**：仓库根 → `<repo>`，家目录 → `<home>`，临时目录 → `<tmp>`，
其余盘符绝对路径 → `<abs>/<最后一段>`，分隔符统一成 `/`。

> ⚠ 这里踩过一个坑，写下来以免复发：遮罩最初只作用于 `--host-bin` 指向的路径，
> 而 `--host-bin` 是 `.mjs` 时 `hostArgv[0]` 是 `process.execPath` —— 一条盘符绝对路径
> 就这样漏进了台账。是测试里那条「台账不含盘符路径」抓到的。

## 9. 退出码（launch 专有 6 / 7）

| 码 | 含义 | 典型场景 |
|---|---|---|
| 0 | 会话正常结束 / `--verify` 通过 / `--dry-run` 打印完成 | |
| 1 | `launch.mjs` **自己**出了意外（bug，不是环境问题） | 抛异常；stderr 会写明「这是 bug」 |
| 5 | 用法错误 | 未知参数 / 参数缺值 / 非 TTY 下没挑运行方式 / `--print` 与 `--verify` 同时给 |
| **6** | **宿主没有被认证** —— 会话没起来（预检拦住），或宿主自己说了认证失败 | 未登录 |
| **7** | **宿主失败** | 退出码非 0 / `is_error:true` / **exit 0 但输出为空** / 超时 / `--verify` 没挂全 / 宿主起不来 |

**为什么 6 与 7 要分开**：用户的下一步动作不同。6 是「去登录」，7 是「去看宿主的输出」。
把两者并成一个码，等于逼人去读长文才知道该做什么。

## 10. 已知边界（不打算做）

| 不做 | 理由 |
|---|---|
| 用 `--bg` 起会话 | 它 exit 0 的意思是「已放到后台」，不是「跑成功了」。本命令的判定纪律不接受一个「不知道」被包装成 0 |
| 按 roster 筛载荷 | §5 三条理由，核心是「第二份载荷必然漂移」 |
| 判定**交互式会话的内容**成败 | 输出直接进终端，本命令读不到。`judge.kind = "handover"` 如实说「交出去了」，不说「成功」 |
| 往 `overwatch.config.json` 加 hooks 开关 | 那份配置有硬校验的键白名单（`question-audit.mjs` 的 69 条测试守着）。本文件用环境变量 + `--no-hooks`，不越界 |
| 在 hook 里用 `${CLAUDE_PROJECT_DIR}` | 那个变量指的是**用户当前项目**。用它会把闸门指错仓库 |
| 等 `claude auth login` 完成后自动重试 | 那是一条交互式登录流程。本命令只负责**说清该跑什么**，不替用户跑 |
