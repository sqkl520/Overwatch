## 一、决定一：改主指标是不是在挑选对自己有利的口径？

### 1.1 先复算已知数（不许引用不核）

`node scripts/measure-execution-phase.mjs --days 0 --json`（461 份落盘 / 21.3 秒）给出
`A n=14 / B n=38 / C n=143`。我从 `perSession` 逐会话重算，**与报告一致**：

| 报告原话 | 我复算 | 一致？ |
|---|---|---|
| A 一次性完成率 0.0% | 0/14 | ✅ |
| C 一次性完成率 31.4% | 46/143 = 32.2% | 数漂（语料长了），方向一致 |
| A 中断均值 14.4 vs B 30.5 | 14.36 vs 31.89 | ✅ |
| A 的活小 6.6 倍（p50 工具） | 154 vs 1069.5 = **6.94 倍** | ✅ 量级一致 |
| 每 100 工具：A 3.29 vs B 1.94 | 5.92 vs 2.98（**A 更差**） | ✅ 方向一致（值随语料变） |
| 门槛 ≥400：A 38.5 vs B 31.4 | A 45.0 vs B 35.0（**A 反超**） | ✅ 方向一致 |
| 体量 1:1 匹配 3 胜 3 负 | 去重后 0 胜 2 负 3 平 | ⚠️ **去重后 A 不再有一胜** |

**注意最后一行**：报告写「3 胜 3 负」，那是**去重前 A=14** 的口径。用第二层去重后的 A=7
重算，匹配对变成 **A 胜 0 / B 胜 2 / 平 3**。也就是说，去重把唯一支持 A 的三对「胜」抹掉了两对。

### 1.2 八种口径，一张表

我把能想到的合理口径都算了（去重后 A=7 / B=34；置换检验 20000 次，固定种子 20261114）：

| # | 口径 | A | B | 谁更好 | p |
|---|---|---|---|---|---|
| 1 | 执行期中断**次数**（原始，n=14/38） | 14.36 | 31.89 | **A** | 0.007 |
| 2 | 每 100 工具中断 | 5.92 | 2.98 | **A 更差** | 0.032 |
| 3 | 每小时间断 | 0.336 | 0.211 | **A 更差** | 0.064 |
| 4 | 每会话**纠正**数（新指标，n=7/34） | 0.286 | 0.324 | A（噪声） | 1.00 |
| 5 | 纠正**密度**/100 工具 | 0.0278 | 0.0258 | **A 更差** | 0.977 |
| 6 | 纠正率/中断 | 0.890% | 0.589% | **A 更差** | 0.595 |
| 7 | 无纠正会话占比 | 71.4% | 82.4% | **A 更差** | 0.608 |
| 8 | 自撤销/100 工具 | 1.266 | 0.480 | **A 更差** | 0.052 |

**读法**：

- 8 种口径里 **6 种 A 更差**，且都发生在**控制体量之后**（每百工具、每小时、密度）。
- 唯二「A 更好」的两行：第 1 行是**没控制体量**的原始次数（A 的活小 6.9 倍，这一行测的是体量）；
  第 4 行是**纯噪声**（p=1.00，A 组 7 个会话里总共只有 2 次纠正）。
- **用户要改的那个「新主指标」（纠正密度）恰好就是第 5、6、8 行——A 在它上面更差。**

### 1.3 「改指标」想兑现的是什么？兑现不了

用户决定的意图是：把「提问」从成本里拿掉，这样「A 不更差」就成立。
我按这个意图算了两遍：

**A vs B（新指标）**：每会话纠正 0.286 vs 0.324（差 0.04，p=1.00）；纠正密度 0.0278 vs 0.0258（A 更差）。
**A vs C（新指标）**：

| 口径 | A | C（从不问） | 谁更好 |
|---|---|---|---|
| 每会话纠正 | 0.286 | 0.056 | **A 差 5 倍** |
| 纠正密度/100 工具 | 0.0278 | 0.0040 | **A 差 7 倍** |
| 无纠正会话占比 | 71.4% | 96.6% | **A 差** |

**这是最狠的一张表**：把提问剔除出成本之后，「开工前问」组（A）的纠正仍然比「从不问」组（C）
**多 5–7 倍**。改指标不但没让 A 不更差，反而在 A vs C 这个最干净的口径上把差距拉得更大。

### 1.4 核心问题：这是不是同义反复？

**部分是同义反复，而且同义反复的是「成本」那一半，不是「收益」那一半。**

新指标把成本定义成「只有纠正算成本」，把「开工前的一切对话」排除。A 组的定义性行为
（开工前问）因此**按定义不可能出现在成本侧**。在这一半上，「A 不更差」是同义反复——
你从成本里删掉了 A 的招牌动作，它当然不会以成本的形式出现。

但「收益」那一半（问准了 → 纠正更少）**不是**同义反复，它是可测的，而测出来的结果是
**A 的纠正更多**（§1.3）。所以改指标买到的不是证据，是**把价值选择伪装成数据背书**：

- 如果「必须问」是**价值选择**（我认为它是，且合理），正确写法是
  「这条不接受指标裁决」——一句话，不需要改任何脚本。
- 改主指标的做法，等于给一个不可裁决的价值选择**配一个精心挑选、仍然不支持的指标**。
  这比不改更糟：它制造了「我们有数据支持」的错觉，而那条数据（§1.2 第 5/6/8 行）恰恰反对它。

### 1.5 样本够吗？不够，而且我能算出不够到什么程度

纠正事件：A 组 2 次、B 组 11 次（全语料 1814 次中断里 18 次纠正）。
泊松精确 95% 置信区间（每会话纠正率）：

```
A  k=2  n=7   rate=0.286  95%CI [0.035, 1.032]
B  k=11 n=34  rate=0.324  95%CI [0.162, 0.579]
```

**A 的置信区间完全包住 B 的**。这批语料**在数学上不可能**区分「A 与 B 的纠正率不同」，
无论用哪种口径。所以「改指标让 A 不更差」即使成立，也只是噪声里的一个点，撑不起产品定义。

### 1.6 一条对施工方的具体更正（红队职责）

施工中的 `measure-ask-vs-tell.mjs` 文件头 §旧口径③ 声称：
「旧口径看不见 `ExitPlanMode`，于是把用计划批准求过一次确认的会话记成从不提问」。

**这个前提在方向上对，在量级上错得很离谱，必须钉死**：

- 我用正则 `"name":"ExitPlanMode"` 扫全语料，得到 **906 次 / 189 会话**——看着像个大缺口。
- 但**这 906 次是假的**：其中绝大多数命中在 `type:"attachment"` 的系统提示快照里，
  不是真的 `tool_use`。按 `b.type === 'tool_use' && b.name === 'ExitPlanMode'` 重算：
  **真的只有 16 次，分布在 8 个会话**。
- 落到「只有计划批准、没有 AskUserQuestion」因而会被从 C 组重新归类的会话：
  **2 个**（`a122e6cc`、`dc11a911`），占 C 组 143 个的 **1.4%**。

**结论**：把 `ExitPlanMode` 补进提问判据是对的（机制诚实），但它救不回 C 组，也改变不了
§1.3 的任何一个数。**谁要是拿「906 次」当论据，那是我一开始犯的同一个错——正则命中 ≠ 工具调用。**

> 复算：`node scripts/measure-execution-phase.mjs --days 0 --json`；`ExitPlanMode` 真调用

## 二、决定二：「应用不是插件」在技术上成立吗？

### 2.1 逐条复验三个「不行」（历史上有好几个「不行」被推翻过，所以必须重测）

| 结论 | 今天的实测 | 判定 |
|---|---|---|
| `claude -p` 本机撞认证闸 | 直接用：`claude -p "…"` → **exit 1，`Not logged in · Please run /login`** | ✅ 成立 |
| | 剥掉宿主两个受管变量 + 给网关令牌：**exit 0，但 `--output-format json` 的 `result` 是空串**，`--output-format text` 也是空 | ⚠️ **能启动但静默返回空**——比「撞闸」更糟，是「假装成功」 |
| ACP 撞 `Authentication required` | `acpx claude exec "…"` → `initialize` OK、`session/new` OK、**`session/prompt` 前报 `RUNTIME: Authentication required`** | ✅ 成立（2026-11-14 复现） |
| 会话注入是平台安全边界 | 未重测（超出本轮范围，上游报告已多次确认） | 未验证（沿用） |

### 2.2 但 `claude mcp serve` 是真的能推理——这条买到了「应用」的全部增量

```
initialize            → OK（serverInfo claude/tengu 2.1.289）
tools/list            → 23 个工具
tools/call Read       → 真读文件，返回 README 前 3 行（非推理类工具，证明通道通）
tools/call Agent("Say PONG")  → 真推理："PONG"，resolvedModel claude-opus-5-5，3008 ms
tools/call Agent(跑 shell)    → 子 agent 真跑出 SHELL_OK_12345（**推翻旧结论「子 agent 跑不了 shell」**）
```

**关键条件**：上面 `tools/call Agent` 成功的每一次，我都**剥掉了宿主两个受管变量并注入了网关令牌**。
不剥不注：`tools/call Agent` → `Agent terminated early due to an API error: Not logged in`。

而且那个 shell 用例暴露了权限闸：一个**故意 obfuscate** 的命令（`String.fromCharCode(...)` 拼 `crypto`）
被权限系统拦下，子 agent 如实报告「被拦，我没绕过」。**所以「能跑 shell」是有权限闸的能跑，不是无条件的能跑。**

### 2.3 「应用」的真实边界（一句话 + 证据等级）

> **一句话**：它是一个**能自己发起推理、但不能脱离本机第三方网关、也不能把配置送到用户项目**的观测器——
> 「应用」这个名字只有在「有一个可编程推理入口（`claude mcp serve`）」这一点上买到了真能力；
> 它到推理的唯一通路是 `127.0.0.1:15721` 这个**第三方（cc-switch）代理 + 一份本机租约令牌**，
> 换台机器就没有。

证据等级，逐项：

| 断言 | 等级 | 依据 |
|---|---|---|
| `claude mcp serve` 有 23 工具、`initialize` 通 | **T2** | 本机实跑，两条 JSON-RPC 响应原文 |
| `tools/call Agent` 能产出真推理 | **T2** | 本机实跑，`PONG` + `model: claude-opus-5-5` |
| 子 agent 能跑 shell（有权限闸） | **T2** | 本机实跑 `SHELL_OK_12345`；obfuscate 命令被拦 |
| 该通道**跨机器**可用 | **T0** | 未在第二台机器测；令牌在 `%LOCALAPPDATA%/Claude-3p/host-creds-*.json`，是**租约**（我读到 `expiresAt`、`pid`、`procStart`），指向**第三方** `cc-switch.exe`（PID 17088，非官方桌面版） |
| 该通道是**产品可依赖**接口 | **T0/T1** | 网关是第三方软件；令牌过期、cc-switch 退出即失效。没有任何证据说它能装进别人的机器 |

**所以「应用不是插件」技术上成立的那一半**：应用确实可以自己发起推理（不用人点）。
**不成立的那一半**：如果「应用」意味着「能独立于宿主配置层运行」，那它不成立——
它读的是宿主写的 transcript、连的是宿主/第三方写的网关，**agents 与 skill 仍然必须装进用户的项目才能到达用户**。
换句话说：**「应用」这个名号没有替代 ADR-0001 那句「`clone 即用` 优先于 `可安装`」的取舍，
它只是在这句取舍旁边多开了一个「自己会推理」的口子。**

### 2.4 一个必须写下来的对比：`claude -p` 的「成功」是空字符串

我跑通了 `claude -p`（剥变量 + 给令牌，exit 0，耗时 ~12 秒），但 `result` 是 `""`。
这与仓库索引里那条「静默失败 exit 0 + 空 stdout」**完全一致**。
**一个返回 exit 0 却说不出话的通道，比一个明确报错的通道更危险**——任何「应用自己发起推理」的
设计若建在它上面，会在生产里静默产出空结果。这不是我推的，是今天测出来的。

> 复算：`claude -p "…"`（原样）、`env -u CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST -u CLAUDE_CODE_HOST_AUTH_ENV_VAR
> -u ANTHROPIC_AUTH_TOKEN ANTHROPIC_BASE_URL=<本机网关>/claude-desktop ANTHROPIC_AUTH_TOKEN=<租约令牌> claude -p "…"`、
> `printf '<initialize>\n<tools/call Agent>' | claude mcp serve`、`acpx claude exec "…"`。

## 三、决定三：「都做」是不是在同时挖三个坑？

### 3.1 现场证据：硬门此刻就是红的，而且是并行造成的

写作本文时，工作树里有并行 Agent 的产物（`git status`）：`overwatch.mjs`、`render-plan.mjs`、
`question-audit.mjs`、`measure-ask-vs-tell.mjs`、改动中的 `verify-claims.mjs`。此刻跑硬门：

```
✗ 4 项违规：
  [README.md]        回归测试数写的是 1276，源码实测 1387
  [CLAUDE.md]        回归测试数写的是 1276，源码实测 1387
  [docs/GUIDE.md]    回归测试数写的是 1276，源码实测 1387
  [.github/workflows/validate.yml] 回归测试数写的是 1276，源码实测 1387
```

实测数在 40 分钟内走了 **1326 → 1338 → 1387**，而四份声明还停在 1276。
**这不是某个 Agent 的失误，是「同一个数字写在四个文件、N 个 Agent 各自加测试」这个结构的必然结果。**

### 3.2 三个共享面，每一个都会打架

| 共享面 | 谁在用 | 并行下的表现 |
|---|---|---|
| `scripts/check-structure.mjs` 的 `PROBE_ARGS` / `REGISTERED` | **每个加脚本的 Agent 都必须改它** | 六个 Agent 改同一个文件；后提交者覆盖先提交者的登记，先提交者的新函数立刻变「未登记」告警。现在 `render-plan.mjs` 已有 **9 个导出未登记** |
| 测试数「同一个数字 × 四份文件」 | `checkTestCount()` 数源码对账四份 | 任一 Agent 的本地 1387 在另一个提交后即过期；**每个 Agent 都会把别人数进去的测试数改回去** |
| `docs/CHANGELOG.md` 的 git 边界 | `checkChangelog()` 只看「最近一次改 CHANGELOG 的提交」之前 | 甲提交源码、乙提交 CHANGELOG → 边界移到乙，**甲的源码提交立刻欠账变红**，而甲根本不知道乙提交了 CHANGELOG |

### 3.3 更根本的：三件事不独立，且已经出了两个集成故障

**故障一（跨 Agent 契约不匹配，当场可复现）**：施工中的 `measure-ask-vs-tell.mjs` **一跑就崩**：

```
TypeError: Cannot read properties of undefined (reading 'length')
  at dedupeResumeForks (measure-intervention-cost.mjs:237)
  at run (measure-ask-vs-tell.mjs:608)
```

根因：`dedupeResumeForks` 的入参契约是 `item.seq: Uint32Array`（见其 JSDoc 第 210 行），
但 `measure-ask-vs-tell` 传给它的 `rows` 由 `sessionRow()` 生成，**那条路径没有 `seq` 字段**。
这是决定一的核心施工件，**交付时是坏的**。

**故障二（孤儿产物）**：`render-plan.mjs` 已经能跑（我实跑输出 8 行 plan），但它的消费者是**零**：
`grep -rn render-plan scripts/ .claude/ docs/` 只命中它自己的测试和 `overwatch.mjs` 里一句
「还没做」。硬门实跑 `node scripts/overwatch.mjs plan` → `overwatch plan · 未实现`。
它的数据源 `task-graph.json` 在 `tasks/runs/` 7 个目录里只有 **2 份**。
**它渲染一屏没人看的界面，数据几乎不存在。**

**doctor 会不会变空壳？** 不会——但这正是问题：**当前的 `overwatch doctor` 完全不显示 plan**
（`node scripts/overwatch.mjs` 输出里 `grep -ci plan` = 0）。所以「doctor 依赖 plan」这个风险
被「doctor 根本不理 plan」绕过了，代价是 plan 渲染器成了孤儿。

### 3.4 判断：同时做三件 vs 按依赖排序做三件

**按依赖排序更可能全部做成。依据不是道理，是本仓库正在发生的这三件事：**

1. 硬门此刻红着，且红的原因是并行（3.1）；
2. 决定一的核心件交付即崩（3.3 故障一）；
3. 决定一的 plan 件交付即孤儿（3.3 故障二）。

**排序应该是**：先 `verify-claims` 假阳性（它是**缺陷修复**，独立、可先合、不碰任何新文件）→
再 `doctor`（入口，它是唯一有真实消费者的，638 ms 实跑输出完整）→ 最后 `plan`（它依赖
`task-graph.json` 存在，而全仓只有 2 份；先做它等于先做最没有使用场景的一件）。
**「都做」把最没有使用场景的 plan 和最紧急的 verify-claims 放进了同一批并发提交，
结果是两者都卡在同一个硬门上。**

| **`render-plan.mjs`（决定三的 plan 渲染）** | **高** | 零消费者（`overwatch plan` 仍打印「未实现」），数据源全仓 2 份（3.3 故障二）。它能跑，但没人看、没数据。**要么接进 doctor/TUI 才活，要么两周后作为「孤儿脚本」被清理。** |
| **`verify-claims.mjs` 的 `projectScriptVerification` 改动** | **低** | 它是**缺陷修复**（`VERIFY_CMD_RE` 不认 `node scripts/lint.cjs`），有具体反例、独立、不依赖别的 Agent。**这是六件里最不容易白做的一件。** |

**结论**：六件里最可能白做的是**决定一的指标测量（ask-vs-tell / question-audit）**与
**决定三的 plan 渲染**。前者白做是因为结论站不住，后者白做是因为没有消费者。

## 五、如果我错了：什么可观测证据会推翻上面任何一条

每一条都写成可观测的，不写「如果数据显示」。

**对决定一（我说「改指标兑现不了」）**：

1. 修好 `measure-ask-vs-tell.mjs` 后，在 **A 组 n ≥ 30** 的语料上跑出：
   **A 的纠正密度 95% 置信区间上界 < B 的下界** → 我说「样本撑不起」错。
2. 有一个**在测量前登记**（写进 `docs/spec`）的口径，在**体量匹配 ≥ 15 对**上 A 胜且 `p < 0.01` → 我说「8 种口径都不支持」错。
3. 出现一个「问了对的问题」的 oracle（比如用户事后标注「这次问得值」），且 A 组的 oracle 通过率显著高于 B → 我说「没有收益证据」错。

6. `claude -p` 在不剥宿主变量的**普通 shell** 里返回非空 `result` → 我说「`claude -p` 撞认证闸 / 返回空」错。

**对决定三（我说「并行必然互相踩」）**：

   （四份测试数在每次提交时都一致，CHANGELOG 边界从不红）→ 我说「结构性必然红」错。
8. `render-plan.mjs` 在两周内获得一个**真实消费者**（`overwatch`/TUI/SKILL 三处之一真的调用它），

9. 修好 `measure-ask-vs-tell.mjs` 的 `seq` 契约后它产出的结果与我 §1.2 的表**方向相反** → 我说「决定一白做」错。
