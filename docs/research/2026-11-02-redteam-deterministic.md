R4 的大方向（「停没停」结构可判、「干完没有」不能只靠读最后一句）**成立**。
但支撑它的三个关键数字，**一个是方法错误、一个是定性错误、一个是同义反复**。

| R4 的结论 | 复核判定 | 决定性证据 |
|---|---|---|

## 二、攻击 A：那 45.9% 真的需要「语义」吗

### 2.1 先复现分母

R4 的 115 来自 `gap.mjs`：`STOPPED_SILENT ∧ WAIT_RE`。我原样复现，得到 **115**（与 R4 完全一致）；再跑一次得到 116，差异来自扫描期间语料仍在增长：

```
silentStops 605-610 | matched 115-116 | endsWithQuestion 0 | 含问号(全文) 32-33
unique sessions 72        ← 115 次命中只来自 72 个会话，最高重复 7 次（48 个会话只出现 1 次）
```

### 2.2 极小的词组表够不够

我把 R4 的 18 词组表缩到 **8 个词**（`要不要 / 等你 / 你定 / 说一声 / 你选 / 需要你 / 告诉我 / 你回`），并**只在尾部 300 字内匹配**（R4 是全文匹配）。对 72 个会话逐条人工标注「结尾是否真的把控制权交还给人」（52 正 / 20 负）：

| 判据 | 命中 | 精度 | 召回 |
|---|---|---|---|
| R4 WAIT_RE（全文） | 72 | **72.2%** | 100% |
| R4 WAIT_RE（仅尾部 300 字） | 55 | **87.3%** | 92.3% |
| **MINI8（仅尾部 300 字）** | 54 | **87.0%** | **90.4%** |
| MINI5（仅尾部 300 字） | 39 | **92.3%** | 69.2% |

误报的成因很干净：**命中词距结尾的平均距离，真样本 116 字，假样本 527 字**。R4 全文匹配把正文中段的「要不要」当成了结尾的交还。

于是「45.9% 需要语义理解」被削弱成：**87% 精度 / 90% 召回，用 8 个固定词，零模型。**

### 2.3 真原句（R4 说需要语义的那一类，全部可被词组表抓到）

```
要不要我把这个守卫改成「只比对本轮有改动的源文件」？
测完回"**通过**"→ 归档 vX.Y.Z、升 vX.Y.(Z+1)
我等你反馈开下一轮。
要不要我现在就做"pom 版本自动注入 plugin.yml"这个根治项？
说一声我就派 planner 拆任务图。
你回一句，我就一次性写完，不用返工。
```

这些句子的共同点是：**都带一个显式的交还词**。R4 自己也在第七节写了「实测形态是『要不要/等你/测完回/你定/说一声』」——它已经找到了答案，却仍把它归为「需要语义」。

## 三、攻击 B：43.5% 是「核对」还是「执行」

### 3.1 R4 的定性错在哪

R4 把 U 类（37 条）描述为「语义也难判」。但它自己给的例子说明了真实性质：

> `N/N 测试通过` —— 测试真的跑了吗？跑的是这一版吗？

这不是阅读理解题，是**一条命令 + 一个退出码 + 一个时间序**。把它归为「需要 AI」是把「需要工具」误记成「需要模型」。

### 3.2 实测：断言能不能被结构化证据配对

我对全部终端静默停机做了两件事：识别断言族，然后在 transcript 里找「一次成功的、命令含测试运行器的 Bash 调用，且发生在最后一次文件编辑之后」。

93 个终端静默停机里，**46 个（49.5%）**含可机器核对的断言族：

```
build 23 | test-count 23 | file-count 18 | artifact-hash 10
commit 6 | todos 6 | push-remote 3 | pr-ci 3 | runtime-probe 3
```

对其中 23 个「声称测试完成」的会话做全文件配对：

| 证据状态 | 会话数 |
|---|---|
| 末次编辑后有成功测试 | **5** |
| 只有历史成功（编辑后没重跑） | 3 |
| 只有失败证据 | 0 |
| **完全没有测试调用** | **15** |

15 个「无任何测试调用」的会话，我逐个查了它们的 `subagents/` 目录：**全部为 0 个子 agent**，证据不在别处。这些断言是真的不可核——但不可核的原因是「AI 没跑测试就宣称通过」，不是「我们读不懂它」。

**这就是 R4 真正抓到的东西，但它给错了名字。** 正确的名字是：**「断言 vs 证据」是可确定性核对的，核对不了的恰好是最该告警的（无证据的完成声明）。**

### 3.3 反例：本可以核对的，R4 说「日志里没有远端状态」

R4 写：`全部链接已校验有效，N 个文件都已同步到远端` ——「日志里没有远端状态」。
全库检索这句：只在 **1 个会话**（`<session-N>`）里出现，该会话在尾部**确实**有 `git push`/`gh` 调用记录。也就是说，「远端状态」不是不可得，是 R4 只看了尾部 512KB 的文本、没做工具调用配对。

## 四、攻击 C：100% 不带问号，是同义反复

### 4.1 这条最硬，也是最假的一条

`stop-signals.mjs` 的判定顺序写死为：

```js
if (signals.textQuestion.hit) return { kind: 'QUESTION_TEXT', ... };
return { kind: 'STOPPED_SILENT', ... };
```

所以 `STOPPED_SILENT` **按定义**满足 `endsWithQuestion === false`。再在 `STOPPED_SILENT` 里统计 `endsWithQuestion === false` 的比例，恒等于 100%。实测：

```
QUESTION_TEXT 停机: 37-38     ← endsWithQuestion 的真实命中，不是 0
STOPPED_SILENT 停机: 598-610
其中 endsWithQuestion === true: 0   ← 由判定顺序决定，必然为 0
```

**全库 `endsWithQuestion` 命中 37–38 次，不是 0 次。** R4 的 0 是「在已经把它排除掉的子集里数它」。

### 4.2 那 115 条真的不带问号吗

不是。同一个 115–116 条样本里（窗口随语料漂移）：

```
含问号（全文）:            32-33  (27.6%)
问号出现在尾部 300 字内:    25-26
问号后允许 200 字内容:      19-20
```

`endsWithQuestion` 要求「问号之后没有实质内容」，这在真实语料里几乎不成立——AI 的典型写法是**问句后面跟一段说明**：

```
要不要我把这个守卫改成「只比对本轮有改动的源文件」？ --- 现在可以开始跑测试了。**你先关掉那两个开发者选项开关**
备好就订？另外那批 Critical 还没修喵，要开工的话我按报告里的「只能改三条」顺序来喵。
```

把「问号后允许 200 字」当作判据，问句检测从 **37–38 提升到 68**。判据不是失效，是**定义太窄**。

### 4.3 选择偏差：R4 用来定义类别的句子，大多不在它判读的样本里

我把 R4 报告里引用的**每一句**回全库定位（201 个主 transcript，整文件读），再用命中集合与 115 条「等你」样本求交：

| R4 引用的句子 | 全库出现 | 在 115 条「等你」样本里？ |
|---|---|---|
| `N/N 测试通过` | 2 次 / 2 会话 | **否**（一处是 R4 自己的会话在复述结论，一处是子 agent transcript `<session-I>`，被判为结构化提问） |
| `N 个文件都已同步到远端` | 1 次 / 1 会话 | **否** |
| `状态已复原（M 个实体 / delivered 0）` | 3 次 / 3 会话 | **否** |
| `没有待办项了` | 2 次 / 2 会话 | **否** |
| `Approve the prompt ...` | 1 次 / 1 会话（首字母大写） | **否**（它是权限请求，被 R4 归 D 类，不进 115 是正常的） |
| `按 C/D 方案做，需要你定` | 2 次 / 2 会话（**其中一个是 R4 自己的会话**） | **否** |
| `我等你反馈开下一轮` | 4 次 / 4 会话（**其中一个是 R4 自己的会话**） | 是（3 个真实会话） |

**这张表是本轮最需要小心的地方，也是我自己差点犯错的地方。**

我第一轮跑这个检查时，`N/N 测试通过` 在 115 条里查出来是 `true`——但那个命中是**我自己的会话** `<session-M>`，它在转录 R4 的结论。这是观测者污染：红队的会话本身变成了语料的一部分，而语料每轮都在增长。

排除自身会话后的结论：**R4 用来定义「S 类 = 需要语义」和「U 类 = 语义也难」的代表句，没有一句独立地、原样地出现在它判读的 85 条集合里**（唯一进入 115 的是 `我等你反馈开下一轮`，而它恰好是 R4 自己列为「需要语义」的那一类）。这不是取证，是举例。

> 这条批评同时适用于我自己：本报告的任何统计只要再跑一次就会变，因为红队会话本身在往语料里落盘。**所有比例都应带「±1 个百分点、随语料漂移」读**。

### 4.4 85 条的标注法本身不可复现

`verdict.mjs` 把类别硬编码成**下标数组**（`U = [1,2,7,8,...]`），而 `list.mjs` 每次重新扫描、按 mtime 排序。实测：

- R4 标注时 `TOTAL 85`；我重跑同一脚本得到 `TOTAL 87`，几分钟后 `TOTAL 89`，再后来 `94`、`95`。
- 扫描期间我自己的会话（`<session-M>`）插到了第 1 位——它在 R4 标注时还不存在。

`list.mjs` 在语料不变时下标是稳定的（3 次连续重跑，95 个下标全部指向同一会话；语料变化时的一次重跑出现 2 个错位）。**但语料一直在变**（我自己的会话每轮都在落盘），所以固定下标**无法跨时间复现**。R4 的 10.6/45.9/43.5 因此无法与具体会话对应，也无法被他人在任何后续时刻复算。

## 五、攻击 D：数字本身

### 5.1 语料规模

| 项 | R4 | 本轮 |
|---|---|---|
| 主 transcript | 186→188 | **196 → 205（扫描期间持续增长）** |
| 主 transcript 字节 | 1.44 GB | 1.45 GB |
| 子 agent | 2,548 / 5.84 GB | **3,781 / 5.92 GB** |
| 工具结果 | 652 / 564 MB | 654 / 0.56 GB |

子 agent 我多扫出 1,200+ 个、近 6GB。结论方向不变：**子 agent 绝大多数是「说完就停」，不携带「该不该继续」的信息**（R4 的 96.1% 我复现为 91.2% 停下，其中 82.5% 是纯 STOPPED_SILENT + 5.4% ERROR_STOP + 1 个 QUESTION_TEXT）。这条 R4 是对的。

### 5.2 死循环 2/188：判据两头都错

`scanAll` 用的 `historyRecords` 默认就是尾部 512KB 的记录。一个 116MB 的 transcript，**512KB 只覆盖 0.4%**。文件大于 512KB 的占 **70.6%**；对中位文件（3.3MB）覆盖率 15.6%，对 >5MB 的文件平均 **5.1%**。

全文件扫描（205 个主 transcript）：

```
8 窗口内 >=3 次相同调用：65 个会话 = 31.7%     ← R4 报 2/188 = 1.1%，差 29 倍
```

再按「重复的是什么」分类：

| 重复内容 | 会话数（n=65） | 说明 |
|---|---|---|
| 纯轮询等待 | **38** | `sleep 115 && ls ...` / `ListAgents` / `wait_agent` / `TaskOutput` |
| 轮询 + 其它 | 18 | |
| 纯工具重复（无轮询） | 9 | `run-tests.sh` ×3、`Read` 同一文件 ×3、`EnterPlanMode` ×4、`preview_start` ×5 |

典型命中（全程合法）：

```
x 43  ListAgents
x 36  Bash: sleep 115; date +%H:%M; git -C "$R" status
x 36  Bash: sleep 585; cd .../fix6 && wc -c fix6-R*.md | sort -rn | head -12
```

**R4 的两句话都不成立**：
- 「死循环极少发生 2/188」——那是因为它只看 0.4%–15% 的文件，命中被窗口切掉了。
- 反过来，全文件判据的命中里 **58%（38/65）是纯合法轮询**，直接拿来当告警会天天误报。

真正的结论是：**这条判据需要「重复的类型」才能用，而那是编排层的信息（`ListAgents`/`TaskOutput` 是宿主工具，`sleep` 是 AI 自己的轮询习惯），不是 transcript 的统计特征。**

顺带：R4 说命中样本是「`sleep 115 && cd ...` 与重复 `Read` 同一文件」——它看到的那两条，恰好就是我分类里的「轮询」和「真重复」各一条。**两条样本撑不起一个判据的精度结论。**

### 5.3 上下文判据：比 R4 说的更不可用

R4 说 154/188 没有 compact 边界。实测口径需要精确：**201 个主会话里 50 个有 `compactMetadata`**（都在头部或尾部 512KB 内可见），**151 个完全不可见**。

更关键的是那 50 个 `preTokens` 的取值：**只有 17 个不同值**，`trigger` 字段**全部是 `manual`**——不是自动压缩的触发点，是人手动 `/compact` 的时刻。所以「阈值」这个东西根本不存在：没有自动压缩，就没有可对照的上限。

**结论成立，但理由要换**：不是「阈值浮动 2.3 倍」，而是**本机看不到自动压缩，判据没有参照物**。

### 5.4 子 agent 上的死循环

抽样 300 个 >512KB 的子 agent：尾扫 `LOOP_SUSPECT` **0/300**，全文件命中 **3/300 (1.0%)**。R4 报 1/2548。方向一致（子 agent 里确实罕见），但同样低估约一个数量级。

### 6.1 那 8 条到底是什么（全量列出，最后一次运行 n=179）

```
① [<project-D-slug>] 重启桌面版后，到「已归档」里取消归档就能接着聊。README 里两条导入记录都更新了。
② [<project-X>] git add 时发现工作目录混进 <archive-dir>/，我没有提交它，加进 .gitignore
③ [<project-Y>] 两道闸都过了就顺了喵。以后从终端开的会话想搬进 Desktop，记得先把终端会话退干净
④ [<project-Z>] .gitignore 忽略 evidence/ 和 runtime/，保留 docs/ prompts/ tools/（模板说明）
⑤ [<project-Z>] 复制对应代码块，替换三个占位符，粘贴即可。目标不大用精简版……
⑥ [<project-Z>] 绝对路径的 .ps1 需要修。## git 状态
⑦ [<project-Z>] 审计报告里的 commit hash 指向历史重写前的版本、<audit-doc>.md 是主 agent 代笔
⑧ [<project-Z>] .gitignore 忽略 evidence/ 和 runtime/（与 ④ 同一段文本，另一分支）
```

逐条看：

- **①④⑤⑥⑧** 是**同一批会话里的操作说明 / 文档生成物**（`len` 都在 1000–2000 字，结尾是自然段落而不是停顿点，分类器把它们误当成了「说完就走」）。它们本该由「结尾是否在段落中间、有没有未闭合的 fenced block」这类**纯结构判据**处理，不需要语义。
- **②③⑦** 是复盘 / 状态陈述（「我做了什么、现在什么状态」）。这类确实需要判断「它算不算干完了」，但它们同时**都带可核对的断言**（`git status`、remote 地址、commit hash），按 §3 的办法能降一档。

**真正需要「理解用户目标才能判断」的，按最宽松的标准也不到 3 条。**

## 七、有没有「确定性判据 + 小模型」的组合优于「大模型」

**有，但不是一个模型问题。**

三条实测依据：

1. **最大的那块不是语义，是结构。** 错误停机 33%，`error` 字段直接可读，两次运行 0 差异。任何模型在这上面都是净损失。
2. **第二块是「执行」不是「理解」。** 23 条完成声明里，5 条有末次编辑后的成功测试、3 条只有历史成功、15 条根本没有测试调用。判断「有没有证据」是遍历 tool_use/tool_result 并看 exit code，模型帮不上忙——反而会像 R4 那样把「日志里没有远端状态」读成「不可验证」，**其实 log 里有 `git push`**。
3. **唯一像语义的残余，用 8 个词的表已经做到 87% 精度 / 90% 召回。** 剩下的 4.5% 不是「同一类问题的更多样本」，而是一堆各不相同的长尾（见 §6.1）。**长尾不适合模型，适合「报出来给人看」。**

我的判断：

- **不要装本地小模型来做这件事。** 本机也没有（`which ollama llama-server lmstudio` 无、11434/1234/5000/8000 全关），装一个只为了覆盖 4.5% 的长尾，成本远大于收益。
- **真正的组合应该是「确定性判据 + 工具执行」，不是「确定性判据 + 小模型」。** 断言核对需要的是：读一次 git status、跑一次测试、比一次 sha256、查一次远端 ref。这些是命令，不是推理。
- **模型唯一可能的位置**：把「该不该打断人」这一步从二分类升级成「值得看一眼 / 值得打断 / 不用管」，那是产品决策，不是判据。而这一步目前的数据量（153 条需要判断的停机）也不足以训练或评估任何模型。

## 八、R4 站得住的部分（必须留档，不能只批）

1. **「停没停」结构可判** —— 成立，`endsWithoutToolUse` 干净。
2. **错误停机结构可判、无后续成功覆盖** —— 成立，我复现 56–59 个唯一会话，全部终态。错误里 23 个是鉴权失败（401/403/`authentication_failed`），其余是 5xx/超时。**这是本语料里最大的单一停机原因，也是确定性判据最硬的一块。**
3. **子 agent 的分布完全不同（96% 说完就停）** —— 成立，我复现 91.2% 停下。
4. **`endsWithQuestion` 不适合当「在等你」的判据** —— **结论对，论据错**。它不是因为「命中 0」，而是因为定义太窄（37–38 → 68 可救）且「在等你」和「以问号收尾」本就是两件事。
5. **「干完没有」不能交给单次模型判断** —— 成立，而且比 R4 说的更硬：15 个会话根本没有测试调用。
6. **原始目标可从字节流取出 93.6%** —— 成立，我复现 93.7%（177/189）。
