## §0 一句话裁决

**双方都对了一半，但错的是同一个东西：都默认「改宽」等于「改判据」。**

用户要的是「AI 先了解项目再动手」，不是「拦截率降到某个数」。锐评证明了「降数字」这条路算错了，但它把结论推到「不装」，越过了它自己的证据。实测给出的第三条路是：**闸门对 `Edit` 这一半已经 100% 正确，问题全在 `Write` 那一半**——而这两半该用**两条完全不同的判据**。

**P1 = 把闸门拆成 Edit 闸（目标锚定）与 Write 闸（保持现有阈值），先把评估口径修对，再谈阈值。**

## §1 用户说「改宽」时，他真正要的是什么

### 1.1 用户在本仓库里的全部相关表达

| 出处 | 原话 | 指向 |
|---|---|---|
| `docs/design/2026-11-11-question-protocol-thesis.md:7` | 「用户一次给到需求便一次做完，不会中途停止，**而最重要的一个环节就是需求的传递**」 | 需求要一次问准 |
| 同上 | 「必须问问题，这是我们这个项目的主题」 | 介入集中在**开工前** |
| `2026-11-14-execution-phase-measurement.md:204` | 「**问问题之前 AI 需要了解项目文件夹状态、环境状态**，然后再去问，而不是写完文件再去问」 | 读项目是**提问的前置**，不是写的副产品 |
| `CLAUDE.md` 硬约束 8 | 派发必须声明产出形态与预算 | 用户要的是过程可控 |

### 1.2 判断

**用户要的是「AI 先了解项目再动手」。「19.9% 太高」是这个诉求的一个代理指标，不是诉求本身。**

证据不在措辞里，在两条可测的推理上：

1. **若是「降数字」，那 2.2%（四轴全开）就该是胜利**，用户应该满意。但 §3 会证明：2.2% 的实现代价是「95% 的会话从第一次写起就无闸」——它买到的不是「AI 更了解项目」，是「闸门基本不存在」。这与用户的诉求方向相反。
2. **若诉求是「先了解项目」，那用户的抱怨根本不是「拦太多」**，而是「AI 在不了解项目的情况下就动手了」。本仓库的语料里这条抱怨确实只有 1 条（§2 R1，且那条不是抱怨），但这**不构成反对**——用户的诉求是**产品立场**，不是从自己被拦的痛感里长出来的。

**所以「改宽」应读作：让闸门在「AI 其实已经了解项目」时不要拦。** 这是一个**准确度**要求，不是一个**阈值**要求。这两者在数据上会走向完全不同的实现（§3）。

锐评在这一点上是对的（它说「判据的锚点错了」），错在它把这个洞察用成了「所以不装」。

## §2 锐评六条理由，逐条验伪或确认

复算命令统一是 `node scripts/resolution-gate-audit.mjs --only R<N>`。

### 2.1 六条理由的复算结果

| # | 锐评的说法 | 我的复算 | 判定 |
|---|---|---|---|

| 2 | 宿主门 `Edit` **0/16,729**、`Write` **3/5,813**、合 **0.013%** | `Edit` **0/14,047**、`Write` **3/4,552**、合 **3/18,599 = 0.016%** | **比率可复算，分母不可复算**（见 2.2） |
| 3 | 被拦组 **0.51%** vs 放行组 **0.96%** | 被拦 **2/395**、放行 **17/1,787** = **0.51% vs 0.95%** | **确认**（且两条「纠正」逐字是「我不小心点错了，点到stop this task」） |
| 4 | 单轴消融 +C 11.0% / +B2 12.5% / +B 16.2% / +A 17.6% / 全开 2.2% | `measure-gate-ceiling.mjs` 本机实跑：C **15**、B2 **17**、B **22**、A-unique **27**、A-greedy **24**、全开 **3** | **确认**（13 项自检全过） |

| 6 | 「136 会话说为 43 个任务簇」 | 前缀 100 字符归并 → **43 簇**；「≥1 个 fork 被拦」= **11/43 = 25.6%** | **确认，且它说的「该重算」我算了**（见 2.3） |

**它没有一个数是编的。** 这一点必须先说清：锐评的测量是可信的。

### 2.2 口径混淆（它自己没意识到）

**它把「宿主文件读取门的触发率低」当成「没读就写很少发生」的证据。这两个不是一回事。**

宿主的门只在「**文件已存在且没读过**」时报错。实测这条限定的后果：

| 事实 | 实测 |
|---|---|
| 真实项目首写里 `Write` 占 | **118/136 = 86.8%** |
| 被拦 27 个里首写是 `Write` 的 | **23/27 = 85.2%** |
| 66 个沙箱会话里「真的一行没读就写」（`gateReads=0`） | **48 个** |
| 这 48 个里被宿主门报错的 | **0 个** |

**48 个会话真的一行没读就写，宿主门一次都没响。** 因为它们的首写是 `Write` 一个新文件——**宿主门在定义上管不到新建文件**。

所以「0.013%」这个数字的分母里，86.8% 的样本本来就不在它的管辖范围内。它测的是「模型会不会编辑一个没读过的既有文件」，那是另一个问题。用它的低触发率去论证「本闸不该存在」，是**把一个窄门的零命中当成一个宽问题的零发生**。

### 2.3 它提了但没重算的一条（我算了）

锐评 §2④ 说「分母是混的」，然后没有重算就继续用 19.9%。按任务簇口径实测：

| 口径 | 覆盖率 | 说明 |
|---|---|---|
| 会话级 `gateReads<3` | **27/136 = 19.9%** | 锐评与两份测量报告都用这个 |
| 任务级「至少一个 fork 被拦」（前缀 100） | **11/43 = 25.6%** | 锐评自己给的数，我复现 |
| 任务级「所有 fork 全被拦」（前缀 80） | **8/41 = 19.5%** | 同一件事的另一种读法 |
| 任务级（**首条人类消息逐字相同**） | **14/70 = 20.0%** | 最严的簇定义 |

**三条口径都落在 19.5%–25.6%。** 所以「口径混淆」这条批评**成立但不改变量级**——按任务算只会更差（25.6%），不会更好。锐评提了这条却没往下算，它错过的是「支持自己结论」的那一半：**任务级误伤率比会话级更高**。

### 2.4 它没意识到的、支持「该动」的证据

**① `Edit` 那一半已经是 100% 正确的。**

| 事实 | 实测 |
|---|---|
| 真实项目首写用 `Edit/MultiEdit` | **18** 个会话 |
| 这 18 个里，首写前**读过目标文件本身**的 | **18 个（100%）** |
| 但闸门（阈值 3）仍拦下其中 | **4 个** |
| 这 4 个全读了自己的目标文件 | **4/4** |

**模型在改文件之前，无一例外都先读了那个文件。** 宿主的 `Edit` 侧 0 次报错独立印证了同一点。这意味着：对 `Edit` 来说，「读过几个不同文件」是个**无关判据**——真正的信号「读过目标文件」在 100% 的样本里都成立，而闸门却因为它数的是「读了几个」而误拦了 22%。

**负向验证（判据非恒真）**：把比对的目标路径改坏一个字符，`readTarget` 立刻从 **18/18 掉到 0/18**。所以这不是一个「怎么写都成立」的判据。

**② 被拦集的重心是「写新文档」，不是「改代码」。**

| 被拦会话的首写目标 | 数量 |
|---|---|
| `.md` | **20/27** |
| `Write`（新建/覆盖） | **23/27** |
| `Edit` | **4/27** |

**这个闸门实际上在拦「写 Markdown 文档」**，不是「改代码」。而用户原话里的痛点是「写完文件再去问」——那说的正是**新建产出的那一刻**。所以闸门选的时间点是对的，选的对象（`Edit`/`Write` 一刀切）是错的。

**③ 结构门已经守住了「改宽后会不可验证」这条。**

锐评 §4 的核心论点是「重放器和闸门是两份解析器，改宽后无法复算」。**这条已经过时**：`observe-reality-check.mjs` 现在调闸门的 `readPathsInTranscriptText()`，`probe-parser-divergence.mjs` 实测 **0/155 分叉**（同文本、同文件+同窗口两种口径都是 0）。

我在临时副本上把闸门动词表加上 `ls/find/grep`，然后跑 `node --test`：

```
→ tests 95 / pass 92 / fail 3
   ✖ gateReadsOf 只认 Read/NotebookRead 与整份读的 shell 动词
   ✖ 重放器不得留第二份解析实现：等价文本上逐条相同
   ✖ transcript 解析器是唯一实现：闸门动词表加 ls，重放器立刻跟着变
```

**锐评说「92/92 一条都没红」，现在有 3 条会红。** 它的失败模式 (a)「改完测试全绿但行为没变」在当前代码上**不复现**：重放器立刻跟着变（19.9% → 12.5%）。

## §3 第三条路：改宽但不改判据

用户的话（「先了解项目」）与锐评的话（「锚点错了」）指向同一个方向：**换判据的锚点，而不是换阈值**。下面逐个实测。

### 3.1 候选逐个评估

| 方向 | would-deny | 沙箱阴性对照 | 新增 I/O | `decide()` 纯函数 | 可被重放复算 |
|---|---|---|---|---|---|
| **现状**（阈值 3） | 27/136 = **19.9%** | 49/66 = 74.2% | 无 | 是 | 是 |
| **A. 换锚点：目标文件/目录** | **92/136 = 67.6%** | 未测（判据更严，必不掉） | 无（`intent.paths` 已在手） | 是 | 是 |
| **B. 阈值降到 1** | 13/136 = **9.6%** | 48/66 = 72.7% | 无 | 是 | 是 |
| **C. 只修解析缺陷** | **28/136 = 20.6%**（↑1） | 49/66（不变） | 无 | 是 | 是 |
| **D. 拆两个闸（Edit 紧 / Write 宽）** | **23/136 = 16.9%**；Write 侧阈值 1 时 **13/136 = 9.6%** | **49/66 不变**；阈值 1 时 48/66 | 无 | 是 | 是 |
| **E. 先修评估口径再重评** | 不改变量，**改变「这个数还能不能信」** | — | 无 | 是 | 是（这就是本项） |
| F. 「首写前读过 README/CLAUDE.md」 | **70/112 = 62.5%** | 24/27 | 无 | 是 | 是 |

### 3.2 关键发现：A 方向与用户诉求相反，但 D 把它救回来了

候选 A 单独看是灾难：67.6% 的拦截率。锐评对此的判断是对的（「换锚点会让拦截率升 3.4 倍」）。

**但 A 的 67.6% 是把 `Write` 新文件也算进去了——而新建文件在定义上没有「目标文件」可读。**

按首写工具拆开，同一个锚定判据给出完全不同的结果：

| 首写工具 | 会话数 | 目标锚定下仍被拦 | 说明 |
|---|---|---|---|
| `Edit/MultiEdit` | 18 | **0** | 全部读过自己的目标文件 |
| `Write` 等 | 118 | 23 | 新建文件无目标可读 |

**「Edit 侧目标锚定」的误伤是 0，而且它比现有判据更严（不再允许「读了三个无关文件就算过关」）。** 这正是用户要的「先了解（要改的）项目再动手」，也正好消解锐评的反对（它说换锚点会升到 67.6%——那只在「不区分新建/修改」时成立）。

### 3.3 候选 C 的方向被任务书说反了

任务书说 C「方向是多算→更宽松」。**实测相反**：

```
现行     27/136
修缺陷后 28/136   ← 变严，不是变松
```

原因是缺陷把 `head -c 400` 里的 `400` 当成了读过的文件——那是**假路径**。修掉它，`be6b89cf` 从 4 个降到 2 个，于是被拦。`measure-gate-ceiling.mjs` 与 `redteam-gate-widening.mjs` 独立给出同一结论（`+D` 贡献 −1）。

**C 是纯 bug 修复，但它会让数字变难看（+1）。它应该做，但不该被包装成「改宽」。**

### 3.4 候选 E 是前置条件，不是替代方案

现状已经比锐评写它时好：解析器统一了，分叉 0/155。但**还剩一个真实的分叉**：

```
observe-reality-check.mjs  用 tailGateReads → 1 MB 窗口
measure-gate-ceiling.mjs   自己重写了 windowReadPaths（为了能换解析器）
```

两者在 206 个会话上已验一致，但那是**两份实现碰巧一致**，不是**一份实现**。任何一次改判据都可能让它再次漂。

**E 的正确内容是：把「窗口读取」也收进闸门本体，让所有测量脚本都调它。** 这是唯一能保证「改完之后那个百分比仍然可复算」的动作。它不改变任何数字，因此**可以独立先行**。

## §4 排序与推荐

### P1 — 拆闸 + 把窗口读取收进闸门本体（一件改动，两个半）

**做什么**：`decide()` 里按 `intent.isWrite` 与工具名分两路：

- `Edit/MultiEdit/NotebookEdit` → 判据改为「**读过这个文件本身**」（`pathKeyOf(intent.paths[0]) ∈ 已读集合`）
- `Write` 及其它 → 保持现有「读过 ≥N 个不同文件」

**执行的是用户的哪句话**：「问问题之前 AI 需要了解项目状态」+「一次做完，不中断」。`Edit` 侧的误伤是纯损失（4 个会话 100% 读过目标文件却被拦），没有任何收益。

**消解锐评的哪条反对**：§3（「换锚点会升到 67.6%」）—— 那只在混着算 `Write` 时成立。拆开后 Edit 侧误伤 0，Write 侧不动。

**可独立回滚吗**：**可以。** 两路判据在同一函数内的两个分支，回滚 = 删掉 Edit 分支。`observe` 模式下不产生任何拦截，可先跑一周看日志。

**验收标准（可机械判定）**：

1. `node scripts/resolution-gate-audit.mjs --only R8` 输出 `Edit-first REAL: 18 · readTarget 18 · gateOk 14`（判据事实）
2. 新增测试：构造「`Read pom.xml` → `Edit pom.xml`」的最小 transcript，`decide()` 必须 `allow`。把 Edit 分支删掉，这条测试必须红。
3. 沙箱桶拦截数 **≥ 48/66**（不许掉到 48 以下 = 判据没被削空）
4. `node scripts/probe-parser-divergence.mjs` 仍是 0 分叉

### P2 — 修解析缺陷（C），但**不**把它算作改宽

**做什么**：`readPathsOfToolUse()` 里让 `head/tail` 的 `-n/-c` 吃掉一个值。

**执行的是用户的哪句话**：「可以给别人用不掉链子」——假路径是 bug，bug 不分宽严。

**消解哪条反对**：锐评 §7 没列这条，但 `measure-gate-ceiling` §8 明确要求「不能把它包装成扩宽」。

**可独立回滚**：可以，一处解析逻辑。

**验收**：`head -n 20 a.mjs` 不得产出 `20`；`cat -n a.mjs` 必须仍产出 `a.mjs`（这两个方向相反的用例都得有）。**注意它会 +1 个拦截**，要和 P1 一起看总账。

### P3 — 阈值 3 → 1，**仅限 Write 分支**

**做什么**：`Write` 侧 `minReads` 从 3 降到 1。

**执行的是用户的哪句话**：「先了解项目」——「至少读过 1 个」比「读过 3 个」更贴近这句话的字面意思。

**消解哪条反对**：锐评 §5（「降阈值是一行常量，零新增风险，却被排除在候选外」）。它说得对，**而且这条不该因为「不到 3-5%」被否**——3-5% 没有数据依据（锐评 §2 成立）。

**可独立回滚**：可以，一个常量。

**验收**：真实 136 → **13（9.6%）**；沙箱 **≥ 48/66**；`decide()` 复算一致。

### P4 — 用 `observe` 跑一周，收「野生 would-deny」

**做什么**：P1–P3 落地后，`OW_PRE_WRITE_GATE=observe` 装进 `settings.local.json`。

**执行的是用户的哪句话**：「一次做完，不中断」——先证明它不会误伤，再开 `deny`。

**消解哪条反对**：锐评 §8.2（「observe 能给出重放给不了的东西：真实会话里被拦之后模型和用户分别做了什么」）。这条它说得对。

**可独立回滚**：删掉 hooks 段即可。

**验收**：`tasks/runs/pre-write-gate/*.jsonl` 里出现 `would-deny` 的行，且逐条能对上归因；**不允许**在没有任何野生样本的情况下开 `deny`。

### P5 — 用「写了但没读目标文件」重定义闸门，取代「读了几个」

**做什么**：把 `attribute()` 的重心从「A/B/B2/C/D 五类」改成「`Edit` 未读目标 / `Write` 未读任何项目文件」。

**为什么排最后**：它需要 P1–P4 的数据才能定阈值。现在做就是把结论写死在测量之前。

**可独立回滚**：只改测量脚本，不动闸门。

**验收**：`resolution-gate-audit.mjs --only R8` 的 `deniedReadTargetBefore` 与 `measure-gate-ceiling` 的对齐断言逐项相等。

### 我推荐 P1 先做，因为 Y 成立；如果 Y 不成立

**Y = 「`Edit` 之前的读是模型的自发行为，不依赖闸门」。** 证据是宿主的 `Edit` 侧 0 次读取门报错，加上 18/18 读过目标文件。**如果 Y 不成立**（比如某个模型确实会不读就 Edit），那么 P1 的 Edit 分支应该保留「读过目标文件」这一条不放行——那样它的行为与现在等价，P1 就退化成纯粹的评估口径修复，仍然可做。

## §5 锐评错在哪：一句话总结

**它把「这个判据测的东西不对」推成了「这件事不值得做」。**
