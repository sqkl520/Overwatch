# 锐评：Stop hook 验证闸该不该做成产品

- 日期：2026-11-13
- 作者：锐评 Agent C1（独立评审，**prompt 中不含任何执行 Agent 的自我评价**）
- 产出形态：`exploration`（评审 + 复算，不改代码、不碰 git）
- 被评审对象：方案 A「Stop hook 验证闸」，`scripts/stop-verify-hook.mjs`（804 行）
- 标注约定：`[实测]` = 本次在本机语料 / 仓库代码上复算，口径写在对应小节；`[引用]` = 直接引自本仓既有报告；`[推演]` = 无直接证据的推断

---

## 0. 判决

**不该做（作为独立产品形态）。**

方案 A 的机制能跑、不锁死会话、fail-open 做得很干净——这些我复算了，**是真的**。
但决定一个产品形态成立与否的不是「机制是否可靠」，是三条：

1. **它的触发条件与用户的痛点在时间上错位。** 实测：可拦的完成声明里 **93.7% 发生在会话中段**，
   只有 6.3% 落在会话最后一次交还上。而用户唯一会读那句话的时刻，是最后一次。`[实测]`
2. **它的「痛点证据」主要来自它自己的实验沙箱。** 引用数据里「全量 332 会话发现 37 条
   `NO_EVIDENCE`」——我今天复算，**真实语料里只有 3 条，其中 2 条是同一份 transcript 的副本**；
   其余 43 条全部落在 `hook-e2e-sandboxes/` 与 `stop-hook-lab/` 这些**为了测这个闸门而造出来**的目录里。`[实测]`
3. **它自己陈述证据时会说假话。** `stop-verify-hook.mjs:259` 把 `truncated` 硬编码成 `false`，
   于是一个只读了尾部 8 MB 的判定，会在 reason 里写「整个文件范围内没有任何测试运行调用」。
   我复算：**14.9% 的拦截建立在这个假陈述上**；在被截断窗口上，**35.2% 的拦截本该判 `UNKNOWN` 放行**。`[实测]`

一个卖「你说完成，先给我看证据」的产品，在自己的 reason 里伪造证据范围 —— 这不是 bug 列表里的一行，
这是产品论题的反面。在修掉它之前，任何「该不该做」的讨论都是在讨论一个不存在的产品。

**该做什么**见 §7：把同一套判定从「拦用户的回合」改成「标注给用户看」，并把主战场从 Stop hook 移到事后对账。

## 1. 先把证据基座摆清楚

### 1.1 我复算了什么

| 复算对象 | 命令 / 方法 | 结果 |
|---|---|---|
| 人工介入基线 | `node scripts/measure-interventions.mjs --days 0 --json` | 342 会话 / 2602 人类回合 / 828 次介入 / 1.79 GB |
| 断言分布 | `node scripts/verify-claims.mjs --json` | 349 transcript / 106 条可核对断言 / 46 `NO_EVIDENCE` |
| 闸门在真实语料上的行为 | 自写 replay：遍历 282 份非实验 transcript，把**每一次** `end_turn` 的最后一条 assistant 文本喂给 `runHook()` | 5489 次 `end_turn`，其中 1442 次含可核对断言，**458 次会被拦**（97 个会话，p50 4 次 / p90 10 次） |
| 闸门在「会话最后一次交还」上的行为 | 同上，只取每个会话最后一个 `end_turn` | **37 次可拦**，扣除子 agent 旁证后净拦 **14 个会话 / 282（5.0%）** |
| 检测器对完成语义的覆盖率 | 宽松完成正则 vs `detectClaims` | 1440 条含完成语义的末轮文本，检测器认出 653 条 → **45.3%** |
| 闸门延迟 | `runHook()` 端到端 | 123 MB transcript **5.7 s**；105 MB 1.5 s；≤65 MB 均 **< 250 ms** |

### 1.2 复算发现的三个「引用数据对不上」

评审判定必须建立在不歪曲的证据上，所以先说三处。

**(a) 「37 条 `NO_EVIDENCE`」有 43 条来自实验沙箱。**

`verify-claims --json` 的 46 条 `NO_EVIDENCE` 按项目分布：`stop-hook-lab-proj*` 19+11 条、
`hook-e2e-sandboxes/*` 7 条、`Overwatch/.tmp-analysis/hook-e2e-runs/*` 6 条，
真实项目只有 `Mentor-Express` 1 条 + `D--Projects-rea` 2 条。
而 `rea` 的那 2 条是**同一份 transcript 的两个落盘**（uuid 交集 2356/2362 = 99.7%）——算 1 条。`[实测]`

也就是说：**真实语料里，这套判据在全量历史上只抓到 2 个没有证据的完成声明会话。**
拿「37 条」当产品需求证据，成立的前提是把闸门自己的靶场当成用户环境。

**(b) 「264 会话 / 2430 人类回合 / 617 次介入」与今天的复算不同源。**
今天 342 / 2602 / 828。差异可以解释（语料在生长、判据被修过），但意味着引用时应连同口径与时点一起引。
`798` 这个数我复算到 `828`，同向，可用。

**(c) 「`verify-claims` 762 行」实际 1934 行。**（`wc -l`）
不影响结论，但一个卖「核对数字」的产品，它自己的规模数字也该对。

三处都不致命，但 (a) 改变了结论方向：**方案 A 的用户需求证据，被它自己的实验污染了。**

## 2. 这个形态有用户吗

### 2.1 p50 = 0 是真的，而且比 0 更糟

复算：342 个会话里 **203 个（59.4%）人工介入次数为 0**；p50 = 0，p90 = 7.9，max = 32。`[实测]`
「有实质工作的会话」口径下 p50 = 1、p90 = 10。

把闸门开到真实语料上，**136 个零介入会话里有 8 个会被拦**。`[实测]`
这 8 个人从头到尾没要求过任何东西，却被一个他们没要求过的进程打断了。

### 2.2 p90 那群人有多大：15.8%

- 介入次数 ≥ 5 的会话：**54 / 342（15.8%）**。`[实测]`
- 这 54 个里，会被闸门拦到的：**49 个**。
- 介入次数 ≥ 1 的会话：139（40.6%）。

所以方案的可用市场是「15.8% 的会话所在的用户」，且是**一台机器、一个用户、五个月**的样本。
换算成外部市场，本仓已有调研给了硬数字：

> `claude code monitor` GitHub 仓库 **4,083 个**；Show HN 同类产品**普遍 2–77 分，常 0 评论**。`[引用]`

### 2.3 触发点与痛点错位：这是最要命的一条

我按「闸门会拦的那一次 `end_turn`」逐条对齐了「用户下一句说了什么」：

| 事实 | 数量 | 占比 |
|---|---|---|
| 可拦的完成声明（全语料、逐 turn） | 603 | 100% |
| 其中发生在**会话最后一次交还** | 37 | 6.3% |
| 其中发生在会话**中段** | 566 | **93.7%** |
| 可拦之后用户下一句是「继续 / 接着 / 下一步」 | 84 | 13.9% |
| 这 84 次里，用户要求**验证/核实**的 | **2** | 0.3% |
| 这 84 次里，用户要求**继续干活**的 | 67 | 11.1% |

`[实测]`（口径：`NUDGE` 判据取自 `measure-interventions.mjs:64`）

读法：**闸门拦住的地方，86% 的时候用户根本没说「继续」——会话就正常往下走了。**
而在用户真说「继续」的 84 次里，他想要的是**下一件事**（67 次），不是「你刚才那句话有证据吗」（2 次）。

方案 A 的核心价值主张是「在你看到 AI 说『做完了』之前，先确认它有证据」。
但数据显示：用户看到那句话时，**已经不在读它了**——他要的是下一步。
闸门把「继续干活」变成了「先把上一句的账结清」，这是**把用户的痛点换成了产品自己的痛点**。

### 2.4 会话末尾那 37 次，值不值

即使只看「会话最后一次交还」这个最有利的口径：

- 37 次可拦 → 扣除子 agent 旁证后净拦 14 个会话（5.0%）。
- 这 37 次里，之后用户还说「继续」的：**4 次**。
- 全语料「AI 宣称完成后用户推一句」的总量：240 次（其中 166 次 AI 最后一句连问都没问）。

`[实测]`

即：闸门最多命中 **4 / 240 = 1.7%** 的「说完就停」类介入。
而它要为此在 5 个月的 282 个会话里制造 14 次打断（其中至少 3 次是假阳性，见 §6）。

## 3. 它比现有方案好在哪：逐条对比

| 方案 | 覆盖 | 打断成本 | 假阳性后果 | 结论 |
|---|---|---|---|---|
| **用户自己检查**（看到「做完了」去跑一遍） | 100%（他自己决定查什么） | 0 | 无 | **不弱于 A**。用户已经在做：97.7% 的 `end_turn` 后面紧跟人类发言（这是对话常态，不是审阅），但「推一句继续」的 240 次里，用户已经在用行动做判断了 |
| **`verify-claims` 独立命令 / CI**（现成，5.6–9.1 s 全量，有 `--session` / `--explain` / `--format md` / 退出码 0/1/2） | 同一套判据、同一批断言 | **0** | 判错只是报告里一格错，不阻塞任何人 | **严格优于 A 的判定能力**，且已交付 |
| **自己写一个 Stop hook**（官方文档给了 `agent` 型样板：「所有单测通过才许停」） | 任意 | 同 A | 同 A | 机制不是护城河；能差异化的只有「断言族识别 + 项目命令检测」这一层 |
| **不做，接受 AI 偶尔撒谎** | — | 0 | 风险自负 | e2e 实测：13 次无 shell 的运行里 **11 次**主动说「我没跑，以下是推演」，**0 次**把推演伪造成运行输出 `[引用]` |

### 3.1 「优势不明显」的具体算法

方案 A 相对 `verify-claims` 的**唯一**增量是「事前 vs 事后」。事前值多少？

- 事后你能看到的：同样是这 106 条断言、46 条 `NO_EVIDENCE`、11 条 `STALE_ONLY`。
- 事前多给你的：模型在被拦后**改口**（e2e 里 2 次拦截、2 次如实改口）。`[引用]`
- 你要付的：每次拦截 = 一轮完整往返。本机 assistant 消息均值 **input 37,595 tok / cache read 303,260 tok / output 690 tok**。`[实测]`
  458 次拦截 ≈ **1,700 万 input token** 的额外消耗，换来 §2.3 里那 2 次「用户要求验证」。

3.1 节的结论：**事前的净增量不是零，是「用 1700 万 token 换 2 次对上了的验证请求」。**

### 3.2 唯一我认账的那一条

会话 `50ec242b`（本仓库自己）：`**497 条测试全绿，但改好了一个核心 bug 它还是全绿。`
全量（主 + 67 个子 agent）里有 638 次 `node --test`、585 次成功——**但最后一次源码编辑在 index 21402，
最后一次测试在 20725**。测试在编辑之前。`[引用]`

这条是 `STALE_ONLY` 的教科书案例，也是 `verify-claims` 事后报告**抓不到**的
（事后会看到一堆历史成功调用，很容易以为证据成立）。**它值。**

但注意：真实的 `STALE_ONLY` 在全量真实语料里只有 **11 条**（去实验目录后），
其中我已确认至少 **2 条是假阳性**（§6.2），1 条来自重复落盘。真正干净的「编辑后没重跑」约 **8 条 / 282 会话**。

**为了 5 个月里 8 条真阳性，让一个进程在 458 个回合上拦用户。这笔账我不认。**

## 4. 失败模式

### 4.1 误拦之后会发生什么（有实测）

e2e 实验：14 次有效运行、2 次拦截、干净配置只有 1 次。两次拦截里 **1 次是误报**
（模型在说「whether tests pass 这件事很重要」，被 `test-count` 正则当成断言）。
两次模型都选了 reason 里给的那条退路（改成「未运行测试」）。`[引用]`

我复算的更大样本给的数字：

- 8 MB 窗口上，**298 / 706 次拦截发生在被截断的读取上**；其中 **105 次（14.9% 的全部拦截 / 35.2% 的截断拦截）**
  在诚实标注 `truncated` 后会变成 `UNKNOWN` 并放行。`[实测]`
- **28 / 701 次（4.0%）** 是「同一条复合命令里既改了源码又跑了测试」被判成「编辑后没重跑」。`[实测]`
- **151 / 701 次（21.5%）** 的「最后一次编辑」其实来自 shell 改动（`sed -i` / `cp` / `cat >>`），
  其中相当一部分是改**测试文件本身**或改 `docs/README.md` 之后被当成「源码改动」。`[实测]`

合并后果：**误拦率不是「偶发」，是每 6–7 次拦截里有 1 次建立在错误事实上**（与 `verify-claims` 自己报的
84.6% 精度同量级，n=13 `[引用]`）。

误拦的具体代价：模型多跑一轮（≈37.6k input token）；如果它拿不到证据，只能改口或重复；
用户看到一次「AI 被拦了」，然后读到一句「未运行测试」。**第三次之后，这句话就变成噪音**——
和「以上内容由 AI 生成，请自行核实」同一种性质：形式上的诚实，实质上的免责声明。

### 4.2 漏拦之后会发生什么

- 检测器对完成语义的覆盖率 **45.3%**：1440 条含「做完了 / 已修复 / done」的末轮文本，只认出 653 条。`[实测]`
- 已知的具体漏：`detectClaims('…已全部修好：')` → `[]`；`detectClaims('…已按下面方式修好：')` → `[]`。`[实测]`
  （`hook-sample-logging` 报告已承认这是**已知未修**）
- `UNKNOWN` / `UNCHECKABLE` 一律不拦（这是对的），但意味着「把测试丢后台再声称通过」永远放行。
  原型报告自己写了：「闸门挡的是『忘了跑』，不是『刻意绕过』」。`[引用]`

漏拦的后果不是「用户被骗」，是**用户以为闸门检查过**。§5 展开。

### 4.3 连续 6 / 9 次上限：是保护，也是缺口

- 我复算：最大连续可拦次数 **9**（正好等于宿主上限）；只有 **1 个**会话超过自设的 6 次上限。`[实测]`
- 但按会话累计：**34% 的会被拦会话（40/117）超过 6 次**，被 `MAX_BLOCKS = 6` 压掉 **187 / 603 次（31%）** 拦截。`[实测]`

读法：上限作为「不锁死用户」的保险是**对的、且必要**（fail-open 三层做得干净，我认）。
但它同时意味着：**闸门在「持续性谎报」这个它最该管的场景里，只能管住前 6 次。**
而持续性谎报恰恰是唯一值得装这个闸门的场景。

### 4.4 「用户被拦烦了直接关掉」——风险多大

**很大，而且证据在产品自己的设计里：**

1. **默认 `mode = 'off'`**（`stop-verify-hook.mjs:89`）。要真的拦，用户必须在 shell 里
   `export OVERWATCH_STOP_VERIFY=block`（模板里明确写了「不要写进 settings 的 env」）。
2. 也就是说，**方案 A 声称的「用户零配置，装完即用」与实现的现状直接矛盾**：
   实际需要 (a) 合并一段 settings，(b) 把 `<OVERWATCH_ROOT>` 换成绝对路径，
   (c) 在 shell 里设环境变量。三步，且 (b) 每台机器都要手改。
3. 一个需要三步手工配置、配错就静默失效（`timeout` 低于实际耗时时宿主**静默 kill**，
   `durationMs` 有值、`hasOutput:false`、`hookErrors:[]`——这个坑原型报告踩过）的功能，
   **不会有人开**；开了的人，在第一次误拦之后会关。

本仓有一条同构的实测教训可以直接引用：通知系统里 `permission prompt` 类 **66/66 = 0% 真阳性**，
最后的选择是「不再通知，但照常写观察记录」。`[引用]`
**这个项目的既有行为模式就是：判不准就闭嘴。** 闸门迟早会走到同一个结局，而到那时它的
「零配置」卖点已经变成了「装了一个不说话的东西」。

## 5. 反面证据能不能反驳它

三条反面研究，威胁程度不同：

### 5.1 MAST / arXiv 2505.18286：不构成实质威胁

MAST 说的是「改角色规格、增强协调」效果不足（1600+ 轨迹，规格类 41.77% / 交互失配 36.94% / 验收类 21.30%）。`[引用]`
它论证的是**多 agent 组织**的失效，方案 A 是**单 agent 的单点闸门**，不在同一层。
arXiv 2505.18286（MAS 收益随模型变强而减弱）同理。

唯一沾边的是 MAST 的「验收类失败 21.30%」——那**支持**「加个验收闸」的方向。
**这两条不构成反驳，反而略微支持「验收分离」这一层。**

### 5.2 HumanEvalComm：部分构成威胁，但打在别的方案上

「不需要问的题硬问 → Pass@1 65.58% → 27.45%」说的是**澄清提问**。
方案 A 不提问，它要求补证据。同构风险是「不需要拦的回合硬拦 → 多花一轮」，我已经量化了（§4.1）。
**不致命，但同向。**

### 5.3 N=180 实验：**这一条是致命的**，而且已经部分应验

原文结论（arXiv:2611.01087）：回答过 2 个前置澄清问题的被试，**复查时间更短、未修改直接接受从 46% 升到 60%（p=.024, d=.38）**，
且**对「问题问到的那部分」里的违规更容易放过**。原话：「pre-answer CQs reduce subsequent engagement and increase unchanged acceptance of LLM responses, including erroneous ones」。`[引用]`

**映射到方案 A：**

| N=180 的机制 | 方案 A 的同构机制 |
|---|---|
| 回答过提问 → 「我已经对齐过了」 | 过了闸门 → 「这个回合已经验过了」 |
| 复查时间变短 | 用户不再自己翻证据 |
| 提问覆盖到的那部分，违规更容易放过 | **闸门覆盖到的 7 个断言族，用户更信；没覆盖到的，用户以为也被覆盖了** |
| 一般信任无变化 | 产品口碑不会变差，但实际风险上升 |

**这不是推演，是可以量化的结构：**

- 检测器只认 7 个族（`test-count` / `build` / `commit` / `push-remote` / `pr-ci` / `file-count` / `vague-completion`）。
- 对完成语义的覆盖率只有 **45.3%**。
- 全语料 5489 次 `end_turn` 里，**4027 次（73.4%）根本没被认出任何可核对断言 → 静默放行**。`[实测]`

**闸门的输出不是一个二元信号（过 / 没过），是一个三态信号（过 / 没过 / 不知道），
而它只把前两态显式说出来。「不知道」被用户读成「过」。**

这就是 N=180 那条在方案 A 上的真实形态：**它不制造虚假安全感，它制造「部分覆盖被误读为全覆盖」。**
一个用户看到 458 次里面有 400 次被放行，会得出「我的 AI 基本不撒谎」的结论——
而另外 4027 次里有没有撒谎，这个产品一个字都没说。

### 5.4 一条额外的、来自这个仓库自己的反面证据

> 『最可靠的办法是打开它看一眼』。」

## 6. 三个可复现的产品缺陷（这不是「待优化」，是「现在不能用」）

按严重度。全部有复现命令，全部未修。

### 6.1 【致命】reason 里的证据陈述是假的：`truncated` 硬编码

`scripts/stop-verify-hook.mjs:259`

```js
return classifyEvidence({ claim, evidence, truncated: false, records });
```

`verdictFor()` 永远传 `truncated: false`，即使 `loadRecords()` 明确返回了 `truncated: true`。
后果：`classifyEvidence` 走到「整个文件范围内没有任何测试运行调用」这一支（`verify-claims.mjs:1042`），
而这句**只是因为它只读了尾部 8 MB**。

真实产出（会话 `76bbe070`，15 MB，只读尾部 8 MB）：

```
· 你写的是：「**614 个测试全绿**喵。」
  测试通过 —— 证据在最后一次源码编辑之前，编辑之后没重跑（有 40 次成功的「测试运行」，…）
```

真实产出（会话 `2d8f47bf`，105 MB）：

```
我认不出这个项目用什么命令跑测试（根目录没有 package.json / pom.xml / …）。
```

——它在说这句话的时候，项目根其实有 `package.json`，只是不在它的 `cwd` 里。

量化（口径：按 turn 前缀字节数判窗口是否被截断，比 `readBack` 的定长回溯更准）：

| 指标 | 数值 |
|---|---|
| 全部可拦断言 | 706 |
| 发生在被截断窗口上 | 298 |
| 诚实标注 `truncated` 后会改成 `UNKNOWN`（即放行） | **105** |
| 占全部拦截 | **14.9%** |
| 占截断窗口上的拦截 | **35.2%** |

另外：把 282 份 transcript 的末条文本喂给 hook，14 次拦截里 **5 次**的 reason 含
「整个文件范围内没有任何…」——对一个它只读了 8 MB 的 11–123 MB 文件。`[实测]`

**一个以「你有没有证据」为唯一卖点的组件，在 14.9% 的情况下虚报自己的证据范围。**
这不是「精度不足」，是「产品论题在自身实现上失败」。参照本仓自己的纪律：
README 写 508 条、CLAUDE 写 192 条、实测 722 条 —— 同一个病。

### 6.2 【高】同一条复合命令里的「先改后测」被判成「编辑后没重跑」

`scripts/verify-claims.mjs:1052`

```js
const after = (i) => i > (ev.lastEditIndex ?? -1);
```

`buildEvidenceIndex` 把 shell 命令的副作用当编辑（`verify-claims.mjs:857`，
`edits.push({ index: use.index, ..., via: 'shell', kind: shellEditKind(use.cmd) })`）。
当一条复合命令里**既改了源码又跑了测试**，两者共享**同一个 record index**，
`i > lastEditIndex` 判假 → `STALE_ONLY`。

复现（`76bbe070`，index 8068，原文）：

```
cd "…/Let-s-learn-English--1" && cp /tmp/AR6.bak src/main/java/…/AchievementRepository.java
&& grep -c MUTATION … && JAVA_HOME=… mvn.cmd -o clean test 2>&1 | grep -E "Tests run:…"
→ 输出：「Tests run: 614, Failures: 0, Errors: 0, Skipped: 0 … BUILD SUCCESS」
```

`cp` 和 `mvn test` 在同一条命令里，`lastEditIndex == successIndexes.last == 8068`。
hook 的结论：**「有 40 次成功的测试运行，但都发生在最后一次编辑之前（编辑后没重跑）」→ 拦截。** `[实测]`

量化：**28 / 701（4.0%）的可拦断言**是这一类。修法只有一行（`>=` 或按 record 内 block 顺序判），
但在修之前，它会稳定地冤枉「按正确顺序做事」的会话——**这正是产品的目标用户**。

### 6.3 【中】「最后一次编辑」把 shell 副作用一律当源码改动

`151 / 701（21.5%）` 的拦截把「最后一次源码编辑」指向一条 shell 命令，其中大量是
`cat >> scripts/xxx.test.mjs <<'EOF'`（写测试文件）、`sed -i` 改 `docs/README.md`、
`cp x /tmp/x.bak`（备份）。`[实测]`

`CODE_EXTS` 排除 `.md` / `.txt` 的设计是好的（注释里写了理由），但 `shellEditKind()` 只能从命令文本猜目标，
猜不到写的是测试文件还是文档。后果与 6.2 同向：把「改了测试之后跑测试」判成「改了代码没重跑」。

### 6.4 附带：产品形态与实现互相矛盾

- 方案 A 写「**用户零配置：装完即用**」；实现要求合并 settings + 换绝对路径 + `export OVERWATCH_STOP_VERIFY=block` 三步。
- `templates/stop-verify-hook.settings.json` 自己写明：「**不要用 `${CLAUDE_PROJECT_DIR}`**，
  它指向被 hook 的项目根，不是本仓库」「换成你自己机器上 overwatch 的路径」。
- 也就是说：**它现在只能装在自己的仓库上**，不能分发给别人而不让人手改路径。
  「零配置」不是待实现的特性，是当下不存在的东西。

## 7. 结论与改法

### 7.1 明确判断：**不该做**（作为独立的 Stop hook 产品形态）

三条独立的理由，任何一条单独成立都足够：

1. **痛点错位（§2.3）**：93.7% 的可拦时刻在会话中段，用户不在读；真正读最后一句话的时刻只占 6.3%，
   且那 6.3% 里只有 4/37 次用户想要「继续」。闸门命中的是产品想象中的用户，不是实测用户。
2. **需求证据被自身实验污染（§1.2a）**：「37 条 NO_EVIDENCE」里 43 条来自它自己的靶场，真实语料 2 条。
3. **自陈述证据不可信（§6.1）**：14.9% 的拦截建立在「整个文件范围内没有任何…」这种它做不到的断言上。

### 7.2 但有一套能力值得留下——**换成「标注」而不是「拦截」**

同一套 `detectClaims / findEvidence / classifyEvidence`，我建议的形态是：

**不拦回合、不改写 reason、不要求模型补证据。** 在会话结束（或会话空闲超过 N 分钟）时，
对用户可见的位置**追加一行判定**，例如：

```
⋯ 本次收尾含 3 条完成性声明：2 条有证据（编辑后有 1 次成功测试）、1 条无法核对（测试跑在后台，无退出码）
```

理由（每条都对着上面某一条失败模式）：

| 改成标注，解决什么 | 对应问题 |
|---|---|
| 不阻塞 → 零轮次成本、零误拦代价 | §4.1 的 37.6k token / 次；误拦从「事故」降为「一格字」 |
| 可常驻 → 覆盖会话中段的 93.7%，而不只是末尾 6.3% | §2.3 |
| 显式写出「1 条无法核对」→ 不制造「已全覆盖」错觉 | §5.3 的 N=180 风险 |
| 不需要用户配 `block` 模式 → 「装完即用」成立 | §6.4 |

**这是「难度更低、覆盖率更高、成本更低、风险更小」的四个方向同时改善，不是折中。**
代价是失去「强制模型改口」这个唯一的净增值——e2e 里那 2 次。我认这个损失，
因为那 2 次换来的是 1700 万 token 与 458 次打断。

### 7.3 如果坚持要做闸门，先过这四道门（缺一不可）

1. **修 §6.1**：`verdictFor` 必须接收并使用 `truncated`。加负向测试：喂一个 20 MB transcript，
   断言 reason 不含「整个文件范围内」。
2. **修 §6.2 / §6.3**：同 index 的 shell 编辑与测试按 block 顺序判；`shellEditKind` 必须区分
   测试文件 / 文档 / 备份。
3. **只拦会话最后一次 `end_turn`**（`stop_hook_active === false` 且后面没有新人类回合）。
   这一条把拦截量从 458 降到 37（−92%），同时保住全部「用户会读到」的场景。
4. **删掉「零配置」这个说法**，或者真的做成插件（`hooks/hooks.json` + 相对路径）。
   在做到之前，产品文案不许写这四个字。

### 7.4 该做什么（如果资源只有一份）

**把资源投到「事后对账 + 变化检测」，不要投到「实时闸门」。**

理由是硬数字：

- 用户真正愿意付的时机是「离开 72 分钟后回来」（相邻真人消息间隔 p50 72 分钟，52.6% > 1 小时）。`[引用]`
- 那个时机要的是「跟我走的时候比，变了什么」，而不是「刚才那句话有没有证据」。
- `verify-claims` 已经能在 5.6–9.1 s 内给出可反驳的输出（原话 / 证据 / 时间线 / 建议 / 退出码），
  **它缺的是一次「diff」而不是一次「gate」**。

一句话：**这个项目最值钱的能力已经存在了，方案 A 是在给它加一个它不需要的触发方式。**
