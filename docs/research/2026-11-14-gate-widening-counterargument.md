# 锐评：把写前闸改宽到 3-5% 是个错的决定

- 日期：2026-11-14
- 作者：锐评 Agent A3（对抗角色，职责是攻击这个决定，不是配合它）
- 产出形态：exploration（本文件；无脚本、无测试、不改任何既有文件）
- 攻击对象：**把 `scripts/pre-write-gate.mjs` 的判据改宽，把 19.9% 的拦截率降到 3-5%**
- 语料快照：`~/.claude/projects/` 下 **432 份主 transcript / 2.0 GB**，fork 去重后 407，真实项目会话 232（有写 136），测试沙箱 175（有写 66）
- 复算：`node scripts/observe-reality-check.mjs --threshold N --json`（N=0/1/2/3/5）

> **语料是活的。** 写本文期间另一个会话仍在往里追加 transcript，同期运行的两个同事脚本
> （`scripts/measure-gate-ceiling.mjs`、`scripts/redteam-gate-widening.mjs`）读到的是 438 份、
> 沙箱 67~68 个。**本文所有比率都锁定在我这一轮（432/407/136/66）**，与他们的绝对数差 1~2 个会话，
> 比率同量级，方向一致。凡引用他们的数都注明出处。
>
> **本文里标「本文自算」的数字没有现成脚本可跑**——判据在正文里逐条写清，任何人用
> `analyzeOne()` + `gateReadsOf()` + `tailGateReads()` 复现即可。标「复算」的给出命令。

## §0 一句话结论

**不该改宽。** 这个决定在做一件错的事：它把「19.9% 太高」当成前提，然后用改判据去凑一个没人测过的
比率目标；而真正的问题定义（闸门数的是「读过几个文件」，不是「读没读懂要改的那个」）一旦修对，
拦截率会**升到 67.6%**，不是降到 3-5%。所以该做的决定不是「怎么把数字降下来」，是
**「这个闸还要不要装」**——而在现有证据下，答案倾向于「不装」。

## §1 这个闸门到底在解决什么问题

### 指控

**没有人报过这个怨。** 闸门防的是「没读就写」，而语料里没有一条用户投诉指向「你没读就写」；
唯一一条能被算成「纠正」的，是用户自己点错了 Stop 按钮。一个没人抱怨的问题，不该用
19.9% 的会话去换。

### 证据

**① 用户真正的介入里，纠正只占 0.87%。** 引用 `docs/research/2026-11-14-intervention-cost.md` §2.3 / §3.5：
1727 次执行期中断里只有 15 次是纠正（0.87%），最大的一块是「新增需求、补充前提」（1379 次）。

**② 被拦的那 27 个会话，纠正率比放行的还低——而且那两条「纠正」是假的。** 本文自算（判据：
`intervention-cost` 同款 `humanTurnText()` + `classifyHumanMessage()`，窗口 = 首写之后到文件尾）：

| 组 | 会话 | 执行期中断 | 纠正 | 纠正率 | 其中真返工投诉 |
|---|---|---|---|---|---|
| 会被拦（`gateReads<3`） | 27 | 391 | 2 | **0.51%** | **0** |
| 会放行（`gateReads>=3`） | 109 | 1778 | 17 | 0.96% | 未逐条核 |

被拦组那 2 条纠正逐字相同，来自同一任务的两个 fork：

```
刚才我不小心点错了，点到stop this task
```

这不是「AI 没读就写导致返工」，这是用户误触停止键。**被拦组里真正的返工投诉是 0 条。**
方向也与假设相反（0.51% < 0.96%），但两组样本都太小，谁也不足以证明什么——只能说**没有证据支持**。

**③ 全语料搜索「抱怨没读」：0 命中。** 本文自算，436 份 transcript 的全部人类发言（排除 `tool_result`），
正则 `/(你没读|没读过|看都没看|不读就|没看代码|没看文件)/` 与 `/(先读一下|先看一下|你读一下)/`
各 **0 命中**。对照组：正则 `/(已经有|重复实现|重复造)/` 有 19 命中，但抽看的样本里
3 条是 `task-notification` 的系统文本、1 条是用户要求模型复述 CLAUDE.md，**没有一条是投诉**。

**④ 宿主自己已经有一道「先读才能写」的门，而它几乎从未被触发——因为模型本来就会先读。** 本文自算：
435 份主 transcript 里，**16,729 次 `Edit` + 5,813 次 `Write`** 中，宿主返回
`<tool_use_error>File has not been read yet. Read it first before writing to it.</tool_use_error>`
共 **3 次**（3 份不同会话，全部是 `Write` 到已存在但没读过的文件）。分成两半看，信息量更大：

- **16,729 次 `Edit`，0 次读取门错误。** 模型在改文件前**已经读过**，几乎无例外。
  这是本闸核心假设的**反面证据**：不需要外部强制，这个行为已经自然发生了。
- `Write` 侧 3 次 / 5,813 = 0.052%，全都是「覆盖一个已存在但没读过的文件」。

也就是说：**「没读就写」在文件粒度上的发生率是 0.013%**。本闸想做的是在
「读过几个无关文件」这个更弱的粒度上再拦一遍，发生率 19.9%——**两个数字差 1500 倍**，
说明闸门测的不是它声称在测的那个行为。

**⑤ 「写之前」这个窗口本来就极小。** 引用 `docs/research/2026-11-13-critique-question-layer-product.md` §1：
828 次介入里只有 68 次（8.2%）发生在第一次写文件之前。闸门只在「第一次写」那一刻动作，
天花板就是把力气投在这 8.2% 里。

### 被攻击方能怎么反驳

1. 「用户不会说『你没读』，只会说『你做错了』。返工正则召回率低，0 命中不等于没发生。」
2. 「闸门是**预防**，不是统计投诉。预防的价值不能靠投诉计数衡量。」
3. 「宿主那道门只挡 `Write` 到已存在文件，管不了 `Edit`，也管不了新建文件。」
4. 「0.87% 的纠正率恰恰说明**用户的容忍度极高**，所以加一道闸的边际成本低——拦错了也不痛。」

### 我的回应

1. 反驳 1 是对的，但它伤的是**你的结论**，不是我的：如果连「没读就写」都数不出来，
   那「改宽判据能让情况变好」也没有可观测的判据。你要么承认这条因果链不可测，
   要么给出一条可测的（§7 给了三条）。
2. 「预防」必须给出因果链：**write-first → 返工**。我测了，方向相反。而且被拦组那 2 条
   「纠正」是误触 Stop —— 说明这个语料里连「疑似 case」都得靠误判凑。
3. 这一条是最强的反驳，我承认它成立**一半**：宿主那道门确实只覆盖「写已存在文件」的一个子集
   （3 次里有 1 次是 `MEMORY.md` 这种已有文件）。但它说明的是**判据应该按文件锚定**，
   而这恰好是 §3 的论点：按文件锚定会让拦截率升到 67.6%，不是降到 3-5%。
4. **反驳 4 反而拆掉了这个决定的前提。** 如果容忍度极高，那 19.9% 就不构成必须处理的问题；
   如果 19.9% 构成问题，那容忍度就不高。**这两个说法不能同时用来支持「改宽」。**
   成本到底多少还取决于一个决定里没写的参数（见 §2）。

## §2 19.9% 这个数字被用来支持什么

### 指控

**3-5% 这个目标不是从数据推出来的，而且「改宽判据」这条路到不了它。**
报告已经算过：四类扩宽全开是 **3/136 = 2.2%**，低于目标区间。也就是说，
「改宽到 3-5%」这个说法在数据上不存在对应的操作点——你要么只改一格（11%~19.9%），
要么全改（2.2%）。

### 证据

**① 单轴消融，没有一格落进 3-5%。** 本文自算（判据：在 `observe-reality-check.mjs` 的同一 1 MB 尾窗口上，
把「闸门认的读」与「结构性探索（`ls`/`find`/`grep`/`Glob`/`git`）」两种证据分别计数，再取并集）；
同事脚本 `scripts/measure-gate-ceiling.mjs` 的单因素消融给出同方向的数（该脚本快照 438 份，基线 27）：

| 变体 | would-deny | 占比 |
|---|---|---|
| 闸门原样（阈值 3） | 27 / 136 | **19.9%** |
| +C 结构性探索算读过 | 15 / 136 | **11.0%** |
| +B2 子 agent（宽松） | 17 / 136 | **12.5%** |
| +B 子 agent（严格） | 22 / 136 | **16.2%** |
| +A 续接上游（多候选并集，上界） | 24 / 136 | **17.6%** |
| **四轴全开** | **3 / 136** | **2.2%** |

**② 只动阈值也到不了。** 本文复算 `node scripts/observe-reality-check.mjs --threshold N --json`：

| 阈值 | 0 | 1 | 2 | 3 | 5 |
|---|---|---|---|---|---|
| 真实项目 would-deny | 0 | 13 (9.6%) | 22 (16.2%) | 27 (19.9%) | 52 (38.2%) |

**③ 唯一能落进 5% 附近的组合是「开 C + 阈值降到 1」**：本文自算并集口径下 7/136 = **5.1%**。
但那是「两个改动」，而且其中 6/7 个剩余会话全是「派过子 agent 但主线程没读」，
判据实际上变成了「你有没有派 agent」。

**④ 分母是混的。** 本文自算：136 个有写会话其实只有 **43 个任务簇**（按首条人类消息归一化），
**104/136 个会话落在 26 个多 fork 簇里**。27 个被拦会话是 **11 个任务**；
按任务算「至少一个 fork 被拦」是 11/43 = **25.6%**。所以「19.9%」既不是会话级误伤率
（报告的 §6.2 已明确它不是），也不是任务级发生率——**它是一个没人定义过的混合口径**，
而被直接拿去当「拦截率」用了。

**⑤ 决定里没写 `brake`，而两种 `brake` 的代价差一个数量级。** 见 `scripts/pre-write-gate.mjs:657`：
`halt`（默认）→ deny 同时 `continue:false`，**整个回合结束**，19.9% 的会话会在第一次写时被打死；
`budget` → 前 N 次不刹车，代价是一到两次往返。前者是「五分之一会话被砍」，
后者是「中位会话从 16 次介入变 17 次」（+6%）。**同一个 19.9% 在这两个口径下不是一个量级的事，
而决定没说是哪个。**

### 被攻击方能怎么反驳

1. 「3-5% 是个产品目标，不是从这份语料推出来的。目标是『误拦率低到用户感觉不到』。」
2. 「2.2% 也在可接受范围内，低一点没关系。」
3. 「19.9% 是按会话算的，被拦的会话本来就不多——27 个。」

### 我的回应

1. 那就请把产品目标的**来源**写出来。「用户感觉不到」需要一个可观测的阈值定义，
   而现在仓库里唯一相关的实测（`intervention-cost`：0.87% 的介入是纠正）说的是
   **用户的容忍区间比 19.9% 和 5% 都宽**。目标没有锚，就不能拿它去驱动改判据。
2. 如果 2.2% 可接受，那这个决定的实际内容是「把闸门削到基本不拦」，不是「改宽」。
   那就应该照实写在决定里，并且回答：一个在 136 个会话里只拦 3 个的闸，值不值 §4 里
   那笔 I/O 与验证代价。**用「降到 3-5%」包装「削到 2.2%」，是让决定看起来比它实际温和。**
3. 27 个本身不是问题；问题是这 27 个里 **24 个（88.9%）** 在拦的时候项目已经被读过
   （`observe-mode-reality-check` §5.1，我复算一致：A 5 / B 5 / B2 8 / C 6 / D 3）。
   一个「正确率 11%」的判据，改宽只会让正确率往下走。

## §3 「改宽」是不是在解错题

### 指控

**是。** 这条指控最硬的地方不是「判据太严」，是**判据的锚点错了**：
它数「读过几个不同文件」，而用户关心的是「有没有读过要改的那个」。
把判据改宽只会让它**数得更多**，不会让它**数得更准**——**这是在加固一个错误的抽象。**

### 证据

**① 读了目标文件本身，照样被拦。** `aed8ec22` / `ea338c0e`（同一目标 `pom.xml`，
同样的两步序列 `Read pom.xml` → `Edit pom.xml`）：`gateReads = 1`，被拦。
这两个是报告 §5.2 自己认定为「真误伤」的那两个。它们的问题不是「读得太少」，
是**「读的那个文件不算数」**——阈值 3 与「读了什么」无关，只与「读了几个」有关。

**② 修对抽象会让拦截率升 3.4 倍。** 本文自算：把判据换成「首写之前读过目标文件本身，
**或**目标所在目录被探索过」，真实项目 **92/136 = 67.6%** 会被拦。
（判据：`pathKeyOf(首写目标)` 精确匹配，或任一读/探索路径以 `dirname(目标) + '/'` 开头。
粒度粗，方向可靠。）

这组数放在一起，结论只有一个：

```
「19.9% 太高」                 → 要求判据更宽
「判据锚点错了」                → 要求判据换锚点，换完是 67.6%
两条诉求不能同时满足。改宽满足的是前者，而且是以牺牲后者为代价。
```

**③ 被拦的 27 个里 24 个的读取证据在闸门结构上看不见——那不是「判据太窄」，是「信息不在这个文件里」。**
A 类（续接会话）的读在上一段 transcript、B/B2 类（子 agent）的读在另一个文件、
C 类（结构性探索）的读取**根本不构成「读过内容」**（报告 §6.3 自己写明：
「一次 `ls` 不等于读了文件内容」）。把 C 类算成「读过」，是在判据里写进一个已知为假的等价。

### 被攻击方能怎么反驳

1. 「67.6% 是你的判据太严（要求目录完全前缀匹配），换种实现会低很多。」
2. 「目标不是『读过目标文件』，是『对这个项目有个基本认知』。要求读 README/CLAUDE.md + 2 个源码文件，就是这个意思。」

### 我的回应

1. 承认粒度问题：如果把「目录探索」放宽到「任意一次在同仓库内的探索」，数字会降。
   但请注意这一点本身证明了 §3 的指控——**67.6% 与 9.6% 之间的差异，全部来自「怎么算探索」的定义**，
   而不是来自「AI 到底读没读」。一个判据的结论对定义这么敏感，说明它测的不是那个东西。
2. 反驳 2 是**唯一能救这个闸的说法**，而且它是可以测的：把判据换成
   「首写前必须读过 `CLAUDE.md` 或 `README.md`（若存在）」——这是原型的 §6.6 与
   `observe-mode-reality-check` §6.5 都点名「两轮都没做」的那一条。
   **这是唯一一个既能收紧锚点、又可能真的降低拦截率的改法。** 它没被放进候选，
   而「改宽四种判据」被放进了候选——这本身就是决定在解错题的证据。

## §4 纯函数性被破坏的代价

### 指控

**引入 I/O 之后，「改宽后只剩 4%」这句话将不可验证。** 而不可验证的改进，比不改更贵——
它会永久性地关掉这个仓库唯一能评估这个闸的仪器。

### 证据

**① `decide()` 现在是纯函数**（`scripts/pre-write-gate.mjs:552` 的文件头明确写「纯函数：不读盘、不写盘、
不读环境变量」，副作用全在 `runHook()`）。A/B/B2 三类扩宽都要求它读**别的文件**：
子 agent transcript（`<session>/subagents/*.jsonl`）与上游会话。

**② 那笔 I/O 有多大。** 本文自算（136 个真实有写会话）：

| 指标 | 值 |
|---|---|
| 有子 agent transcript 的会话 | 96 / 136 |
| 子 agent 总量 p50 / p90 / max | **13.5 MB / 132.7 MB / 428.4 MB** |
| 全语料子 agent 总量 | 6.1 GB |
| 最大单个子 agent 目录 | 243 文件 / 428.4 MB，全量 `JSON.parse` **5.35 s**（≈80 MB/s） |
| 若「每次写都扫子 agent」× 被拦的 27 个会话（4266 次写） | **430 GB 累计读，约 92 分钟** |

**③ 更要命的是：`observe` 模式永远不会写标记，所以评估期每次写都要重读。**
`decide()` 的 observe 分支返回 `markWrite: null`（`pre-write-gate.mjs:633-636`），
`runHook()` 只在 `out.markWrite` 存在时落盘（`:764`）。所以 `observe` 下**通篇没有标记**，
每写一次跑一次 `getReads()`。现行 1 MB 尾读实测 16~34 ms，可接受；
换成子 agent 全扫就是**秒级**，而且正好落在最需要免费的评估阶段。

**④ 重放器和闸门本来就是两份解析器，改宽只会让它们分叉。**
`scripts/observe-reality-check.mjs:62` `import` 了 `readTranscriptReads` 但**从未调用**
（全文只有这一处出现）；重放器用的是自己那份 `gateReadPathsInText()`（`:423`）
配自己那份读动词表 `GATE_READ_VERBS`（`:67`）。

实测证据（本文自算，同一份真实 transcript、同一个 1 MB 尾窗口）：

| 会话 | 改宽后的闸门 `readTranscriptReads` | 重放器 `tailGateReads` |
|---|---|---|
| `2562780d` | 19 | 4 |
| `61fe6d9f` | 23 | 2 |
| `d3b951b4` | 34 | 2 |
| `4d15fd65` | 40 | 10 |
| `57af6178` | 21 | 6 |

**⑤ 我今天把闸门的 `SHELL_READ_VERBS` 追加 `grep/ls/find/git`（仅临时副本，未改仓库），然后：**

```
node --test scripts/pre-write-gate.test.mjs scripts/observe-reality-check.test.mjs
→ tests 92 / pass 92 / fail 0        ← 一条都没红

node scripts/observe-reality-check.mjs --threshold 3
→ gate 口径 would-deny 27 / 136 = 19.9%   ← 一个数都没动
```

**测试全绿 + 报告数字不变 + 闸门行为变了。** 这就是「改完之后无法验证」的实物。

**⑥ 那条被当作「防漂锚」的测试，名字比它证明的多。**
`scripts/observe-reality-check.test.mjs:154` 叫
「`tailGateReads` 与闸门自己的 `readTranscriptReads` 在同一切口上给同一个数」，
但函数体里比较的是 `tailGateReads(p, size)` 与 `gateReadPathsInText(readFileSync(p))`
——**两个都在重放器文件里**。它从未调用 `readTranscriptReads`。
所以它证明的是「重放器与自己的一致」，不是「重放器与闸门的一致」。

**⑦ `verdict()` 那条「真 `decide()` 复算」对解析器是同义反复。** 它把
`readPathsWindow` 注入 `state.reads`（`:534-538`），而 `decide()` 见 `state.reads` 就直接用
（`pre-write-gate.mjs:607-609`），`transcript_path` 根本不会被读。实测：

```
evidence 数组 5 条 + transcript_path 指向一个不存在的文件 → {decision:"allow", reads:5}
evidence 数组 0 条 + 同上                                → {decision:"would-deny", reads:0}
```

它守的是「计数与阈值判断一致」（这条有价值，27 vs 26 那个 bug 就是它逮的），
**不是**「重放口径与闸门实现一致」。改宽之后，后者再没有任何东西守。

### 被攻击方能怎么反驳

1. 「把 I/O 做成可注入的：`decide(input, { getSubagentReads })`，纯函数性保住，测试照样能打桩。」
2. 「重放器可以改成直接调闸门的 I/O 路径，就不会漂了。」
3. 「92 条测试不红，是因为我还没写那几条测试。改完会补。」

### 我的回应

1. 这条成立，但代价要算清：hook 里一次 I/O + 重放器里一次 I/O = **两份实现必然漂**
   （④ 已经实测漂了，5 个会话里最大差 32 个路径）。要做对，重放器必须调闸门那条路径，
   于是重放不再是纯函数、阈值扫描要重扫 430 GB。**这不是「做不到」，是「成本没写进决定」。**
2. 同 1。另外请写明：改成调真 I/O 之后，`--threshold` 扫描一次要多久（现行 90 秒）。
3. 「改完会补测试」正是本锐评要拦的那件事：`observe-mode-reality-check` 的 26 条测试、
   `pre-write-gate` 的 66 条测试都没守住读动词表。补测试要靠**先声明判据**，
   而现在连「什么叫读过」都准备改成「`ls` 也算」。**先改判据再补测试，测试只会把新行为钉死。**

## §5 门槛降到 1 这个替代方案

### 指控

**同一个目标（降低拦截率）下，降阈值是一行常量改动，报告自己算过并推荐了；改判据是四个判据 + 三类 I/O。
决定选了后者，没有任何理由。**

### 证据

本文复算 `node scripts/observe-reality-check.mjs --threshold 1 --json`：

| | 阈值 3（现行） | 阈值 1（一行常量） |
|---|---|---|
| 真实项目 would-deny | 27 / 136 = 19.9% | **13 / 136 = 9.6%** |
| 归因分布 | A 5 / B 5 / B2 8 / C 6 / D 3 | A 1 / B 2 / B2 6 / C 3 / **D 1** |
| 沙箱阴性对照 | 49 / 66 = 74.2% | **48 / 66 = 72.7%**（判据没被削空） |
| `decide()` 复算一致 | 27 | 13 |
| 代码改动量 | —— | 1 个常量（`defaultConfig().minReads`，`pre-write-gate.mjs:115`） |
| 新增 I/O | —— | **0** |
| `decide()` 纯函数性 | 保住 | **保住** |
| 重放可验证性 | 保住 | **保住** |

`docs/research/2026-11-14-observe-mode-reality-check.md` §7 原文：
「把阈值降到 1，拦截率 9.6%、假阳性区几乎消失 —— **这是数据支持的更优门槛**。」

### 被攻击方能怎么反驳

1. 「9.6% 还是高于 3-5% 的目标。」
2. 「阈值降到 1 会让闸门挡不住『真的一行没读就写』——`D-no-evidence` 从 3 掉到 1，但真实项目里读 0 个的有 13 个。」

### 我的回应

1. **这正是本锐评的核心**：如果 9.6% 也不行，那说明问题不在阈值、不在判据，而在目标本身没有依据
   （§2）。一个「必须落到 3-5%」的硬目标，把一个「一行改动、零新增风险」的方案排除在外，
   却把「四判据 + 三类 I/O + 失去可验证性」的方案选进来——**决策理由必须写出来，
   否则这不是技术选择，是先有结论再找手段。**
2. 反驳 2 说反了：阈值 1 的判据是「至少读过 1 个文件」，它挡的正是「一行没读」；
   阈值 3 额外挡的 14 个会话，按报告自己的归因全是「读在别处」。**阈值 1 更贴近闸门声称要做的事**
   （「第一次写之前先证明你读过这个项目」= 至少读过 1 个），反而更自洽。

## §6 反方向攻击：现在派 Agent 改宽，最可能出现的三种失败

以下三条都假设「改宽」已经派出去了。每条给**可观测的早期信号**——在改动落地当天就能看出来的那种。

### (a) 改完测试全绿，但行为没变（重放器和闸门用了不同数据源）

**已实测复现**（§4 ⑤）：把闸门读动词表扩宽后，92/92 测试全绿，重放器仍报 27/136 = 19.9%。

**早期信号（改完当天，按顺序跑）：**

1. `node scripts/observe-reality-check.mjs --threshold 3 --json` 的 `deny` / `attribute` 逐字段
   与改前**完全相同** → 改动没触达被测量的那条路径。
2. `grep -c "readTranscriptReads" scripts/observe-reality-check.mjs` 仍为 `1`（只有 import 行）
   → 重放器还是没调闸门的读函数，两份解析器仍在各自演化。
3. 拿一条**含 `ls`/`grep`/子 agent 读**的真实 transcript，分别喂 `readTranscriptReads()`
   与 `tailGateReads()`，路径数不相等 → 已分叉，此时报告里的任何比率都只描述重放器，不描述闸门。

### (b) 改完闸门永远不会拦（判据被削弱到恒真）

**形态已经算出来了**：把「结构性探索」与「子 agent 读」都算成证据、阈值降到 1，
剩下的 7 个真实会话里 **6 个是「派过子 agent」、1 个是「派了 agent 但子 agent 目录为空」**。
也就是说判据实际退化为「你有没有派过子 agent」——这与「读过项目」没有因果关系。

**更极端的对照实验（本文自算）**：把判据换成「首写前有过 ≥1 次任意非写工具调用」：

| 判据 | 真实项目 | 沙箱 |
|---|---|---|
| 「≥1 次任意非写工具调用」 | **0 / 136 = 0.0%** | 48 / 69 = 69.6% |
| 「≥3 次」 | 2 / 136 = 1.5% | 50 / 69 = 72.5% |

**判据对真实项目恒真、对沙箱仍然正确**——也就是说阴性对照**不会报警**。

**早期信号：**

1. 沙箱桶拦截数掉到 **< 30 / 66**（现行 49）→ 判据已被削空。这是唯一有效的负向对照，
   而它只有 66 个会话、4 种 prompt 模板，本身就弱。
2. 真实桶 < 5% 而沙箱桶仍 > 70% → 判据不是「判别力变强」，是「对真实项目不适用」。
3. 剩余被拦会话里 **> 80% 带 `agentCalls > 0`** → 判据已退化为「派不派 agent」的代理变量。
4. 假装装上 `deny` 模式跑 20 个真实会话，一次都不拦 → 恒真确认。

### (c) 改完 `observe` 日志失去分桶能力，再也没法评估

**为什么会发生**：`observe` 日志的评估能力来自三个可对照的维度——`would-deny` 计数、
`attribute()` 五类归因、以及「同一份语料上用不同阈值重放」。改宽会同时动前两个：
新增 `subagentReads` / `upstreamReads` 字段（旧日志没有），并且 `attribute()` 的
A/B/B2/C 四类**必须重新定义**（C 类被吸收进判据后，「有证据但闸门不认」这个桶就空了）。

**早期信号：**

1. `tasks/runs/pre-write-gate/*.jsonl` 里同一天的记录出现**两种字段集**（有的行缺
   `subagentReads` 键）→ 跨天比较已失效，而报表不会报错。
2. 用改前/改后两版重放器跑**同一个 snapshot**：`gateReads` 分布不变、但 `attribute` 分布变了
   → 是定义漂了，不是行为变了。这种情况比行为变了更危险，因为它看起来像「改进生效」。
3. 「D-no-evidence」桶从 3 掉到 0 或 1，而真实项目里「读 0 个文件」的会话数**没变**
   → 分母没动、分子被定义吃掉了。

## §7 如果我错了：什么证据会让我改变结论

以下每条都是**可观测、可跑、有阈值**的。不需要「如果数据显示」，只需要照做。

| # | 观测 | 当前实测 | 让我改口的阈值 | 怎么测 |
|---|---|---|---|---|
| 1 | 语料里用户抱怨「没读就改」的发言条数 | **0 / 436 份** | **≥ 3 条**（非 `tool_result`，正则 `/(你没读|没读过|看都没看|不读就|没看代码|没看文件)/`） | 遍历全部人类发言，排除 tool_result，跑正则 |
| 2 | 宿主 `File has not been read yet` 错误数（分 Edit / Write 看） | **Edit 0 次 / 16,729；Write 3 次 / 5,813**（435 份） | **Edit 侧 ≥ 20 次**（说明模型确实会不读就改） | `grep -c "has not been read yet"` 汇总主 transcript，并回查同 `tool_use_id` 的工具名 |
| 3 | 被拦组的返工需求率 vs 放行组 | 0.51% vs 0.96%（无方向支持） | 被拦组 **≥ 1.5×** 放行组，且被拦组纠正 **≥ 10 条** | `measure-intervention-cost.mjs` 同款判据，按 `gateReads<3` 分组 |
| 4 | 「读过目标文件或其目录」的会话占比 | 只 **44 / 136 = 32.4%** 探索过目标目录，20/136 读过目标文件（**65.6% 没碰目标文件**） | 若 **> 90%** 的会话本来就碰过目标 → 按目标锚定不会有误拦，「不装」也没损失 | 同 §3 ② 的判据 |
| 5 | 真实 `deny` 模式下「拦住 → 用户紧接着纠正」的闭环 | **从未发生**（闸门从未在生产开过 `deny`） | 观测到 **≥ 1 次**真实闭环：被拦后 3 轮内用户发出含「不对/重做/改回」的消息 | 装 `deny` + `brake=budget` 跑一周，读 `tasks/runs/pre-write-gate/*.jsonl` 与对应 transcript |
| 6 | `measure-intervention-cost` 能否支持把「首写前是否读过」作为一个分组 | 现在分的是 A/B/C（按提问时机），**不含这个维度** | 若加上该分组后，被拦组返工需求率显著更高（置换检验 p<0.05，且返工事件 ≥30 条） | 扩 `measure-intervention-cost.mjs` 的分组维度 |

**特别声明**：#4 这条现在**指向我自己结论的反面**——我只测到 32.4% 的会话探索过目标目录。

我的判断仍然是不该**改宽**，理由是：**这个方向要求判据更严（67.6%），而不是更宽（3-5%）**。
若主线程的目标真的是「保证 AI 看过要改的东西」，那 §8 的第 4 项才是应该做的——
并且要准备好接受 67.6% 这个拦截率。

## §8 替代方案排序

排序依据：**证据支持强度 → 成本 → 可逆性**。1 最优，6 最差。

### 1. 不装（保持现状：模板在 `templates/`，不在任何 `settings.json` 里）

- 现状已如此（`.claude/settings.local.json` 无 hooks 段，`tasks/runs/pre-write-gate/` 为空）。
- 证据：语料里 0 条相关投诉、0 条真返工、宿主文件级门的 `Edit` 侧 0 次触发（模型本来就先读）。
- 成本 0，可逆（本来就什么都没装）。
- **这是本文推荐的一项。**

### 2. 只开 `observe`，**且明确不设拦截目标**，跑一周收「野生 would-deny」

- 价值在于它给出重放给不了的东西：真实会话里 `would-deny` 之后，模型和**用户**分别做了什么。
- 成本：`observe` 下不写标记（`pre-write-gate.mjs:633`），**每次写都重读 1 MB**，
  实测 16~34 ms/次。136 个会话 21,166 次写 ≈ 20.8 GB 累计读，可接受。
- 注意：样本量决定了它不会快——`would-deny` 只发生在首写那一刻，即每会话最多 1 次。
- 这是 §7 第 5 条的**前置条件**：不装 `observe` 就永远没有野生样本。

### 3. 阈值 3 → 1（一行常量）

- 19.9% → **9.6%**，沙箱对照 72.7% 不变，零新增 I/O，`decide()` 保持纯函数，重放仍可验证。
- 这是报告自己推荐过的、数据支持的方案，却不在候选里。
- 若必须有「拦截」这个功能，选它。

### 4. 换锚点：判据从「读过几个文件」改成「读过要改的那个文件（或其所在目录）」

- 这是**修对抽象**的那条路，而不是改宽。
- 代价：拦截率会到 **67.6%**（本文自算），必须先重新论证「67.6% 可接受」。
- 与宿主已有能力重叠：宿主已经在「写已存在文件」这个粒度上拦（`Edit` 侧 0 次 / `Write` 侧 3 次），
  本方案只补上「新建文件 / `Edit`」这两块。
- 这条不是「降低成本」的方案，是「换问题」的方案。**选它之前要重新写目标，不能沿用 3-5%。**

### 5. 只开 C（结构性探索算「读过」）

- 19.9% → **11.0%**（本文自算 15/136；同事 `measure-gate-ceiling` 同值）。
- 零 I/O，不碰纯函数性，改动集中在一处动词表。
- **但方向上是错的**：原型 `pre-write-gate-prototype` §1.3 明文写过「`grep` / `ls` 不算读过——
  看了文件名不算读了内容」，`observe-mode-reality-check` §6.3 也重申过。
  开 C 等于把一句已知为假的等价写进判据。排在这里只因为「若非要改宽」，它是最小的一刀。

### 6. 四轴全开（A + B + B2 + C）

- 19.9% → **2.2%**（本文自算 + `measure-gate-ceiling.mjs` + `redteam-gate-widening.mjs` 三者一致 = 3/136）。
- 代价：引入子 agent 与上游会话的 I/O（被拦的 27 个会话按「每次写都扫」折合 **430 GB / 约 92 分钟**）；
  `decide()` 失去纯函数性；重放器必须复制 I/O 路径，于是「改宽后只剩 X%」这句话的来源
  与被部署的代码不是一份（§4 ④ 已实测分叉）。
- 而且它**落不到 3-5% 的目标区间**——它落到了 2.2%，比目标更激进。
- **最贵、最不可验证、且与自己的目标不符。这是本文明确反对的那一项。**
