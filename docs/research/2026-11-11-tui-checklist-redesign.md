### 1.4 部分异常态（1 项有事、2 项没事）

```
 声明对不上   ✗ 1 条完成声明无证据支持 · 7 条存疑 · d 看证据
 后台监视     ✗ 监视未在跑（jobs 1.3d / probe 1.3d 未更新） · 先修这个
 ✓ 其余 1 项没有发现
```

压掉的项**被数出来**了。这是本重做里最容易做错的一处：`continue` 掉零值行之后若不收尾，
「压掉」与「没查」就同形了——那正是逆向报告 §3.4 反复强调的那条线。

## 二、判决句怎么和 L0 协调

**结论：不并列，分层。**

试过的两个方案，都否掉了：

- **A. 把「4 项检查都清白」接到 L0 后面**：
  `0 件在等你 · 10 个会话在跑 · 19 个已停 · 4 项检查都清白`。
  问题有二：① 它把两种不同性质的事实（会话计数 / 证据覆盖）塞进同一句；
  ② `verdictLine` 用 `joinWithin` **从尾部丢项**，60 列以下这句必然被丢掉——
  那是**静默丢掉自证**，比不写更糟。
- **B. L0 一句判决 + 检查区再一句「✓ 4 项检查都清白」**：正常态就成了两句判决，
  正是用户说的「突兀」的另一种形态。

**最终形态**：L0 管「会话有几件」，检查区管「凭什么说没事」，两者各说各的，不重复任何数字。

- 有异常时：异常项逐行给断言 + 出路，末尾补 `✓ 其余 N 项没有发现`。
- 全绿时：检查区只剩一句 `✓ 4 项检查都清白 · 监视在跑`。
  它不是第二句判决，它是**那句判决的依据**；而且「监视在跑」逐字出现，
  因为健康时它是最容易被计数吞掉的那一项（逆向 §3.3 第 3 条）。
- 全部为零**绝不留空**：空白会让「全清白」与「没查」同形。

## 三、实现

### 3.1 `scripts/tui-layout.mjs`

| 函数 | 变化 |
|---|---|
| `checklistRows()` | 形状不变（恒 4 行，四道数据源一条不砍），每行新增 `kind` 与 `data`；句子由下一个函数统一产出 |
| `checklistSentence(row, {wide})` | **新增**。双版本 `label` 写法：有发现时说事实（`2 个会话问了没答`），无发现时说短句（`没有会话问了没答`），**永不写 `→ 0 个`** |
| `isQuietRow(row)` | **新增**。只有 `tone === 'ok'` 算「查了、没发现」。`muted`（还在算）与 `bad`（读不到 state.json）都**不算**——搞反了就是把「不知道」说成「清白」 |
| `checklistSummaryLine(count, {rest, extra})` | **新增**。收尾句：`✓ 4 项检查都清白` / `✓ 其余 2 项没有发现` |
| `checklistLines(rows, {cols, layout, useColor, skipKinds, extra})` | **新增**。决定哪几项上屏；返回 `{lines, hidden, quiet}`。`quiet` 只取决于「有没有非绿项」，**与 `skipKinds` 无关** |
| `checklistLine(row, {cols, layout, useColor, wide})` | **重写**。` 标签` + 1 列字形 + 一句断言，两段落，无右对齐列；`budget < 14` 时只留标签与字形 |
| `checklistHeaderLine()` | **删除**。它唯一的职责是画那对元表头 |
| `composeListScreen()` | 去掉表头那一行；改调 `checklistLines()` |
| `STAGES` 的 `showCheckSource` | 语义改为「检查项句子里是否保留『凭什么这么判』的括注」（不再是一整列） |

`skipKinds` 的默认值是 `['inbox']`：它的数字就是 L0 的第一位，下面还有整段需动作原文。
交互屏在 `alert`（监视未跑的告警）存在时再追加跳过 `health`——那条告警已经给了原因
与修复命令（`node scripts/install-watcher.mjs install`），再画一行是同一句话的第二遍。

### 3.2 `scripts/oversight-tui.mjs`

- `printPlain()` 与 `composeListScreen()` 现在**共用同一套呈现**。旧实现两条路径各写一份
  （一条 `checklistLine`、一条手拼 `padDisplay('检查了什么', 51)`），同一个概念两套文案。
- `--plain` 在判决行下面那行补上 `· 数据 8s前`（交互屏该位置是右对齐的 `8s前扫描`）。
  优先用 `opts.lastSuccessAt`，拿不到就退回 scan 自报的 `generatedAt`。
- 全绿态在收尾句下面多给一行 `依据：inbox · asked · verify-claims · health`。

### 3.3 保留（逆向报告明确说这是我们的优势，不是缺陷）

1. **常驻性本身** —— 它监控用户看得见的对话框（随时可敲 `/status`），我们监控看不见的后台进程。
2. **「数据多新」** —— 它只在诊断场景给 `Last update attempt`；我们常驻在判决行右侧。
3. **后台监视存活状态** —— 本机实测 jobs / probe 停过 31 小时，那是真实发生过的失效。
4. **失败项必带一条出路** —— `claude doctor` 是 `- <issue>` + `  Fix: <fix>`；
   我们的 `先修这个` / `d 看证据` 同构。

60 列以下有三条降级，顺序与 `STAGES` 同源：

1. 先撤句子里的括注（`（WAITING/BLOCKED/FAILED）` 这类「凭什么这么判」）；
2. 再截断正文，但**必须带 `… (+N 列)` 披露**（不静默切掉）；
3. 太窄只留标签与字形——硬塞会让一行变成 `… (+53…`，既不告诉读者发生了什么，
   也不告诉他丢了多少。细节在 `d` 里。

全绿句 ` ✓ 4 项检查都清白 · 监视在跑` 只有 28 列，44 列以上完整、20 列截成
` ✓ 4 项检查都清白 ·…`——**任何时候都不是空行**。

## 六、没做 / 不确定的

1. **没有目视验证交互屏**（无 pty）。所有宽度结论都用 `displayWidth` 逐行量过，
   但「Windows Terminal + Cascadia 在 76 列下换行有没有视觉抖动」没看。
2. **颜色未目视验证**。`✗` 红 / `·` 黄 / `…` 灰 / `✓` 绿 走的是既有 `paint()`，
   未改配色表；但「四种 tone 在同一段里离得够远、不刺眼」是审美判断，不是断言。
3. **`checklistSentence` 的措辞没过用户验收**。文案是照逆向结论写的
   （双版本 label、无发现一句短句），但具体字眼（`没有会话问了没答` vs `问了没答 没有`）
   仍有取舍空间。
4. **`skipKinds` 的默认值 `['inbox']` 是判断，不是事实。** 理由写在注释里
   （L0 第一位 + 需动作原文已覆盖），但「0 件在等你时是否仍要画一行 `没有会话在等你`」
   是个产品取舍，我选了不画。
