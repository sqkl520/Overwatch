# 苛刻用户评审：Overwatch 凭什么值得装

> 角色：批判 Agent X3。立场：**每天开 15 个 Claude Code 会话的资深开发者，在 HN 上第一次看见这个项目。**
> 产出形态：`exploration`。不修改代码、不碰 git。
> 全部结论基于 2026-11-11 在本机上的**真实运行输出**，不转述 README。凡我给不出实测的地方，明确标「未实测」。

---

## 0. 一句话

**这个项目最大的问题不是功能不够，是它自己就是它要治的那个病。**

它卖的是「AI 说它做完了，得拿证据核对」。而它自己的 README 写「508 条回归测试」，实测是 **722 条**；它自己的 CLAUDE.md 还写着 **192 条**。三个数字，同一件事。

它卖的是「会话卡住一天没人发现」。而它自己的后台监视**已经停了 32 小时**，是它自己的界面把这件事显示出来的——**因为通知通道正是那个停掉的进程**。它不是发现了问题，是没法通知你。

---

## 1. 第一反应（刻薄版，逐字）

> 「又一张会话表。我 `claude agents` 已经有了一张，还不用我 clone 一个仓库、等 52 秒。」
>
> 「所以这是一个监控 15 个 AI 的工具，由一个 AI 写、由 AI 判定、它的自测数字在三个文件里写着三个值。我为什么要把我的会话交给它看？」
>
> 「README 里有一整节解释『为什么我不能自动接力』。花了三年做出来一个不能按的按钮，然后把『按不了』写成了设计哲学。」

第三句是最关键的：README 第 81–87 行整节论证「这不是缺陷，是平台的安全边界」。论证是对的，但**一个产品的卖点不能是「它做不到什么」的合理化**。用户不会因为你的诚实而装它，只会因为你需要它而装它。

## 2. 逐条质疑：每个卖点的「我为什么不需要」

### 2.1 「扫所有会话压成一张表」

**我不需要。** 实测对比（同一时刻，同机）：

| | `claude agents --json` | `scan-sessions --days 3` |
|---|---|---|
| 覆盖 | 15 条（busy 8 / idle 5 / blocked 2） | 33–43 条 |
| 耗时 | 15–23 秒 | **51.8 秒**（README 写 33 秒） |
| 能看到状态之外的? | 否 | calls / novelty / depth / tokens |

多出来的 20–28 条**没给我任何可执行信息**。看真实输出：

```
[EXPLORING] Projects/Overwatch         calls=  3734 ... idle=28.7h dormant
[EXPLORING] Projects/Overwatch         calls=     0 ... idle=28.6h cold-start
[EXPLORING] Projects/Overwatch         calls=     0 ... idle=28.1h cold-start
[EXPLORING] Projects/Overwatch         calls=     0 ... idle=28.0h cold-start
```

四行同名，其中三行 `calls=0`——**什么都没发生过**，却各自占一行、算进「已停 20+ 个」。我要的是「哪个在等我」，你给我 11 行一模一样的 `Projects/Overwatch`。这不是可见性，是**用 52 秒换一行噪声**。

致命的细节：`noun()` 把 `D--Projects-Overwatch` 压成 `Projects/Overwatch`，然后 `slice(0, 24)`。**11 个不同会话，项目名一模一样，我无法在表里区分它们。** 一个「把 N 个会话压成一张表」的工具，表里 11 行不可区分。

更荒唐的是这一行：

```
[PRODUCING] Projects/Overwatch   ... idle=-5s  persistent-change-in-window
```

**`idle=-5s`。** 负的 idle。同一屏还有 `-17s`、`-26s`、`-34s`、`-36s`（另一个项目也有 `-49s`、`-42s`）。原因是 `nowMs` 在扫描开始前取，`lastActivity` 读的是扫描过程中的文件，差值可能为负。TUI 的 `fmtDur` 有 `if (s < 0) return '0s'` 兜住了；**`scan-sessions.mjs` 的 `fmtDur` 没有**，直接印出 `-5s`。

这就是我第一眼会截图发到 HN 评论区的那个东西。

### 2.2 「检测 AI 谎报完成」

**这是它唯一有资格卖的，也是它最拿不稳的。** 我实测了：

```
合计 17 条可核对断言：9 SUPPORTED / 6 STALE_ONLY / 1 NO_EVIDENCE / 1 UNKNOWN
```

看着像那么回事，但细看：

**（a）6 条 STALE_ONLY 里，5 条是同一个项目的同一个会话连续报的。** 一个会话说「614 个测试全绿」，被判 STALE；同一会话的下一句「变异验证 5/6 变红」，也被判 STALE；「497 条测试全绿」又是一条。**AI 在一次长汇报里说了三遍类似的话，工具就把同一个「你改完源码没重跑」的事情说了三遍。** 用户看到「7 条存疑」，实际是**4 个关掉的项目会话**在报同一类事，全部不在线（实测 `claude agents` 里都没注册）。我不会去处理一个 3 天前关掉的会话的存疑。

**（b）唯一那条硬矛盾，可能是我自己的误报。** 实测原文：

```
AI 说：「M2 防刷与经济健康全部做完——开发、测试、真服验证、文档收口全绿」
证据：测试运行调用 0 次；最后一次源码编辑在 10-19 01:35
```

**这个会话是 Java 项目（Mentor-Express），跑的是 `mvn verify`，不是 `npm test`。** 而它的建议文案是硬编码的：

```js
const cmd = fam === 'test-count' ? 'npm test（或本项目实际的测试命令）'
```

工具认得 `mvn verify` 是测试（不然 `Let's learn English` 那 10 次成功测试从哪来），却在建议里让我「重跑 npm test」。**它的每一条建议都把它没读懂的项目当成 Node 项目。**

**（c）最根本的：它自己也承认精度 84.6%，样本 13 条。** 也就是说不装 `--include-subagents` 时，每 6–7 条里就有 1 条判错，而它**不会告诉你哪一条判错了**。我拿到「6 条存疑」，要自己把 6 个会话翻一遍才能知道是不是冤枉——**那我为什么不直接翻？** 工具的全部价值在于「省掉我自己看」，而它把最后那一步还给了我。

### 2.3 「检测问了没答」

**这里有两个检测器，在同一份数据上给出相反的答案。**

```
TUI --plain：   问了没答 · 3 个会话问了没答（transcript 末条是问句，之后没人回）
asked.mjs：     没有待回答的问题（扫了 249 个 transcript）
                已排除：开场客套 3，超过 24 小时 4，问句后自己继续了 1
```

我把 TUI 认为的那 3 条捞出来看了，**它们是真的在问我**：

- Hilltop Village：「要我跑一次 `clean package` 生成 JAR 吗喵？」
- PerfScope：「要我把 Release 说明的草稿写出来吗喵？」
- C盘空间：「需要我针对哪一项再细看吗？」

但它们的等待时长是 44 分钟、1.3 小时、1.8 小时；`asked.mjs` 排除的是**别的**会话，不是这 3 条（它 `tooOld` 4 个、`continued` 1 个）。两套口径互不可见。

而更要命的是：**TUI 数出这 3 条之后，列表页里没有任何标记告诉我哪 3 个是它们。** 我 grep 了全部代码，`meta.question` 只出现两处：一处在构造，一处在 `askedCountOf()` 里**计数**。它不渲染、不复用、不筛选。详情页 `detailLines()` 也没有「它问了你什么」这一行，只有 `最近说：`。

**结果就是：屏幕上写着「3 个问了没答」，我按 j/k 从头翻到底，找不到这 3 个是谁。** 一个用来「叫醒我」的功能，最后一步要我自己找。

### 2.4 「后台监视」

**我不需要常驻一个进程监控另一个进程——而且实测它已经死了 32 小时。**

```
后台监视  ✗ 监视未在跑（jobs 1.3d / probe 1.3d 未更新）· 先修这个
runner.log 最后一行：2026-10-31T19:22:58Z
state.json mtime：32.07 小时前
```

它确实诚实地说「监视未在跑」，`watch.mjs` 的 `healthCheck()` 还会说「进程可能还活着但卡住了，这恰恰是 DF-023 记的那类故障」。这句话写得很漂亮。

**但请把它读一遍：一个负责叫醒你的进程，靠它自己来告诉你「我叫不醒你了」。** 你把通知通道交给一个进程，这个进程死了，通知它的死因的唯一通道也死了。你只有在主动打开 TUI 的时候才会知道。而「主动打开 TUI」正是这个产品想替你省掉的动作。

**这是这个项目结构性的死循环，不是偶发 bug。** `install-watcher.mjs` 的注释里还写着「一次整目录删除把启动器和数据一起删掉，监控系统就此起不来」——它已经踩过一次这个坑，用「把启动器搬进仓库」打了补丁，但「谁来监视监视者」这个问题从未解决。

### 2.5 「TUI」

**我不需要它。** 理由很具体：

1. **首屏 52 秒。** 实测 `--plain` 一次 52.6 秒、`scan --days 3` 51.8 秒（README 写 33 秒）。`pendingLines()` 会说「这不是卡死」——**需要专门写一行字解释「这不是卡死」，本身就是一个产品缺陷。**
2. **它说「每 8s 轮询」，而一次扫描 52 秒。** 状态行原文：

```
parts.push(refresh, `每 ${app.intervalSec}s 轮询`);
```

`intervalSec` 默认 8，但 `scheduleNext()` 是在 `await job.promise`（整个扫描完成）之后才调用的。所以真实周期是 **52 + 8 = 60 秒**，状态行写的是 8 秒。这不是刷新慢，是**界面在陈述一个它没做的事**。
3. **tmux 分屏能看真相，它只能看重建。** README 自己写了「扫描是事后重建，不是实时」「最可靠的办法是打开它看一眼」。**你已经在文档里承认，最可靠的做法是我自己去打开会话——那这个 TUI 存在的意义是「在我懒得打开之前，给我一个可能不准的版本」。**
4. **跨平台是残的。** 通知只有 Windows Toast（`notify.mjs` 第 173 行：「当前平台不支持」直接 throw）。Linux 上 `c` 复制需要 `xclip`——**一个「零依赖」的项目，在剪贴板这一件事上依赖了外部二进制，而 README 的「零依赖」没提。**

### 2.6 「桌面通知」

**通知这件事，它在自己的 README 里已经给出死刑判决**：`permission prompt` 66/66 = 0% 真阳性；去重键把 8 次真实等待挤成 1 个；`lastSeenAt` 73/73 从不刷新。修是修了，三个都有负向测试。

**但 0% 真阳性的那一条，结论是「不再通知，但照常写观察记录」。** 翻译一下：有一个类别它永远判断错，于是它选择闭嘴。**我作为用户，无法知道它现在闭嘴的那些类别里，还有几个是同样的 0%。** 「通知抑制准确率无法自测」这条被写在「已知局限」里——**一个通知工具，承认自己的通知准确率无法测量。**

## 3. 最致命的一条

**如果只能留一个理由让它不值得装，那就是：**

> **它把一个「看一眼」的问题，做成了一个「信一个 84.6% 准的重建结果」的问题，而它自己在文档里承认「最可靠的办法是打开它看一眼」。**

具体到可复现的一步：

当你看到屏幕写着 **「1 件在等你 · 3 个问了没答 · 1 条声明无证据支持」**，你接下来必须做的动作是：
1. 打开 3 个会话确认那 3 个问句是不是真在问你（TUI 不告诉你哪 3 个）；
2. 打开那个「无证据」的 Java 会话，发现它的建议是「重跑 npm test」；
3. 回头想「还有 20 多个 EXPLORING 我没看」——**而这 20 多个，工具明确说了「不驱动任何动作」。**

**你为省「逐个打开 15 个会话」的时间，付出了「先等 52 秒，再逐个打开 3–7 个会话，并承担一条判错的风险」。** 净收益在最好的情况下接近零，在误报的情况下是负的。而那唯一的硬收益——「AI 报了假完成」——的精度只有 84.6%，且它自己说样本小。

**换句话说：这个工具最诚实的形态，是一份每周跑一次的离线报告，而不是一个常驻的、声称实时的面板。** 它现在的形态（TUI + 常驻监视）恰好是它最不擅长的形态。

## 4. 什么情况下我会装（反过来想）

我给三个具体场景，并直说现有功能能不能覆盖。**覆盖不了的我标 ✗，能覆盖的我标 ✓。**

### 场景 A：我关掉笔记本 / 睡了一夜，第二天早上想只花 60 秒知道「哪些会话在等一个必须我做的决定」

**能覆盖一半。** 这是我唯一认账的场景，因为 `claude agents` 不会在早上弹给你任何东西。

但实测我打开 TUI 得到的第 1 行是 **「0 件在等你」**，而 `claude agents` 说 **2 个 blocked**。原因是 `ACTION_MAX_AGE_SEC.BLOCKED = 7 天`，那两个 blocked 一个 213 小时（8.9 天）、一个 798 小时（33 天），被「超龄降级」进了「已停」。

**设计上这是对的**（33 天前的问题不该叫醒你），**但界面上是错的**：那个 8.9 天前的 blocked 是一个**真实在等你的 Java 会话**（「要我现在就把用户实测单交给你，还是你先看这四份测试报告？」），它的 `suggestedReply` 清清楚楚是「把实测单发给我」。它不在「需动作」里，而在「已停 (23)」里，一行小字 `· 超龄降级：Hilltop Village（8.9d > 7.0d 上限）`。

**7 天这个线，对一个「我出差一周回来」的人就是错的。** 我会装——但我会先去把那两个上限改成 30 天。**一个需要我改代码才对的默认值，不能算它覆盖了。**

判断：**△ 覆盖了一半，代价是改一行常量。**

### 场景 B：我同时开了 5 个会话跑同一个功能的不同部分，其中一个说「全部通过」，我想知道到底是不是

**能覆盖，这是它唯一赢的地方。**

实测这条判定是真的有用：

```
AI 说：「614 个测试全绿」
证据：有 10 次成功的测试运行，但都发生在最后一次编辑之前（编辑后没重跑）
```

**这一条我认。** 它抓的正是「sanitised optimism」——最后一步改了代码，然后嘴上说绿。`CODE_EXTS` 排除 `.md`/`.txt` 这个设计（注释里写了「改一份 CHANGELOG.md 不会让昨天的测试结果失效」）是**真做过功课的**，不是拍脑袋。

判断：**✓ 覆盖，且是唯一无法被 `claude agents` 替代的一条。** 但它被埋在一个要等 52 秒的 TUI 里，而它本该是一个可以在 CI / git hook 里跑的、5.6 秒的独立命令。**它现在的产品形态在拖累它最好的功能。**

### 场景 C：我想在下班前把「今天 AI 在哪个会话撒谎了」记一笔，明天上班接着查

**覆盖不了。** 全仓没有「自上次查看之后的变化」这个视图——我 grep 了 `since` / `digest` / `上次看` / `lastVisit`，零命中。TUI 每次都是全量重来，`verify-claims` 每次全量重扫 3.1 秒 / 0.16 GB。

**我要的不是「现在什么状态」，是「跟我上次走的时候比，变了什么」。** 这是所有监控产品的第一性功能（`git diff` 而不是 `git status`），而它没有。

判断：**✗ 未覆盖，且这是它最该有而没有的。**

### 场景 D（加分项）：我在 HN 上被人问「你的 AI 到底有没有在骗你」，我想甩一个可复现的链接

**能覆盖，且这是它真正的传播优势。** `node scripts/verify-claims.mjs --days 3 --explain` 的输出是**可反驳的**：它给了原话、证据调用次数、时间线、建议。别人可以拿同样的命令跑同样的数据。

判断：**✓ 覆盖。**

**小结**：4 个场景，2 个 ✓、1 个 △（要改常量）、1 个 ✗。**净结果是「值得装，但只为了一个功能，且那个功能不该长成现在这样」。**

## 5. 和 `claude agents` 的正面比较

官方（实测 `--json`，字段 `id / cwd / kind / startedAt / sessionId / name / state / pid / status`）：

```
claude agents --json          15 条，15–23 秒
claude agents --json --all    25 条（blocked 2 / busy 11 / idle 4 / done 1 / stopped 7）
```

**它能派发、能回复、能 attach**（`--agent` / `--model` / `--permission-mode` / `--add-dir` 全在 `--help` 里）。Overwatch 不能写、不能派发、不能回复。

### 对照表：什么它做不了而 Overwatch 做得了

| 任务 | `claude agents --json` | Overwatch | 判 |
|---|---|---|---|
| 列出注册中的会话 | ✓ 15 条 | ✓ 33–43 条（含未注册的已停会话） | **平**——多的那些是噪声（11 行同名） |
| 现在 blocked 的是哪两个 | ✓ 直接给 2 条 | ✗ **显示「0 件在等你」**（8.9d/33d 超龄降级） | **官方赢** |
| 派发 / 回复 / attach | ✓ | ✗（平台安全边界，README 已论证） | **官方赢** |
| 这个会话在干什么 | ✗ 只有 state | ✓ calls / novelty / depth / tokens / 末句 | **Overwatch 赢** |
| 完成声明有没有证据 | ✗ | ✓ 17 条断言分四档 | **Overwatch 赢，唯一硬差异** |
| 最后改了源码之后有没有重跑测试 | ✗ | ✓ 精确到「编辑在第 N 条、测试在第 M 条」 | **Overwatch 赢** |
| 会话失败的原因（503 / 等输入 / 死循环） | ✗ 只有 `blocked` | ✓ `stop-signals.mjs` + job `needs` 原文 | **Overwatch 赢** |
| 跨 3 天以上的历史 | ✗ 只有活着的 | ✓ `--days N` | **Overwatch 赢（但慢）** |
| 实时性 | ✓（就是进程自己） | ✗ 事后重建，52 秒 | **官方赢** |
| 桌面通知 | ✗ | ✓（但自身已死 32 小时） | **Overwatch 名义上赢** |

### 我的判决

**有 4 行是 Overwatch 真赢的，其中 1 行（断言 vs 证据）是没有任何替代品的。**

**但这 4 行里，有 3 行（干什么 / 历史 / 失败原因）本质是「把 transcript 读一遍」——这是 `claude agents --json` 的输出里那几个 `sessionId` 加一次 `jq` + `tail` 就能逼近的。** 只有「断言 vs 证据」这一行，需要真正的时间线配对逻辑（`CODE_EXTS` / `isMutatingCommand` / `lastCodeIndex` / `lastEditIndex`），那是这个仓库 2000+ 行里唯一没有替代品的部分。

**所以答案不是「不该存在」，是「它现在有 4/5 的代码在做一个 `jq` 能做的事，而那 1/5 被埋在里面」。**

## 6. 附：实测到的具体缺陷清单（可复现）

这些是我在这一轮里**亲手跑出来**的，不是从 README 转述的。按严重度排。

| # | 缺陷 | 证据 | 严重度 |
|---|---|---|---|
| 1 | **后台监视已死 32 小时，且无法自我通知** | `state.json` mtime 32.07h 前；`runner.log` 末行 `2026-10-31T19:22:58Z`；TUI 第 4 行「监视未在跑」 | **致命**（产品核心能力失效且不可感知） |

## 7. 我的结论

**该不该继续做：该，但要做减法，而且方向要砍对。**

理由不是「它有潜力」这种空话。具体是：

1. **`verify-claims.mjs` 这一块是真资产，别无分号。** 它的 `CODE_EXTS` / `NON_SOURCE_FILES` / 同一秒按记录顺序 tiebreak，这些是踩出来的、有注释、有实测的设计。这部分应该被抽成**独立命令 / CI step / git hook**，5.6 秒跑完，输出一段可以贴进 PR 的文字。它现在被绑在一个 52 秒的 TUI 里，是**被自己的产品形态拖累**。

2. **TUI + 常驻监视这一块，建议砍掉或者彻底降级。** 理由已经说了：它服务的场景（「我离开一会儿，回来看看」）被 52 秒的启动 + 60 秒的假轮询 + 一个已经死了 32 小时的监视进程抵消掉了。**而它唯一敢承诺的实时性，`claude agents` 免费给了。**

3. **如果一定要保留 TUI，有 3 件事必须先做，缺一不可：**
   - 让「问了没答」可定位（列表行加标记 / 加筛选），否则这个数字就是噪声；
   - 把 `STALE_ONLY` 按会话聚合（一个会话说三遍，不要报三条）；
   - 在首屏说清「本机 scan 需要 52 秒」，别在文档里写 33 秒。

4. **最该补的功能不是新功能，是「自上次查看以来的变化」。** 我 grep 了全仓，没有。这是监控工具的第一性能力，也是唯一能让「常驻」这件事成立的理由——**常驻的价值不在于「我现在是什么状态」，而在于「它替我盯着，变了才叫我」。现在它每次都在重新告诉我全部状态。**

**如果我是那个在 HN 上看到它的开发者**：我会 clone，跑一次 `verify-claims.mjs --days 3 --explain`，如果输出对得上我自己的项目，我会把它加进 CI。**我不会装那个监视器**，因为「一个已经死了 32 小时的监视器」这句话本身就是它的墓志铭——**而它自己知道，却只能等你打开它才告诉你。**
