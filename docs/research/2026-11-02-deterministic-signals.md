# 确定性判据能做到什么程度（2026-11-02 实测）

- 日期：2026-11-02
- 问题：**不依赖 AI，只用确定性规则，能判定「会话停下来时工作是否干完 / 是否在死循环」到什么程度？**
- 方法：对本机 `.claude/projects` 下全部 transcript 实跑新脚本 `scripts/stop-signals.mjs`，并对 85 个「末尾真正停住」的会话逐条人工判读。
- 所有数字均可复算，复算命令附在每节末尾。

---

## 一、结论先行

**确定性判据足以判断「会话停没停、停在哪」，但不足以判断「工作干完没有」。**

三个改变方向的数字：

| 实测 | 数字 | 含义 |
|---|---|---|
| 原始目标可从字节流中取出 | **93.6%**（176/188） | 「用户要什么」不需要 AI，是纯结构提取 |
| 「真的停下来了」可确定性判定 | **100%** 结构可判 | 末尾有无未执行的 `tool_use`，无歧义 |
| 停机时「没有在等任何人」 | **48.2%**（79/164 个有人类输入的会话） | 最大的一类停机，AI 只是说完就走 |
| 停机时「在等人做决定」但**不带问号** | **100%**（115/115） | 现有 `endsWithQuestion` 在这类上命中 **0** |
| 完成声明（"全部通过/已提交"）的语义可靠性 | 误报 **18.8%**（3/16） | 文本匹配会把「提议」读成「完成」 |

我逐条判读了 85 个末尾停机：

| 类别 | 数量 | 确定性？ |
|---|---|---|
| 客套问候 / 权限请求 / 结构化提问 | 9（10.6%） | **确定性可判** |
| 显式交还（问句、编号选项、"等你"、"测完回我"） | 39（45.9%） | 需语义，但**可判** |
| 断言已完成 / 给建议 / 贴报告（无显式交还） | 37（43.5%） | 语义也难判，**这是 AI 真正要补的部分** |

**如果"够用"的定义是"判断该不该自动继续"，确定性判据只覆盖约 10.6%。剩下 89.4% 里，45.9% 靠语义能判、43.5% 连语义都难判。**

所以：**"必须先解决 AI 能力"这个前提不成立，但它要解决的不是「能不能判」，而是「判得对不对」。** 详见第六、七节。

## 三、确定性判据清单（`scripts/stop-signals.mjs`）

全部是结构判据，没有一条读自然语言语义。唯一的文本匹配（问句结尾）在第 5.2 节被证明精度不足。

| # | 判据 | 实现 | 实测命中（188 个 transcript） |
|---|---|---|---|
| 1 | 真的停下来了 | 末尾无 `tool_use` 块 | 161 停下来 / 27 在干活 |
| 2 | 失败停机 | 记录的 `error` 字段 | 54 会话；**且 57/57 都是「错误是最后一个动作」**，无一条被后续成功覆盖 |
| 3 | 死循环 | 最近 8 次工具调用中同一「工具名+参数」出现 ≥3 次 | **2/188**（放宽到 50 次窗口也只有 9） |
| 4 | 上下文接近上限 | 尾部 token 水位 / 历史 `compactMetadata.preTokens` | **0/188** —— 该判据在本机**不可用**，见 §5.3 |
| 5 | 原始目标 | 首条 `origin.kind === 'human'`，兜底 `queue-operation.enqueue` | **93.6%**（176/188） |
| 6 | 结构化提问未答 | `AskUserQuestion`/`ExitPlanMode` 按 `tool_use_id` 配对 `tool_result` | **0**（9 次调用全部有回答） |
| 7 | 末句是问句 | 复用 `asked.mjs` 的 `endsWithQuestion` | 8 会话 —— 精度不足，见 §5.2 |

### 3.1 判据 2 的实测细节（这条最硬）

```
sessions with any error in head+tail: 64
  error superseded by a later successful turn (would be false positive): 7
  error is terminal: 57
```

会话级 7/64 是历史噪声（错误之后恢复了）。把判据收紧成「错误是最后一个动作」后，**57 个有错误的会话中 57 个都是终态错误，无一误报**（其中 54 个出现在当前扫描的会话级分类里，差值来自扫描期间新落盘的文件）。

真实错误形态（可直接作为判据，不需要解析文本语义）：

```
{"isApiErrorMessage": true,  "error": "authentication_failed"}
{"error": {"message": "524 {\"error\":{\"type\":\"bad_response_status_code\"...}"}}
{"error": {"message": "Request timed out."}}
```

> 复算：`node scripts/stop-signals.mjs`，或 `.tmp-analysis/turns.mjs`

### 3.2 判据 3 的实测：死循环极少发生

```
loop hit sessions (window=8,  repeat=3): 2
window=20 repeat=3: 2      window=20 repeat=5: 0
window=50 repeat=3: 9      window=50 repeat=5: 2
```

命中样本是 `sleep 115 && cd ...` 与重复 `Read` 同一文件。

**这个判据是确定性的，但它在真实语料里几乎不触发。** 「担心 AI 陷入死循环」在这份语料里不是主要风险 —— 主要风险是 §5.1 的 48.2%。

我在实现时踩了一个自证性错误：第一版把窗口套在「单轮记录」上，轮内通常只有 1–3 次调用，`LOOP_SUSPECT` 恒为 0。必须用**前文历史**做窗口。修好后才有上面这组数。

## 四、逐条人工判读：85 个末尾停机

口径：文件**以一次静默停机结束**（末尾记录是元事件，不是后续 assistant 输出），85 个会话（同一会话的不同分支会重复出现，已去重到 85 个）。

判读依据是 AI 最后一段文字的尾部；判读脚本与原文列表：

```bash
node .tmp-analysis/list.mjs      # 85 条编号 + 原文尾部
node .tmp-analysis/verdict.mjs   # 归类统计
```

| 类别 | 数量 | 占比 | 例子（真实原句） |
|---|---|---|---|
| **D 确定性可判** | 9 | 10.6% | `你好呀~ 又见面了，有什么想让我帮忙的` / `approve the prompt (or grant write access) and I'll retry` |
| **S 语义可判** | 39 | 45.9% | `**部分改动要不要按方案 A / B 做，需要你定。**` / `我等你反馈开下一轮。` / `测完回"**通过**"→ 归档 vX.Y.Z` |
| **U 语义也难** | 37 | 43.5% | `全部链接已校验有效…N 个文件都已同步到远端。` / `N/N 测试通过。` / `没有待办项了。` |

U 类的困难不在「读懂这句话」——每句都读得懂，难在**判断它是否成立**：

- `全部链接已校验有效，N 个文件都已同步到远端` —— 真的同步了吗？日志里没有远端状态。
- `N/N 测试通过` —— 测试真的跑了吗？跑的是这一版吗？
- `状态已复原（M 个实体 / delivered 0），存档 sha256 全程未变` —— 这是最典型的「自证」：**AI 声称自己验证了自己**。
- `代理可以正常使用了` —— 后面附了真实探测结果（`无凭据 407，带凭据 200`），这条可信；但如果它没附，判据无从分辨。

**这就是 AI 判断真正的位置**：不是读最后一句，而是拿「目标」去核对「证据」。

## 五、确定性判据的四个硬边界

### 5.1 最大的一类停机不是提问，也不是完成

`docs/research/2026-11-01-ground-truth-first.md` 的 87.5% 是**按「人下一次接话前 AI 最后一句是不是问句」**算的，分母是真人接话事件。换个口径（按会话文件结尾）复算：

| 口径 | 停机 | 在等人 | 没在等任何人 |
|---|---|---|---|
| 人接话前（历史口径） | 2,363 | 12.5% | 87.5% |
| **会话文件结尾（本轮）** | **164 个有人类输入的会话中 79 个** | — | **48.2%** |

两个数字不矛盾：**会话结尾处的停机更可能是「真的在等」**（48.2% vs 12.5%），因为会话能结束，往往是因为轮到人说话了。

`no response requested.` 在 85 条里出现 6 次 —— 那是宿主合成的占位消息，不是 AI 说的话，判读时必须排除。

> 复算：`.tmp-analysis/final2.mjs`

### 5.2 `endsWithQuestion` 在真实「等你」的话上命中 0

```
silent stops that actually ask for a decision: 115  (19.5% of 590)
  of which without "?" at the end:            115  (100.0%)
```

115 条是判定为「确实在等你」的静默停机，**没有一条以问号结尾**。真实形态：

```
要不要我把这个守卫改成「只比对本轮有改动的源文件」？ --- 现在可以开始跑测试了。**你先关掉那两个开发者选项开关**
**部分改动要不要按方案 A / B 做，需要你定。**
测完回"**通过**"→ 归档 vX.Y.Z、升 vX.Y.(Z+1)
等哪一轮你验过点头，那一轮的包摘掉后缀就是正式 0.1.6。我等你反馈开下一轮。
```

`endsWithQuestion` 的注释写得很清楚：它要求问号之后没有实质内容（`这是什么？反正做完了。` 不算）。这个设计对「是不是以问句收尾」是对的，但**「在等你」和「以问句收尾」是两件事**。实测两者的交集在这批语料上是 0。

这是本轮最具体的反例：**一个经过两次迭代、有测试覆盖的文本判据，在它最该命中的场景上命中率为零。**

### 5.3 上下文「接近上限」在本机是不可判的

- transcript 里**没有 context window 大小字段**（查过全部键名，只有 `usage.*` 与 `params.max_tokens`）。
- 唯一可观测的触发点是 `compactMetadata.preTokens`，但它在 **351,605 ~ 820,487** 之间浮动（50 次压缩，2.3 倍差距）——取决于模型与窗口配置。
- 因此「接近上限」只能相对于**历史阈值**判定，而 188 个会话里 154 个根本没有可对照的 compact 边界。

实测命中 **0/188**。这条判据无法用确定性方式实现，只能退化为「水位上报」，由人看。

> 复算：`.tmp-analysis/compact.mjs`

### 5.4 子 agent 是完全不同的分布

2,548 个子 agent transcript：

```
STOPPED_SILENT 2274 | ERROR_STOP 172 | NOT_STOPPED 100 | CONTEXT_RESET 1 | LOOP_SUSPECT 1
```

- **96.1% 判为「停下来」**——不是 48.2%。子 agent 本来就是「干完就交卷」。
- **错误停机 6.7%（172 个）**，比主会话高——子 agent 更容易撞上网关错误。

含义：如果把判据用在子 agent 上，**「停下来」几乎不携带信息**，只有 `ERROR_STOP` 有区分度。这和 `README.md`「只有 FAILED/BLOCKED 有区分度」的既有结论一致。

### 5.5 宿主状态只覆盖 6%

```
terminal stops: 84
  with a host session file: 6   (busy 3 / idle 3)
  no host record: 78
all sessions with a host session file: 10 / 186
jobs state files: 18 (running 0)
```

**宿主 `status` 不能当作确定性判据的支柱**——它只覆盖 5% 的会话，且 `waiting` 态在 11 个状态文件里出现 0 次。Overwatch 的判据必须以 transcript 为准。

## 六、完成声明能不能靠文本判？

我把「全部通过 / 已提交 / 已推送 / 没有待办 / 搞定了」当作完成信号，看人下一句是否否定：

```
completionClaimStops: 138
  followedByHuman: 16
  humanDisagreed: 3
  falsePositiveRate: 18.8%
```

误报样本（AI 说完成，人否掉）：

```
AI: "…我建议保留；你要是坚持要处理，说一声。"
人: "处理掉GitHub 服务器上那 3 个旧提交对象…"
```

第 1、3 例是**判据本身的问题**（「保留」被当成完成），第 2 例是**语义问题**：`等你验证通过说一声，我再推 Release` 是**未完成**，但因为含「已」字被匹配。

样本只有 16 条，18.8% 的置信区间很宽。但方向和 §5.2 一致：**文本匹配在「交还控制权」和「宣称完成」之间分不清**。

## 七、所以：AI 是必需的吗？

**结论：必需，但范围比预想的窄，而且不是「让它读最后一句」。**

三条证据：

1. **判据该覆盖的部分已经很硬**。停机、错误停机、原始目标、结构化提问，四个都是 100% 结构可判，不需要任何模型。这部分应当继续用确定性规则，成本为零、结果可复算（两次运行 0 差异）。

2. **「该不该继续」需要语义，且确定性文本做不到**。115/115 的反例说明：把「要不要我做 X」和「已经做完 X」分开，需要理解句子，而不是匹配词。`endsWithQuestion` 的 0% 命中是这条的定量证明。

3. **「做完没有」需要核对，而不是理解**。U 类 37 条（43.5%）里，问题不是「读不懂」，是「无法验证断言是否成立」。这需要的是**证据核对**（目标 + 改动的文件 + 测试输出 + git 状态），比「让大模型读最后一段」更接近能落地的东西。

**对项目方向的三个具体建议：**

- **不要等 AI 能力打通才做接力判定。** 错误停机（54 个会话）、结构化提问（0 个未答，但判据已有）、原始目标（93.6%）现在就能用，全部确定性。
- **`endsWithQuestion` 不能作为「在等你」的判据。** 需要的是「交还控制权」检测，实测形态是「要不要/等你/测完回/你定/说一声」，但这仍是文本匹配，只能做提示不能做决策。
- **"是否干完"不要交给单次模型判断。** 它需要外部证据（测试真的跑了吗、文件真的改了吗、远端真的同步了吗）。这是确定性 + 工具调用的组合，而不是纯语义题。一个本地小模型在这题上不会比正则更可靠，见第八节。

## 八、本机小模型：没有

实测结论：**本机没有任何本地推理运行时。**

| 检查 | 结果 |
|---|---|
| `which ollama llama-server lmstudio` | 无 |
| `AppData\Local\Programs` | 三个 GUI 应用，均非推理运行时 |
| 端口 11434 / 1234 / 5000 / 8000 | 无服务 |
| 端口 8080 | 一个浏览器调试端口，不是模型服务 |
| `~/.cache` | 无模型目录 |

硬件是有的（一块消费级 GPU），装 Ollama 跑 7B 级别模型可行。但**没有实测就不给结论**：本报告不评估「小模型够不够用」，因为没有可测的对象。

一个先验的谨慎判断（**未经实测，仅标注为判断**）：§7 第 3 条说的「核对」任务需要的是工具调用与状态比对，而不是生成能力。小模型在这个方向上不占优势；而在 §5.2 的「交还控制权」分类上，7B 级别模型能否超过 0% 的文本基线，需要单独实测才能说。

## 十、本轮修正的错误（留档）

| 错误 | 后果 | 修正 |
|---|---|---|
| 死循环窗口套在单轮记录上 | `LOOP_SUSPECT` 恒为 0，误以为"没有死循环" | 改用前文历史窗口 |
| 先判「有 tool_use = 在干活」再判提问 | `AskUserQuestion` 的停止点被算成在干活 | 提问判定提到最前 |
| 只扫主 transcript | 漏掉 5.84 GB / 2,548 个子 agent | 补测 §5.4 |
| 原始目标只读 `origin.kind === 'human'` | 30 个会话（16%）取不到目标 | 补 `queue-operation.enqueue` 兜底 → 93.6% |
| 用 `endsWithQuestion` 判「在等你」 | 115/115 漏判 | 保留为对照，不当判据 |
