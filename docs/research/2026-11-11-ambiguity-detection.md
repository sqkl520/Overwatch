# 从一句话里找出「该问什么」：歧义检测的可用方法与最小方案

- 日期：2026-11-11
- 作者：研究 Agent Q2
- 产出形态：`exploration`
- 上游命题：[`docs/design/2026-11-11-question-protocol-thesis.md`](../design/2026-11-11-question-protocol-thesis.md)
- 标注约定：`[实测]` = 本文件作者在本机语料或本仓库代码上复算，口径写在 §5，可重实现；
  `[文献]` = 有论文/官方文档原文支撑，链接见 §6；`[推演]` = 无直接证据，作者推断。

## 0. 结论先行

1. **不存在现成的「一句话进、问题出」的检测器。** 文献里能查到的方法只有两族：
   ①把需求编译成可执行代码再比对行为（ClarifyGPT 的 code consistency check）；
   ②先有一份成文 spec，再按分类学扫描它（GitHub Spec Kit 的 `/clarify`、Kiro 的 Analyze Requirements）。
   两族都要求「已经有一个比一句话长得多的输入」。**把一句话变成第一个问题的这一步，没有现成方法。** `[文献]`

2. **「开工前问」不会自然发生，只能机械强制。** 本机 239 个会话、2307 条真人消息里共 505 个
   `AskUserQuestion` 问题（228 次调用，50 个会话），**只有 8.1%（41 个）发生在任何写文件动作之前**；
   92% 的问题是干到一半才问的。`[实测]` 这与 Ambig-SWE 的实测同向：不给强制提示时，
   模型几乎从不主动澄清（Claude Sonnet 4 在强提示下把「是否欠定义」判对 89%，弱提示下退化到 74%）。`[文献]`
   **推论：本项目的差异点不是「会不会问」，而是「能不能在第一次 Write 之前拦住」。**

3. **检查清单能列话题，但不能判「该不该问」。** 我在 68 个真实会话上跑了六槽位关键词检测：
   首条消息平均有 **4.9 / 6 个槽位判为「缺失」**——清单几乎对每条消息都全红，
   这样的触发器区分不出「这条需求真的缺信息」和「这条需求只是没写套话」。
   后续用户自己补上的比例是 34%–74%（按槽位不同），但**我没有对照组**，
   这个数字不能证明「缺失预示后来需要」，只能说「缺失的槽位有时后来确实被补上」。`[实测]`
   这是「纯模板检查清单不足以做触发器」的证据，也说明必须再加一维「不问的后果」。

4. **唯一有真实评测数字、且能对上一句话场景的信号是「实现分歧」。** ClarifyGPT：
   同一需求采样多个实现 → 输出不一致即判歧义；MBPP-sanitized 427 题里判出 140 题有歧义，
   平均 2.85 个问题/题；GPT-4 的 Pass@1 从 70.96% 提到 80.80%（相对 +13.87%）。`[文献]`
   它的形状与「读项目代码、发现 3 种缓存方案 → 3 个问题」高度同构，**是本项目最值得抄的一件事**。
   但它依赖「能跑代码并比对输出」，对非函数级任务要改写。

5. **一周能交付的不是检测器，是「排序器 + 强制闸门」。** 候选问题由四条便宜规则产生
   （槽位、仓库内已有实现的分歧、不可逆动作、历史复述），用 `不可逆性 × 分歧度 × 未答 × 阻塞性`
   排序取前 3–5 个，用一条 hook 保证「没确认过的问题清单，不许第一次 Write」。
   **难点不在「发现问题」——那部分召回率会很高；难点在「不问废话」，而这一点没有任何现成方法可抄。** `[推演]`

## 1. 可用的检测方法（逐条可行性）

### 1.1 代码一致性检查：采样多个实现，分歧即歧义

**做法**（ClarifyGPT 原文 §3.1–3.2）`[文献]`
1. 用 LLM 生成一批测试输入（种子 + 类型感知变异）；
2. 对同一句需求采样 N 个代码解；
3. 把 N 个解在同一批输入上跑，**比较输出是否一致**；
4. 一致 → 判为不歧义，直接输出其中一个解；不一致 → 判为歧义，把「功能不同的那几个解」喂给下一阶段生成针对性问题。

**数字**（原文 Table 2/3）`[文献]`

| 指标 | 值 |
|---|---|
| 判为歧义的比例 | 140 / 427（MBPP-sanitized），约 33% |
| 歧义题的平均问题数 | **2.85** |
| GPT-4 Pass@1（人工回答） | 70.96% → **80.80%**（MBPP-sanitized），51.52% → 60.19%（MBPP-ET） |
| GPT-4 均分（四基准，模拟回答） | 68.02% → 75.75% |
| ChatGPT 均分 | 58.55% → 67.22% |

**为什么它对本项目重要**：这是唯一一个**用「实现分歧」而不是「语言歧义」来判定」的方法。
用户说「加个缓存」，我们能读代码，发现仓库里已有两套缓存（`scripts/watch.mjs` 的轮询式 vs
`scripts/install-watcher.mjs` 的安装式），这本身就是「两种理解」的物证——不需要判断这句话语不语义歧义。

**可行性评估**：

| 维度 | 判断 |
|---|---|
| 对一句话需求 | **直接可用**，但要求「能生成并执行候选实现」 |
| 成本 | 每次 N 次代码生成 + 执行。原文用 1 个函数的规模；仓库级任务每次可能是 N × 数十分钟 |
| 失败模式 | 原文自陈两条局限：输入复杂（图像/文件）不适用；无返回值的程序（深度学习）不适用。仓库级改动大多没有可执行返回值，**这是硬伤** |
| 一周可行性 | **低**。可以做「静态版」：不执行，改成「采样 3 个实现方案文本，聚类差异点」 |
| 对本项目的定位 | **思路照抄、实现降级**：把「输出不一致」换成「方案文本有实质差异」，变成纯静态信号 |

### 1.2 探测式提问（clarify prompt）：最便宜，也最没用

- gpt-engineer 的 `clarify` 预置提示词全文只有三句：
  「判断是否需要澄清，不要执行。可以做合理假设；如果不确定，**只问一个问题**；否则输出 `Nothing to clarify`。」
  `[文献]`（读自仓库 `gpt_engineer/preprompts/clarify`）
- ClarifyGPT 的对照实验直接打穿了这个做法：GPT-Engineer 对**已经写得很清楚**的需求仍然问了 3–5 个问题，
  其中「有没有偏好的编程语言？」这类问题在函数签名已经写明 Python 时纯属废话；
  而 ClarifyGPT 只问 1 个（升序还是降序）。`[文献]`
- 学术版：Wu (2023) 提出「用一个 LLM 扮演 communicator，专门识别高歧义/低置信处并提问」，
  是立场论文（6 页，MAPS 2023 workshop），**没有量化结果**。`[文献]`

**可行性评估**：一周内可做（就是一个 prompt）。**但它单独用会产生废话**，必须叠一个「不问」的判据。
本机实测旁证：505 个问题里有 25.9% 的答案不是任何选项（自由文本，平均 66 字），
说明用户在**选项没覆盖到关键分歧**时会自己写；但也说明选项设计已经在起作用。

### 1.3 分类学 + 清单：成熟、可借鉴，但都是「事后扫描 spec」

| 来源 | 分类学 | 机制 | 对本项目的可用性 |
|---|---|---|---|
| **GitHub Spec Kit `/clarify`** | 9 大类：功能范围、领域与数据模型、交互与 UX、非功能质量、集成与外部依赖、边界与失败处理、约束与取舍、术语一致性、完成信号（另有杂项占位符一类） | 逐类标 `Clear/Partial/Missing`，**最多 5 个问题**，排序用 `Impact × Uncertainty`，每题必须 2–5 个互斥选项或 ≤5 词短答，一次只问一个，答完即时写回 spec `[文献]` | **排序公式和「最多 5 问」直接可抄**。分类学是给「已有 spec」设计的，对一句话会全判 Missing |
| **Kiro Analyze Requirements** | 五类：逻辑不一致、歧义措辞、冲突约束、未声明假设、缺失边界 | 跨需求推理，问题流式输出，每题带「涉及哪几条需求 + 白话解释 + 可选修法」`[文献]` | 「每题必须点名它改动了什么」这条纪律可抄。它是 spec→design 之间的门，不是一句话入口 |
| **Kiro Quick Spec** | — | 明确说「问题集中在前期问完，换来后面不再有审批门」`[文献]` | **与本项目命题同构的现成产品佐证**（它把澄清当成省掉审批门的代价） |
| **Requirements smells（12 类）** | Ambiguity / Completeness / Complexity / Consistency / Correctness / Traceability / Reusability / Understandability / Redundancy / Verifiability / Relevancy / Undefined（Montgomery 分类法被 Gentili & Falessi 沿用） | 10 位从业者访谈：**最严重的是 Ambiguity 与 Verifiability，最高频的是 Ambiguity 与 Complexity** `[文献]` | 提供「哪类缺陷值得检测」的优先级。**注意：这是 10 人单公司访谈，样本小，作者自己声明不可泛化** |
| **CLAMBER（8 类）** | 三维八类：Epistemic Misalignment（Unfamiliar / Contradiction）、Linguistic Ambiguity（Lexical / Semantic）、Aleatoric Output（Who/When/Where/What 缺失） | 约 12K 数据，评测 LLM 的「识别歧义」能力 `[文献]` | 「Who/When/Where/What 缺失」这一维直接对上「缺主语/缺时间/缺位置/缺任务要素」，**是需求缺陷分类法里最贴近「一句话」的一组** |
| **AmbigNLG（6 类）** | CONTEXT / KEYWORDS / LENGTH / PLANNING / STYLE / THEME | 每类有填空模板，追加到原指令后作为「无歧义参考」`[文献]` | LENGTH / STYLE / CONTEXT 三类对「写文档类任务」直接可用；对编码任务偏弱 |

**可行性评估**：分类学本身零成本（一份 markdown 表）。**问题是覆盖率**——见结论 3 的实测：
六槽位检测在真实首条消息上几乎全判 Missing（平均 4.9/6 个槽位没命中），
这意味着「按清单问」等于每次都问同样 5 个问题，与 gpt-engineer 被 ClarifyGPT 批评的毛病同型。

### 1.4 三段式评测：检测 / 提问 / 利用，可复用为验收口径

Ambig-SWE（ICLR 2026）把「能不能处理欠定义需求」拆成三件事分别测，值得照搬成我们的验收指标：`[文献]`

| 能力 | 怎么测 | 实测结果 |
|---|---|---|
| (a) 检测欠定义 | 随机构造 fully-specified vs underspecified 两种输入，看模型是否只在后者提问 | 不给提示时**几乎从不交互**；Sonnet 4 强提示下 Acc 0.89 / FPR 0.03 / FNR 0.18；Sonnet 3.5 在中等提示下 Acc 0.84 / FPR 0.24 / FNR 0.09；Qwen3-Coder 在**所有**提示下 FNR 100%（从不问） |
| (b) 问得准 | 信息增益（embedding 余弦距离）+ GPT-4o 打分（1–5） | 有能力的模型打分都收敛在 4/5 左右；**差别在「问几个」**：Sonnet 4 平均 4.03 问，Qwen 6.02 问，信息增益相近（0.171 vs 0.179） |
| (c) 用得上 | 看最终 resolve rate | 交互比不交互最多 +74%；Sonnet 4 恢复到 full 设定的 89% |

另有一个对本项目特别关键的观察：**「先探索代码库、只问代码里查不到的」**是 Claude 系模型的做法，
而 Deepseek/Qwen 一上来就问实现细节，**问到了用户本来不知道的东西**，白费回合。`[文献]`

**可行性评估**：高。这三个指标可以直接变成我们自己的回归测试（见 §2.5）。

### 1.5 不确定性 / 语义熵：理论上对，工程上贵

- Semantic Uncertainty（Kuhn et al., ICLR 2023）：对同一输入采样多个回答，按**语义等价类**算熵，
  比 token 级熵更能预测「模型会不会答错」。`[文献]`
- Adaptive-Consistency：按样本间一致度自适应分配采样预算，不必固定采样数。`[文献]`
- 「Act or Clarify?」（CogSci 2026）把「问不问」形式化为**期望后悔**：当「现在动手可能造成的损失」
  大于「问一句的成本」时才问；实验显示人类的提问率与潜在损失成正比。`[文献]`

**可行性评估**：中低。语义熵要求多次采样（成本 ×N），且它测的是「模型不确定」，
不等于「需求缺信息」——模型可能对一句残缺需求非常自信地给出唯一解（CLAMBER 实测的 overconfidence 现象）。`[文献]`
**但对排序有用**：「Act or Clarify」的后悔模型正是我们想要的排序公式的原型（见 §2.2）。

### 1.6 从历史 transcript 反推「当时该问什么」

**这个方向有没有名字**：没有完全对应的名字。相邻的三支：
- **经验抽取**（ExpeL 等）：从成功/失败轨迹里抽取自然语言 insight，测试时检索复用。`[文献]`
- **反事实轨迹解释**（ACTER 等）：生成「怎样做本来能避免失败」的反事实序列。`[文献]`
- **specification mining**：从程序执行轨迹反推规格（Amann et al., POPL 2002 起）。`[文献]`

三支都不是「从失败轨迹反推该问的问题」。**没有直接前例，这条路是我们自己的（也可能正因如此没人验证过）。** `[推演]`

**本机可行性实测**：`[实测]`
- 2307 条真人消息中，带明确纠错语义（「不是这个意思 / 我指的是 / 理解错 / 谁让你」等）的只有 **14 条，分布在 4 个项目**。
- 带返工语义（「重做 / 重来 / 全量重跑 / 返工」）的会话占 50.3%（73/145），**但这个数字是假的**：
  逐个看原文，绝大多数命中来自用户反复粘贴的一段固定开场白（「中断了就全量重跑」），
  不是对某次交付的不满。**去掉模板句后，真正的返工投诉样本是个位数。**

**结论**：这条路的**数据量支撑不起训练，但支撑得起「人工读 20 条 + 写 5 条规则」**。
如果要做，正确的做法不是「训练一个模型」，而是「把 14 条纠错 + 个位数返工逐条人工归因，
问一个问题：当时如果问了 X，这条纠错会不会消失？」——一天能做完，且结论可以直接写进 §2 的规则表。

## 2. 最小可行方案（一周）

### 2.0 设计立场（先承认一个取舍）

不做「检测歧义」，做「**排序候选问题**」。理由：
检测要求判对/判错（CLAMBER 实测最好的模型也只有 54% 准确率，等同抛硬币），`[文献]`
排序只要求「把最可能白干的排前面」，错一个的代价是多问一句，不是做错一件。

### 2.1 信号层：四条规则

| # | 信号 | 判定方式与成本 |
|---|---|---|
| **S1 不可逆动作** | 需求文本命中 `推送/发布/删除/覆盖/迁移/改 lockfile/装依赖` 等动词。正则，零成本 |
| **S2 仓库内实现分歧** | 对需求关键词做仓库符号检索（复用 `scripts/` 已有的 walk + 扩展名过滤），若同一概念有 ≥2 处独立实现，生成一个问题。低（一次目录遍历；本仓库 depth≤3 共 1748 个文件，一次遍历 <1s）`[实测]` |
| **S3 静态版实现分歧（ClarifyGPT 降级）** | 对需求采 3 个「实现方案」文本，提取「改动文件集合 + 关键动词」，取交集为空或互斥则判歧义。中（3 次模型调用） |
| **S4 历史复述** | 需求里的规则句与 `tasks/`、`CLAUDE.md`、历史 transcript 做短语匹配；命中则**不问，直接回引**。低 |

**S1 与 S4 的依据**（都来自仓库既有研究，不重复推导）：
- S1 用的动词表与 `docs/design/intent-contract.md` §2.3 的 `capability` 受控词表**同一套**；
  该文件实测：120 条样本里 **42 条（72%）** 的提问含改持久状态的动作（push/发布/删除/提交/安装/部署）。
- S4 复用同一批实测：40 组「项目×规则」共 677 次陈述，**只有 40 次是首次，其余 637 次是复述（冗余 16.9×）**。
  这是「不问废话」的主力：用户最烦的是被问已经说过三遍的事。

**S2 为什么可信——本仓库里三组真实的「同一概念两套实现」**`[实测·读代码]`

| 用户可能怎么说 | 仓库里的两种做法 | 两种做法的分歧点 |
|---|---|---|
| 「加个监控」 | `scripts/watch.mjs`（轮询式）／ `scripts/install-watcher.mjs`（安装式） | 是「定时扫」还是「装个钩子」——决定改哪个文件、由谁启动 |
| 「改一下停机判定」 | `scripts/stop-signals.mjs`（求**覆盖率**，判不出就说判不出）／ `scripts/classify-stop.mjs`（求**精度**，判不了给 `UNCLASSIFIABLE`） | 两者头部注释互相点名，且明确写了「本文件的设计原则与另一个不同」 |
| 「把『AI 在等回答』弄准一点」 | `scripts/asked.mjs`（找**问句结尾**的自然语言）／ `classify-stop.mjs` + `stop-signals.mjs`（找 **`AskUserQuestion` 的结构化 `tool_use`**） | 文本信号 vs 结构信号，召回与精度完全不同 |

**这三组正是 ClarifyGPT「两个实现 = 两种理解」信号的静态版本**：不需要跑代码，
只需要在仓库里发现「同一个词对应两套不兼容的实现」，就能断定这句话至少有两种理解。

**S1+S2 是必须先做的**：它们不需要模型，判错了也不会造成「问了句蠢话」以外的后果。
**S3 是可选加档**，一周内只在「artifact 形态 + 高预算」时打开。

### 2.2 排序：不用 `Impact × Uncertainty`，用「不问的后悔」

Spec Kit 用 `Impact × Uncertainty`，`[文献]` 但这两个量都要人估。我们改用可机械算的版本：

```
score(q) = irreversible(q) × divergence(q) × unasked(q) × blocking(q)

irreversible ∈ {0, 1}       # S1 命中且动作不可撤销（push/delete 类）= 1；只读类 = 0
divergence   ∈ {0, 1, 2}    # S2 命中两处独立实现 = 2；只命中一处 = 1；未命中 = 0
unasked      ∈ {0, 1}       # S4 未命中 = 1；已说过 = 0（直接归零，永不问）
blocking     ∈ {0.5, 1}     # 该问题的答案是否改变「先在哪个文件动手」——由 S2 的文件集是否空判
```

取 `score > 0` 的前 3 个，**硬上限 5 个**（Spec Kit 的上限，理由见 Ambig-SWE：Sonnet 4 用 4.03 问拿到与 6.02 问相同的信息增益）。`[文献]`

这个式子的理论依据是「Act or Clarify?」的期望后悔：只有当「不问导致的潜在损失」超过「问的成本」时才问。`[文献]`
`irreversible` 就扮演「潜在损失」，`unasked` 扮演「问的成本已付过」。

### 2.3 「不问废话」的四道闸门（这是方案的核心，不是附属）

按顺序，任一命中即**丢弃**该候选问题：

1. **已答过**：`tasks/`、`CLAUDE.md`、`intent.md`、本会话前文里已有答案 → 不问，改为回引一句「按你 X 月 X 日说的 Y 做」。
2. **代码里能查到**：问题答案可由一次 `Read`/`Grep` 确定（例如「项目用什么测试框架」）→ 不问，自己查。
   Ambig-SWE 的实测支撑：探索优先的模型用一半的问题量拿到相同信息增益，且**问实现细节的问题被证明是浪费回合**。`[文献]`
3. **不影响验收**：答案改变不了「什么算做完」→ 降级为「我会按 A 做，除非你反对」，不占提问额度。
   Spec Kit 的原话是「只保留会实质影响架构、数据建模、任务拆分、测试设计、UX 行为、运维就绪、合规校验的问题」。`[文献]`
4. **超出预算**：已问满 N 个（默认 3，上限 5）→ 剩余问题写进「我做的假设」清单，随交付物一起给用户看，不阻塞开工。

### 2.4 强制点：一条 hook，不是一段 prompt

**这是整个方案唯一有把握做成的事**，也是结论 2 的直接推论（92% 的问题都发生在开工之后）：
在本仓库已有的 `.claude/settings` 机制上加一条 `PreToolUse` 钩子，对 `Write` / `Edit` / `NotebookEdit`
检查 `tasks/runs/<run-id>/questions.md` 是否存在且状态为 `resolved` 或 `waived`；否则拒绝并返回提示。

- 为什么必须是 hook 而不是 prompt：Ambig-SWE 实测，纯提示能让交互率从「几乎为零」抬到 89%（Sonnet 4 + 强提示），
  但也实测「提示工程对识别能力的提升很有限，且不同模型差异极大」。`[文献]` 我们要的不是「大概率会问」，是「不问就写不进去」。
- 为什么这个仓库做得到：`scripts/` 已有 `check-structure.mjs` 的硬门模式、`verify-claims.mjs` 的
  「断言 vs 证据」判定，`AskUserQuestion` 的回答已按 `The user answered: "问"="答"` 结构化落盘
  （`scripts/classify-stop.mjs` 头部注释已记录这个格式）`[实测·读代码]`。**结构化答案已经在手，缺的只是闸门。**

### 2.5 验收：三个可回放的指标（照搬 Ambig-SWE 的三段式）

预声明（先写死，不许事后改，符合本仓库「验收标准预先声明」硬约束）：

| 指标 | 口径 | 及格线 | 怎么算 |
|---|---|---|---|
| **M1 前置率** | 「第一次写文件之前已存在 resolved 问题清单」的会话占比 | ≥ 90% | 扫描新 transcript，检查首个 `Write/Edit` 之前是否有 `questions.md` 且 resolved |
| **M2 有效问题率** | 问题的答案**不是**「已答过/代码能查到/不影响验收」的比例。人工抽 50 个问题标注 | ≥ 60% | 单人标注，标注规则写死在 `questions.md` 头部 |
| **M3 废话率（反向指标）** | 用户回答是「什么玩意/随便/你决定/No preference」或答案与已给信息重复的比例 | ≤ 10% | 复用 §5 的解析方法：从 `The user answered:` 里提答案，与选项 label 比对 |

**基线数据（现在就有，不用等）**：`[实测]`
- 前置率现在 = **8.1%**（41/505 个问题，口径见 §5）；
- 答案不是任何选项的自由文本 = **25.9%**（98/379 对）；
- 用户明确索要选项/提问的会话 = 23/239（9.6%，44 条消息，原文如「给我选项，不要只跟我说问题」）。

第三个数说明一件事：**用户不是反对话，是反对「话说一半」**。这正是本题的立论基础，也说明 M2/M3 是这套方案里比 M1 更值钱的指标。

### 2.6 一周排期（按能不能砍排序）

| 天 | 做什么 | 产出 | 可砍吗 |
|---|---|---|---|
| D1 | S1 + S4 规则（正则表 + 复用短语匹配）；写 `questions.md` 格式 | `templates/questions.md` + 一个纯函数模块 | **不能**（这是全部价值的下限） |
| D2 | S2 仓库分歧检测（walk + 符号聚类）；在 3 个真实项目上跑，人工看 20 条 | 一个脚本 + 20 条人工判定 | **不能**（这是「读代码反推」的唯一实现） |
| D3 | 排序式 + 四道闸门；在 100 个历史首条消息上回放，与「用户第 2–5 轮实际补了什么」对照 | 回放报告（召回/废话两个数） | 不能 |
| D4 | `PreToolUse` hook 接 `Write`/`Edit`；负向测试（不打清单必须被拒） | hook + 负向测试（本仓库惯例：硬门必须做负向测试） | 不能 |
| D5 | S3 静态分歧（可选）；把 14 条纠错样本人工归因，写进规则表 | 规则表增补 | **可以砍**，砍了不影响 M1 |

**判断：一周能做出来**，但前提是把「检测歧义」降级成「排序候选问题」。
如果坚持要一个准确率意义上的检测器，一周做不出来，也看不到做出来的路径（见 §3）。

## 3. 为什么可能做不好（反面）

1. **识别准确率的天花板很低，而且是有实测的。** CLAMBER 用约 12K 数据测了 5 个模型，
   最好的 ChatGPT 在「这句话有没有歧义」上的准确率是 **54.25%，F1 52.77%**；
   加 CoT 和 few-shot 只带来边际提升，还会让**小模型更过度自信**（ECE 从 21.47 升到 45.14）。`[文献]`
   如果我们的检测器也停在 55%，它产生的候选问题里近一半是无用功。

2. **「问得多」和「问得准」可以同时变好，也可以互相抵消。** Ambig-SWE 里 Qwen3-Coder
   问得最多（6.02）、信息增益最高（0.179），但 resolve rate 反而**比不问的基线更差**（拿到文件位置后
   又去自己重查一遍，白费回合）。`[文献]` 我们的 5 问上限是从别人那里抄来的常数，
   **没有任何证据表明 5 适合我们的场景**。

3. **「从历史 transcript 学习」的数据根本不够。** 本机 2307 条真人消息里只有 14 条纠错语义。`[实测]`
   一个每条规则只能靠 14 个样本支撑的系统，做出来的东西本质上是**人工直觉的编码**，不是学习。
   如果对外宣称「从历史学习」，会立刻被这个数字打穿——这和 `docs/design/verdict-intent-contract.md` §三
   里「字符重合度与方向改变正交」是同一类错误：**度量看起来很合理，但它在原理上测不到它声称要测的东西。**

4. **最强的反方证据来自我们自己的语料：用户已经在要求「给我选项」了。** 23/239 个会话里，
   用户不得不亲自说「不要跟我直接说问题，给我选项」。`[实测]` 这可以读成「需求真实存在」，
   也可以读成「**AI 问了但问得没法答**」——后者意味着问题不在「检测」，在「提问的形态」。
   如果是后者，我们花一周做的检测器解决的是错误的问题。

5. **用户自己也答不上来（thesis 未答问题 #3）没有任何进展。** 所有查到的产品（Spec Kit / Kiro / Cursor）
   都假设「用户心里有答案，只是没说」。如果答案是「用户不知道」，那么正确的动作不是问，
   而是**给出带后果的默认值让对方确认**——这与「问问题」是不同的产品形态。本文件没有解决它，只是把它标出来。

6. **「读代码反推有几个未定选择」这件事没有前例可抄。** 我搜过的组合
   （repository-grounded clarification / code-context requirement elicitation / 代码库驱动的需求澄清）
   **没有任何直接命中**。`[文献·查无]` 查无前例可能是机会，也可能是这条路本身不通——
   `specification mining` 搞了 20 多年，公认的局限是「推断出的规格依赖轨迹覆盖度、易过拟合、误报率高」，
   而我们要做的是它的逆问题（从代码推「还没写的那部分该问什么」）。`[文献]`

## 5. 实测口径（可重实现）

**语料**：`~/.claude/projects/*/*.jsonl`，**264 个文件**，
其中 **239 个会话**至少有一条真人消息。

**真人消息判据**（与 `docs/design/intent-contract.md` §9.1 同口径，并排除续写摘要）：
`type === "user"` 且 `typeof message.content === "string"` 且 `!isMeta`
且 `origin.kind` 为空或 `"human"` 且正文不以
`<task-notification|<local-command-caveat|<system-reminder|<ide_opened_file|<cross-session|<command-name|<command-message|<local-command-stdout`
开头。总计 **2307 条**。

**问题计数**：`tool_use.name === "AskUserQuestion"` 共 **234 次调用**，其中 **228 次**的
`input.questions` 是数组（另 6 次该字段被写成字符串，解析不出结构化问题，**这 6 次在计数时被丢掉**）。
228 次调用共 **505 个问题**，分布在 **50 个会话**。每次调用的问题数：1 问 82 次、2 问 67 次、
3 问 27 次、4 问 52 次。选项数分布：2 项 72 题、3 项 286 题、4 项 147 题；`multiSelect` 仅 15 题。
推荐标记（选项 label 含「推荐」）出现在 309/505 = **61.2%**。

**前置率（结论 2 的 8.1%）**：遍历会话，维护「已出现过的 `Write`/`Edit`/`NotebookEdit` 次数」与
「已出现的真人消息序号」；提问发生在 `writes === 0 && humanIdx <= 1` 时计为前置。
得 **41/505 = 8.1%**（17 次调用 / 41 个问题属于前置；211 次调用 / 464 个问题属于开工后）。

**槽位检测（结论 3 的表）**：取「首个真人消息 ≥60 字符、会话 ≥3 条真人消息、且不在临时/探针目录」的 68 个会话。
六槽位正则：路径（盘符路径 / `/xxx/` / 代码文件扩展名 / 目录 / 文件夹 / 文件）、
验收（测试|test|验收|验证|通过|跑通|单测|assert|CI）、排除（不要|别|除了|排除|不需要|不动|禁止|保持现状）、
交付（提交|推送|发布|PR|commit|push|release|打包|部署）、选型（Node|Python|React|TypeScript|Java|Kotlin|框架|版本|沿用|技术栈）、
范围（只要|仅|只做|范围|先做|第一阶段|MVP）。「后续补上」= 第 2 条起的任意真人消息命中同一正则。
**注意：这些正则是粗糙的，尤其路径槽位会把 URL 也算进去；本表只作方向性证据，不作精确比例。**

| 槽位 | 首条未命中 | 后续补上 | 首条已命中 | 后续再提 |
|---|---|---|---|---|
| 路径 | 51 | 30（59%） | 17 | 14（82%） |
| 验收 | 55 | 29（53%） | 13 | 12（92%） |
| 排除 | 37 | 22（59%） | 31 | 31（100%） |
| 交付 | 62 | 46（74%） | 6 | 6（100%） |
| 选型 | 66 | 41（62%） | 2 | 1（50%） |
| 范围 | 65 | 22（34%） | 3 | 1（33%） |

**这张表最重要的一列是最后一列：首条已经提到的槽位，后续仍然被提到的比例是 50%–100%。**
它说明正则命中 ≠ 「这个信息已经答清楚了」——用户可能提到了「测试」但没说怎么算通过。
**所以「槽位缺失」既不是「该问」的充分条件，也不是「已答」的充分条件**，
任何只靠关键词的清单，两头都判不准。

**纠错语料（§1.6 / §3 第 3 条）**：纠错正则
`^(不对|不是|错了|等等|等一下|停|打住|不行)|不对呀|不是这样|重来|重新做|搞错了|理解错|你说的不对|我没让你|谁让你`，
在 4 个项目命中 14 条。返工正则 `重做|重来|全量重跑|推翻|作废|白做|返工` 在 145 个会话里命中 73 个，
但人工抽看后确认绝大多数来自用户固定的开场白模板，**不可用作返工率**。

**提问会话 vs 无提问会话的人均真人消息数**：在「≥3 条真人消息」的 145 个会话里，
44 个用过 `AskUserQuestion`（人均 **25.52** 条），101 个没用过（人均 **10.71** 条）。
**这个差异不能读成因果**——「问得多所以聊得久」与「任务本来就更复杂所以又问又久」同样符合数据。
