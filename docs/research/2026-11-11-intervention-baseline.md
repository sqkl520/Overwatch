**三条会被后续工作依赖的判断：**

1. **介入的主因不是「AI 做错」，是「AI 说完就停、用户还得推」。**
   365 次催促里有 **202 次**发生在 AI 正常 `end_turn` 之后——AI 宣称完成、收工，
   用户回一句「继续」。其中 152 次 AI 的最后一句话里**连问都没问**，直接收工。
   这类占全部介入的 **19.3%**，是单一体量最大的一块。

2. **能靠「开工前问清楚」消除的上限是 37%，不是全部。**
   按可避免性分级，P1（前提没定清，本可在开工前问）295 次 = 37.0%。
   剩下的 63% 里，环境故障 18.2%、误触/主动停手 9.1%、AI 看不到用户眼前现象 3.5%、
   纯节奏 4.1%，还有 28.1% 是「AI 已经在提问、用户作答」——那部分不是浪费，是机制在生效。

3. **「开工前多问」的空间比直觉小得多。**
   现有 `AskUserQuestion` 被调用 **177 次**（按 `message.id` 归并后是 175 次——
   有 2 次响应在同一条记录里带了两个提问 block，算一次提问；其中 176 次拿到有效回答，
   其余是入参校验失败），但**提问发生在工作深处**：提问前的中位工具调用数是 **405 次**，
   首次人类发言就提问的只占 6.7%。也就是说，用户和 AI 的共识是「先干起来再说」，
   问的都是过程中长出来的岔路。

## 二、定义与理由（这一节决定数字可不可信）

### 2.1 什么算「人工介入」

先给分母，否则「介入数」只是「对话轮数」的同义词。

每次 AI `end_turn`（把控制权交回用户）算一次**机会**。用户接过话，有三种情况：

- **正常对话**（`normal`）：新增需求、补充信息、会话开场任务书。**不算介入。**
  实测 1978 次，占人类发言的 81%。
- **介入**：用户这次发言是**在收拾上一步的烂摊子或补上一步的缺口**。
  798 次，占 19%。

这条分界线不是靠语气判，而是靠**AI 当时的状态**：

| 类型 | 判据 | 为什么算介入 | 次数 |
|---|---|---|---|
| 打断 | `[Request interrupted by user]` 或 `…for tool use]`（**两种变体，实测 195 + 20**） | 用户亲手按了停止 | 162 |
| 答问 | `AskUserQuestion` 的成功 tool_result | AI 主动开口问了，用户必须答 | 176 |
| 插话 | 用户发言时 `prevStop === 'tool_use'`（AI 还在干活） | AI 没停，用户强行塞话进来 | 76 |
| 纠正 | 消息 ≤600 字符且含否定/回退词 | 否定已有产出 | 19 |
| 催促 | 消息 ≤40 字符且以推进词开头（「继续」「接着」） | AI 停了但活没干完 | 365 |

### 2.2 「AI 停了 5 次等用户，算 5 次还是 1 次」

**算 5 次。** 理由：每一停都是用户必须付一次注意力才能推进的阻塞。合并成「任务级」
数字会把「一个长会话被反复打断」的痛感抹平——而那种长会话恰恰是最该被优化的。

同时给出按会话的口径（p50/p90/max），两种都摆出来，读者自己判断。上面的分布表
就是按会话口径。

### 2.3 「用户说继续」算不算介入

**算，前提是能找到它前面是谁停的。** 365 次催促里有 202 次跟在 `end_turn` 后面，
说明 AI 自己认为做完了。用户不同意——这个分歧本身就是失败信号。
（另有 143 次跟在 `stop_sequence` 后面，那是 API 故障，不是失败信号，见 4.3。）

但要区分两种成因，两者药方完全不同：

- **AI 用散文问句请示**：「要我继续吗？」「要不要我接着跑第 2 轮？」——48 次。
  有问有答，机制没问题，**格式错了**：该走 `AskUserQuestion`，不该耗一整轮自由文本。
- **AI 直接宣称做完就收工**——152 次。用户必须自己判断「它真做完了吗」，
  然后打「继续」。这是**完成标准没定清**，开工前就能问。

### 2.4 必须排除的三类假信号

不排除的话，介入数会虚高数倍。这三条都踩过坑：

1. **宿主注入的合成消息**。全量 `task-notification` **7129 条**、命令回显 423 条、
   `system-reminder` / `ide_opened_file` 等。它们是 `type: "user"`，但**不是用户打的字**。
2. **同一条 API 响应被拆成多条记录**。宿主把每个 content block 单独落盘，
   同一个 `message.id` 重复 3~7 次。某会话 8318 条 assistant 记录只对应 2663 个 id，
   原始 `end_turn` 计数 890 次，去重后只有 290 次——**虚高 3 倍**。
   且 `stop_reason` 只出现在**后几条**记录上（前几条是 thinking/text），必须「最后一个非 null 值生效」。
3. **同一会话的两份落盘**。实测 2 组，其中一组两文件 98% 内容相同（早期快照）。
   不按 `sessionId` 去重会把一个会话算两次。

### 2.5 `origin.kind === 'human'` 不能当必要条件

实测 2378 条人类消息带 `origin.kind: "human"`，但另有 **380 条真实人类消息根本没有
`origin` 字段**（2.1.270 之前的版本不写）。反过来，有 `origin` 但 `kind` 是
`task-notification` / `peer` 的必须排除。所以判据是：

- 有 `origin` 且 `kind !== 'human'` → 排除
- 有 `origin` 且 `kind === 'human'` → 保留
- **没有 `origin`** → 靠 `isMeta` 与合成前缀过滤后保留

## 四、哪一类介入最有可能被提问消除

### 4.1 答案：`P1` 里的「完成标准没定清」

**证据链**（这是全篇最值得看的一段）：

1. 365 次催促里，**202 次**发生在 AI 正常 `end_turn` 之后。AI 认为自己做完了。
2. 这 202 次里，**152 次** AI 的最后一句话里没有任何问句——不是请示，是宣告收工。
3. 用户回的是「继续」「继续把剩下的 HIGH 都修完」「继续，把 7 条验收跑完」。

这说明：**AI 对「做完」的定义比用户窄。** AI 完成了一个可交付单元就收工；
用户心里的「做完」是整条任务链走完。这个差异在开工时问一句就能消除：

> 「这轮做到哪个边界算完成——修完这一条，还是把这一批都修完？」

这类问题有明确答案、可以走结构化选项、且**不依赖任何过程信息**。这是唯一
能靠「开工前多问」系统性消除的类别。

### 4.2 反直觉的第二答案：`P1` 里的打断（73 次）

162 次打断里，73 次（45%）用户打断后说的是带新前提的实质指令，例如：

- 「撤回改动，大happy是我像改的，你改错了，英文只需要说 with happy 即可」
- 「不对不对，我说错了。我在质疑的点是为什么要添加信标附魔台末影箱……**而不是**
  为什么要手动『添加』节点」
- 「在哪里设置等待大厅传送点？等待传送点不应该是玩家局内出生点吗」

这些是**前提理解偏了**，不是执行错了。共同点：用户在开工时给的描述留了歧义，
AI 选了一种解释就开始干，干到一半用户发现选错了。这类也能靠「开工前把歧义点
指出来问」消除——但需要 AI 主动识别「这句话有两种读法」。

### 4.3 明确**不能**靠提问消除的（占 63%）

- **P3 环境故障 145 次（18.2%）**：143 次是 `stop_sequence`——实测 507 条
  `stop_sequence` 全部是 API 额度不足/模型不可用/网关错误。用户说「继续」是在等
  环境恢复。与对话设计无关，只能靠重试与降级。
- **P4 误触/主动停手 73 次（9.1%）**：打断后**什么也没说**（或只说「继续」）。
  这是用户按错了或临时想看别的，AI 什么都做错不了。
- **P2 过程信息缺口 28 次（3.5%）**：用户看到界面卡住、日志报错、真机闪退才报案。
  这些信息**开工时还不存在**，问也问不出来，只能靠 AI 自检更狠。
- **Q 已提问 224 次（28.1%）**：机制已经在跑。每把一次 P1 提前问掉，就多一次 Q。
  这不是浪费，是代价。

### 4.4 一个必须说清的坏消息

现有 `AskUserQuestion` 的**提问时机已经很靠后**：提问前中位工具调用数 **405 次**，
只有 6.7% 的提问发生在第一次人类发言时。这意味着现在的提问模式是
「干到一半撞上岔路才问」，而不是「开工前先把前提问清」。

所以「多提问」这个方向不是简单加大提问量——那只会把 Q 撑大。
真正要做的是**把提问前移**：在派发/开工的那一刻，识别出「这次任务里哪些前提
是猜的」，先问掉再动手。P1 的 295 次就是这个动作的收益上限。

## 五、测量器本身的可信度

### 5.1 一个真实的自我纠错记录

初版实现有三个缺陷，都是靠「拿独立实现复算」抓出来的，不是靠读代码发现的：

| 缺陷 | 后果 | 怎么发现的 |
|---|---|---|
| `end_turn` 按记录数算，未按 `message.id` 去重 | 5304 → 虚高到 16000+ | 用独立实现按 `message.id` 归并后对比，逐会话差 80 处 |
| 文件末尾的 assistant 记录未 flush | 以 AI 结束的会话各少 1 次 | 逐会话对比发现 2 处差 1 |
| `[Request interrupted by user for tool use]` 未匹配 | 20 次打断漏进「插话」类 | 抽样看 `interject` 内容时发现的 |

最终独立复算结果：**5304 = 5304，逐会话 0 处差异**。

### 5.2 单元测试守的是什么

34 条测试，每条对应一个实测反例，不是「能跑就行」：

- 合成消息过滤（7129 条 task-notification 一条都不能算人类发言）
- 同一 `message.id` 的多个 block 只算一次交还
- `stop_reason` 只在后段出现时仍要计入
- 会话第一条人类发言永远不算介入（实测 6 条开场任务书曾被误判成「纠正」，
  其中一份 9361 字符的规格文档在第 1706 字符处含「退回 Planning Agent」）
- 长文档不参与纠正判定
- 两种打断变体都归 `interrupt`
- 同一 `sessionId` 的多份落盘只算一个会话

### 5.3 稳健性

- 全量窗口（`--days 0`）与 30 天窗口的结论一致：P1 分别为 37.0% 与 38.0%。
- 催促使判据从「整条只有继续」放宽到「≤40 字符且以推进词开头」后，
  从 80 涨到 365——原判据漏掉了「继续，把剩下的 HIGH 都修完」这类。
  这是修正，不是膨胀：被补进来的每一条都在推 AI 往前走。

## 六、怎么复算

```bash
node scripts/measure-interventions.mjs              # 默认 30 天
node scripts/measure-interventions.mjs --days 0     # 全量（本文数字）
node scripts/measure-interventions.mjs --json       # 机器可读
node scripts/measure-interventions.mjs --root <dir> # 指定 transcript 根
node --test scripts/measure-interventions.test.mjs  # 34 条
node scripts/check-structure.mjs                    # 硬门
```

写作本文时：`check-structure` exit 0，全量测试 **756/756** 通过。

### 引用注意

所有数字随会话增长会变。本文的数字取自某一次运行；**当前这个正在写报告的会话本身
也会被写进 transcript**，所以再跑一次会多出 1 个会话、几十条记录——这不是误差，
是语料在生长。引用时请连同样本量和运行时刻一起引（271 会话 / 2438 人类回合 /
1.78 GB），不要只引百分比。本文的判据都写在代码里，改一行就会改变数字——
所以任何「改进」都必须用同一份脚本、同一套判据重测，否则不可比。

## 七、留给下一步的问题

1. **完成标准**：能不能在派发时就要求 AI 写下「这次做到哪个边界算完」，
   并在收工时逐条自检？这是 P1 里最大的一块（152 次）。
2. **歧义识别**：能不能在开工时标出「你这句有两种读法」？这是打断类 P1（73 次）。
3. **散文问句归位**：48 次「要我继续吗？」应该走结构化提问——但目前这类
   反而被算进 Q，掩盖了它其实是格式问题。
4. **P2 需要另一个指标**：AI 看不到用户眼前的现象，这个靠提问消除不了。
   要衡量它，需要另一个测量维度（自检覆盖率），不在本文范围内。

**这四条都不是本文能回答的。本文只提供一个可复算的基线，让后续改进能被证伪。**
