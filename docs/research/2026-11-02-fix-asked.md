## 结论先行

这次误报有**两个独立的成因**，修的是两处，不是一处：

| | 问题 | 改法 |
|---|---|---|
| **判定维度缺失** | `asked.mjs` 只看「单个 transcript 末行是问句 + 距今 < 24h」，回答不了「现在还值不值得提醒」 | 新增 `assessAsked()`，五条可离线复算的判据 |
| **分类错误** | `ASKED` 在 `HOST_FACT_STATES` 里，绕过了**所有**门禁 | 移出该数组，让它重新受分类门约束 |

第二处比第一处严重得多。第一处是阈值选得不对——会多报几条。第二处是**结构性豁免**：
一个状态一旦进了那张表，就同时绕过了分类门、时间门，以及此后加的任何一道门。
而它是被当成「宿主事实」加进去的，可它不是。

## 一、原 bug 的现场（可复算）

会话 `<session-B>`（<project-B>）：

```
问句           2026-11-01T23:31:45.824Z
宿主 statusUpdatedAt  2026-11-01T23:31:46.007Z   ← 晚 183 毫秒
其后唯一记录   2026-11-01T23:31:45.920Z  system/stop_hook_summary（+96ms，宿主簿记）
通知发出       2026-11-02T09:59:49.463Z          ← 静默 10.5 小时后
```

三个关键事实：

1. **问句是真的。** 「要我把这批改动提交吗？还是先继续清单里的 N 个任务？」——
   带具体选项，`classifyQuestion` 判 `decision`，客套门拦不住。
2. **它在 24 小时窗口内。** 10.5h < `MAX_QUESTION_HOURS = 24`，时间门拦不住。
3. **它问完那一秒就 idle 了，然后一整夜都是 idle。** 这是原判据结构上看不见的部分。

`statusUpdatedAt` 只比问句晚 183 毫秒这件事很重要：它说明**这次 idle 正是由这个问句造成的**。
宿主在 AI 停止输出的那一刻把它置为 idle，此后再没变过。
所以「会话 idle」这个信号本身既不能证明「在等人」，也不能证明「没在等人」——
它的语义只是「此刻没在跑」。要判断「还值不值得提醒」，需要另一个维度。

## 二、为什么 `MAX_QUESTION_HOURS = 24` 回答不了这个问题

原来的 24 是拿**回复延迟分布**标定的（2026-11-01 实测 492 个问答对：p90 = 14.7h、99% 在 24h 内）。
那个分布回答的是「多久没答算积压」。

本次要回答的是「**现在还值不值得打断人**」。两者不是同一个问题：

- 回复延迟：问句 → 人回话
- 恢复延迟：问句 → 会话下一条任何记录（AI 继续干活也算）

实测本机 241 个 transcript、**411 个问句结尾的 turn**：

| 问句后到下一条记录的间隔 | 累计占比 |
|---|---|
| ≤ 1h | 77% |
| ≤ 2h | 86% |
| ≤ 4h | 89% |
| **≤ 8h** | **93%** |
| ≤ 12h | 95% |
| ≤ 24h | 100% |

问句后「完全没有任何后续记录」的：**4 / 411**。

对比一下：问句 → 第一条**真人回复**的分布要慢得多（p50 = 29m、p90 = 15.44h、p99 = 27.64h）。
拿后者定阈值会让门槛形同虚设——会话早就自己继续干活了，人却在 15 小时后才回，
那种情况下再提醒是多余的。

## 三、8 小时是怎么选的（以及它漏掉什么）

取 8h = 「93% 该恢复的都恢复了」那条线。

**代价是可量化的。** 按同一组 411 个样本回推不同阈值的效果：

| 阈值 | 会提醒 | 会拦 | 被拦的里面后来真被回答的 |
|---|---|---|---|
| 2h | 350 | 61 | 57（漏报 13.9%） |
| 4h | 364 | 47 | 43（漏报 10.5%） |
| **8h** | **379** | **32** | **28（漏报 6.8%）** |
| 12h | 386 | 25 | 21（漏报 5.1%） |
| 24h | 407 | 4 | 4（漏报 1.0%） |

**这是主动选择漏报 6.8%，换取不再误报。** 依据是用户明确的口径：要的是「别再误报」，
不是「做到完美」。通知系统的信噪比已经在用户那里透支了——一条误报的代价是用户开始
忽略所有通知，那是断崖式的；一次漏报的代价只是少一条提示。

**为什么不取 12h / 24h**：本次误报的问句静默了 **10.5 小时**。12h 的门槛拦不住它，
24h 更是原样放过——那就等于没修。这条是硬约束：**新阈值必须低于被修 bug 的静默时长。**

**为什么不取 2h**：漏报率会翻倍（13.9% → 6.8%），而 2h 到 8h 之间拦掉的量只多 29 条。
实测数据里 2h 到 4h 之间是断崖（86% → 89%），4h 到 8h 之间只有 4 个百分点，
所以 4h 和 8h 的实际效果几乎一样（364 vs 379）。取 8h 是因为它同时覆盖了
「睡一觉回来还想回」这个真实场景，而 4h 会把「下午问的、晚上才回」全砍掉。

## 四、五条判据，以及为什么是这个顺序

```
1. silent-too-long              问句后一直静默 > 8h
2. continued                    问句后有带 message 的记录
3. answered-elsewhere           同 cwd 另一个会话里，问句后有人说过话
4. host-not-idle                sessions/*.json 的 status !== 'idle'
5. host-idle-before-question    idle 的时间戳早于问句
```

第 1 条排最前是有意的。它不依赖宿主、不依赖跨会话，**本次误报单独靠它就拦下了**。
如果把它放到第 4、5 条之后，一条「宿主读不到 + 没有兄弟会话」的会话就会绕过它——
那正是最危险的一类：数据缺失伪装成正常放行。

### 4.1 第 2 条：什么算「会话自己继续过」

判据是「带 `message` 的记录」。`system` / `attachment` / `last-prompt` / `cost-state` 都没有 `message`。

这条一开始写宽了：只要求「有记录」。结果**宿主在停止点后 96 毫秒写的
`stop_hook_summary`** 也被算成了「会话继续」——它也是带时间戳的记录，只是 `type === 'system'`。
如果按那个写法，本次要修的误报一条都报不出来（每个问句后面都有这条）。

### 4.2 第 3 条：跨会话证据必须索引**全部**会话

误报里说话的那个会话 `<session-E>` 当时自己已经继续干活了（不以问句结尾），
**所以它根本不是候选**。只索引候选会话会正好漏掉这条证据。

为此 `scanAll` 分成两遍：
- 第一遍读每份 transcript、登记其中真人消息、挑出候选
- 第二遍才对候选做对账

单遍会有一个隐蔽 bug：**结果取决于目录遍历顺序**。
`sibling` 排在 `asker` 后面时还没进索引，证据就不在。测试当场抓到了这个
（`scanAll：跨会话证据与目录遍历顺序无关`）——把两个文件名反过来，单遍实现的结果就变了。

### 4.3 什么算「人说的话」

`type === 'user'` 且 **`origin.kind === 'human'`**。

不用正则猜文本，因为 `tool_result` 也是 `user` 记录——用正则会把每一轮工具回执
都算成人话，等于「凡是有工具调用就是人类已答复」。`origin` 字段是宿主写的，
实测 `<project-D-slug>` / `Github` / `<project-B>` 的会话都有。

同时 `tool_result` 在**第 2 条**里是算数的（它证明会话继续了）——两件事必须分开，
合成一条 user 记录时最容易搞混。

### 4.4 第 4、5 条：`idle` 不等于「在等人」

第 5 条要挡的是：一个会话在**问句之前**就已经 idle 了。
那时这次 idle 与当前问句无关，会话是在问之前停着的，不是问完停在这的。

宽限 5 分钟（`ASKED_FRESHNESS.hostGraceMs`）：宿主写状态比 transcript 晚一点点
（实测 183 毫秒），但 5 分钟的宽限足以覆盖一次慢写，又不足以掩盖「昨天就停着了」。

## 五、第二处修复：`ASKED` 不在 `HOST_FACT_STATES` 里了

```js
// 改前
export const HOST_FACT_STATES = Object.freeze(['WAITING', 'BLOCKED', 'FAILED', 'ASKED']);
// 紧邻注释：「这三者对分类门/时间门免疫」
```

数组是四个、注释写「这三者」——这是这件事留下的痕迹：加进去的时候没人去核对
「这张表的定义是什么」，只看到「它也是通知源」。

**这张表的定义是「由宿主直接写下、不经过 transcript 推断的状态」。**
`ASKED` 是从 transcript 文本推断出来的（`asked.mjs` 文件头第一句就是「不依赖宿主」），
按定义就不该在里。它进去了，于是绕过了：

- `kind-not-notifiable` 门
- `unclassifiable-too-recent` 时间门
- 以及此后加的任何一道门

观察日志还把它标成 `"classify":"host"`——一个推断信号的来源被记成宿主，
连事后复盘都会被误导。

**改法**：收窄为 `['WAITING','BLOCKED','FAILED']`，注释重写并写明判据：

> 判断一个状态该不该进这张表，只问一句：**这个结论是谁下的？**
> 宿主下的结论 → 进。我们从文本猜的 → 不进。

`ASKED` 现在走和其它推断状态一样的路：分类器会判出 `ASKED_UNANSWERED`
（那是 `NOTIFY_KINDS` 的一员，所以不会因此变成永远不通知）。
另外 `watch.mjs` 的 asked 层调用现在**传了 `sessionsRoot`**——
不传的话 `asked.mjs` 会退化成老行为（`freshness: 'host-unknown'`），也就是修复前的样子。

## 八、诚实的边界

1. **8 小时是主动选的漏报率**，不是「正确答案」。按本机样本它会漏掉 6.8% 最终被人回答的问题。
   如果实际使用中觉得漏报太多，应当基于真实反馈重新标定，而不是凭感觉调数字。
2. **跨会话判据按 cwd 精确匹配**。用户换了目录、或者在同一个项目里开了不同子目录的会话，
   这条判据就不生效（退回其它四条）。这是有意的保守：拿不准就别拿别人的会话当证据。
3. **`origin.kind` 是新字段**。老 transcript（2026-10 之前）可能没有，那样跨会话判据会把
   那个人当成「没说过话」——方向是漏报，不是误报，符合 fail-closed 的要求。
4. **本次没能做完整的真机回放。** `<session-B>` 的 transcript 在那之后被测试会话追加过
   （`2026-11-02T13:23` 的 RESUMED 注入），所以「按当时的 nowMs 重跑扫描」不再能复现现场。
   原 bug 的验证改用固定时钟 + 构造记录（见 `asked.test.mjs` 里标注为「本次 bug 核心」的用例），
   所有时间戳都取自真实的 `<session-B>`。
