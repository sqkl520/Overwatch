## 零、一句话结论

文档的问题不是「有几处写错了」，是**「写错了没人会知道」**。所以本轮的重点不是把那几处改对，
而是把「会写错的地方」变成提交前会红的检查——和已有的 `checkTestCount()` 同一个思路。

本轮改了 4 类文档不一致、新建 3 份文档、给硬门加了 5 道检查（含 1 道覆盖全新维度）。
其中 **2 道检查在本轮工作期间就当场抓到了真实漂移**（测试数 860→871、新报告未登记），
这不是演示，是它们第一次运行就发生的事。

## 三、长效机制：把「记得同步」换成「不同步就红」

### 3.1 已建成的五道检查（都在 `scripts/check-structure.mjs`）

| 检查 | 守什么 | 成本 | 负向测试（把错放回去，确认变红） |
|---|---|---|---|
| `checkDocReferences()` | 活文档引用的 `scripts/` `templates/` 路径必须存在；计划中的须标「待建」 | <10ms | ✅ 改成本文不存在的脚本名 → 红 |
| `checkDocCommands()` | 文档里 `node scripts/x.mjs --flag`：脚本存在 + `--flag` 被源码支持 | <10ms | ✅ 加 `--bogus-flag` → 红 |
| `checkDocConstants()` | 文档写 `` `CONST = N` `` 时，源码该常量必须是 N | <10ms | ✅ `MAX_SUBAGENTS = 100` 改 30 → 红 |
| `checkResearchIndex()` | 每份研究报告必须在索引登记 + 索引保留状态标记 | <10ms | ✅ 放一个未登记文件 → 红 |
| `checkCapabilities()` | 能力清单每条命令可执行 + README 指向它 | <10ms | ✅ 断链/改错命令/删入口 → 分别变红 |

它们与已有的 `checkTestCount()` / `checkLinks()` / `checkDesignIndex()` / `checkChangelog()` 同源。
**总耗时仍是「一秒内」**——全是读文件正则，不跑任何子进程（除了 `checkSyntax` 那条既有的）。

### 3.2 能力声称可验证化：`docs/CAPABILITIES.md`

这是任务书要求的 (a)。做法：README 的「能做」表每一行，在 `CAPABILITIES.md` 里有一条**能跑的命令**。

**它的边界（必须说清）**：硬门能证明「命令的脚本与参数真实存在」，**不能证明「输出支持这句声称」**。
后者要人读一遍输出。所以它挡的是最坏的一种——能力还写在 README 里、脚本已经删了——不是全部。

### 3.3 数字集中管理：结论是「**不要集中**」

任务书要求的 (c)。我考虑过「把所有数字收进一个 JSON」。**不做，理由如下**：

- 数字分两类。**会漂的**（测试数、扫描耗时、介入次数、报告份数）和**不会漂的**（常量、阈值、路径）。
- 会漂的数字**根本不该被写下来**。收进 JSON 只是把「文档里一个错数」变成「JSON 里一个错数」，照样要人记得更新。
  正确做法是**改成引用命令**：README/GUIDE 里所有耗时、占比、次数都改成「跑 X 命令看」，并说明为什么。
  本轮已这样改（D7、介入次数、报告份数）。
- 不会漂的数字**已经**被 `checkDocConstants()` 守住了（显式 `CONST = N` 形态）。再做一层 JSON 是重复。
- 唯一值得机械对账的是**测试数**——它变化频率最高且散落四份文件，`checkTestCount()` 已经处理。

所以 (c) 的答案是：**不做集中管理，做「会漂的改成命令引用 + 不会漂的进硬门」**。

## 四、「不值得做」的机制（附理由）

任务书明确要求：成本高于收益的，说清不值得。以下三个我评估后**放弃**：

### 4.1 检查「散文里的数字」——不值得

「子 agent 上限 **100**」「每会话 24h **≤2**」这类句子里的数字，要判断它指的是哪个常量，
需要语义理解。我试做了一版正则（数字后 14 字内出现常量名即比对），在真语料上**立刻给出 2 处误报**：
`PER_SESSION_MAX_24H` 前面的「24」是文件名的一部分、`COL_PROJECT` 前面的「156」是行号。
误报率一旦超过 10%，维护者就会把整道门关掉——**一道会被关掉的门比没有门更坏**，
因为它制造「检查过了」的错觉。只保留零误报的显式 `` `CONST = N` `` 形态。

### 4.2 真跑文档里的每个命令验证 exit 0——不值得，且有害

任务书 (b) 提到「`node scripts/xxx.mjs --help` exit 0」。实测这个不可行：
- `scan-sessions.mjs --help` **不认 `--help`，直接开扫**（实测 77 秒）。
- `verify-bugfix-negatives.mjs` 会**改写源码再还原**，绝不能在门里跑。
- `stop-verify-hook.mjs` 读 stdin，无输入会等超时。
所以改成「静态验证脚本存在 + 参数在源码里出现过」。它抓不到「参数存在但运行时崩」，但那类由 CI 的 Tests 步骤兜。

### 4.3 给每份研究报告强制状态字段——本机已过重，不做

可以要求每份报告 frontmatter 带 `status:` 并逐份校验。但 66 份历史报告的分类是**人读出来的判断**
（「这条被后续报告推翻了」），不是机器能从文件读出的属性。硬门最多能查「索引里提到了这份文件」
（已做），查不了「状态标对了没有」。强行加字段只会得到 66 个 `status: unknown`。

## 五、文档结构建议

现状：`docs/` 下 66 份 research + 11 份 design + 10 份 spec + 2 adr + 6 份游离文档，
根目录还有 README/CLAUDE/CHANGELOG。**新来的人会迷路**——这是真的，我自己第一遍也点了错的文件。

### 5.1 已做的：加一个入口

新建 `docs/README.md`，按「你想知道什么」指路，并**说清四类文档的可信度不同**：

| 目录 | 可信度 | 引用前要做什么 |
|---|---|---|
| 根 / `docs/*.md` | 当前事实 | 数字跑命令复核 |
| `spec/` | 当前事实（唯一真源） | 与代码冲突以代码为准 |
| `design/` | **全部未实现** | 先看状态列 |
| `research/` | **会过期的过程记录** | **先查状态标记** |

这比「合并文件」更有效：问题不是文件太多，是**读者不知道手上这份该信几分**。

### 5.2 建议合并的

| 现在 | 建议 | 理由 |
|---|---|---|
| `docs/observe-period.md`（P0 观察期） | 移入 `docs/research/`，索引里标「历史阶段」 | 它描述的观察期已结束（文件自己写「上一版作废」），是过程记录不是当前手册 |
| `docs/install-watcher.md` | 并入 `docs/GUIDE.md` 一个 §，或移入 `docs/research/` | Windows 自启的实测踩坑，面向使用者但很窄；留在主线增加入口噪声 |
| `docs/PUBLISH-TRIAGE.md` | 移入 `tasks/`（不可发布区）或归档 | 它是**一次性分拣清单**（判定日期 2026-11-02），不是长期文档。放在 `docs/` 会被当成「当前发布规则」 |

### 5.3 建议归档（移出主线、保留）

| 文档 | 为什么归档而不是删 |
|---|---|
| `design/` 里 4 份 `Proposed` 且「技术前提已实测不成立」的（`frontend-and-shape` / `hosted-mode` §1§3§5 / `continuation-engine` 第三件 / `2026-11-04-next-phase-plan`） | 里面有大量实测数据，删了要重做。索引已标状态，够用 |
| `docs/spec/original-design.md` | 已被推翻的原始稿，但它是「为什么改」的证据。**保留**，已在文件头声明失效 |

### 5.4 入口该怎么组织（最终形态）

```
README.md                 产品定位 + 30 秒上手 + 能力边界（对外门面）
docs/README.md            总入口：按问题指路 + 四类可信度              ← 新建
docs/CAPABILITIES.md      能力 → 命令（硬门核）                        ← 新建
docs/GUIDE.md             使用手册（输出怎么读、出问题怎么办）
docs/CHANGELOG.md         改动流水账
docs/spec/                现行规格（唯一真源）
docs/adr/                 决策
docs/research/README.md   研究索引 + 已推翻结论（**引用任何 research 前必看**）
docs/design/README.md     设计索引（全部未实现）
```

**判断入口够不够用的标准**：一个没读过这个仓库的人，能不能在**不点开任何子目录**的情况下，
从 README 找到「我想知道的下一份」。现在可以了。
